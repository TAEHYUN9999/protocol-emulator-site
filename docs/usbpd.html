File Role Words
firmware/usbpd_sink.pe USB PD sink on the CC line at logic level. Hart 1 decodes BMC into raw 5-bit symbols; hart 0 follows them as they arrive (4b5b decode, CRC-32 per nibble), answers every good SOP Message with GoodCRC, drops repeated MessageIDs, requests a PDO from Source_Capabilities and retries the Request when its GoodCRC does not come. 498 of 512 (hart 1 starts at word 420)

This protocol was not part of the design when the RTL was written. It uses only existing instructions (shout, rel, waitp.to, tset/tsetr/twait, tgeth/tgetl, ld/st on the data memory and the frame buffer, host FIFO); the RTL is unchanged. The chip's CRC unit is 16 bits wide, so the CRC-32 is computed in software, one bit per 13 to 21 instructions. Checked in simulation only, not on a board.

Section numbers are those of the Universal Serial Bus Power Delivery Specification, Revision 3.3, Version 1.0 (October 2026), downloaded from usb.org.

Not implemented: Hard Reset and Cable Reset signalling (only SOP frames are taken), Soft_Reset handling, Not_Supported answers, the sink's timers above the Protocol Layer (SinkWaitCapTimer, PSTransitionTimer, SenderResponseTimer), collision avoidance by Rp (5.2.2: the sink only answers), extended and chunked Messages, PPS/AVS RDOs, VCONN, SOP'/SOP''.

Pins

Constant Default Use
CC P0 the CC line as one logic level: the chip drives it push-pull while it sends and lets go after; the source model drives it the same way; a line nobody drives reads high

A real CC line idles at a level set by Rp and Rd and swings by vSwing (1.125 V); a BMC transceiver between the line and the pin (comparator and tri-state driver) is assumed.

Timing

HALF = 42 ticks is half a unit interval: 3.36 us per bit, 297.6 kbit/s. The longest path between two twaits in txsend is 11 ticks (the next symbol's load). The receiver (hart 1) sets the timer to Q3 = 63 ticks, 3/4 of the nominal unit interval, at every boundary edge: an edge before it is the middle of a 1 and the next boundary must follow within another 63 ticks; no edge is a 0, and its boundary must come within 63 more. 63 ticks lies between half a UI and a UI over the whole fBitRate range (37.9 to 46.3 ticks and 75.8 to 92.6 ticks). The work per bit (store, symbol, alignment) is at most 20 ticks after the boundary, before the earliest middle edge.

Hart 0 decodes a nibble and runs four CRC-32 bits in about 190 ticks, while a symbol takes 420; at the EOP only the residual and the header are left. It then builds and encodes the GoodCRC (two bytes and their CRC, about 500 ticks) inside the 1000-tick IFGT wait.

Host interface

Address Use
0x00 POS object position to request (1 to 7; 0, or more than the source offers: 1)
0x10 good Messages received (CRC and length right)
0x11 frames dropped (CRC, 5b error, length, broken off)
0x12 repeated MessageIDs acknowledged and dropped
0x13 retries of the Request
0xA0.. the last Message received: header, data objects, CRC
0xC8.. the last Message sent, with its CRC

Events to the host FIFO (dropped when the FIFO is full): every new Message as NDO << 4 | Message Type (21h Source_Capabilities with 2 PDOs, 03h Accept, 06h PS_RDY), 01h the GoodCRC of our Request, 00h our Request got no GoodCRC after nRetryCount retries.

The frame buffer holds the 4b5b table (0x20), the symbols to send (0x30) and the received raw symbols (0x50 to 0x9F), so Ethernet and the capture cannot run with this firmware.

Tests

test/test_usbpd.py (cocotb). The source model is written from the spec (sections in the module docstring): packet building, 4b5b, CRC-32 as a shift register, BMC encoding, and a decoder that rebuilds half cells from the chip's edge times. Only the host interface above is taken from this page. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T COCOTB_TESTCASE=<test> make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_usbpd

Every chip frame is checked: preamble of 64 bits from a low level, SOP, symbols, CRC, every edge interval in clocks, refBitRate over the last 32 preamble bits, pBitRate over every later 32-bit window, the trailing edge, low time before release and release time.

Controls

Each change was made in a copy of usbpd_sink.pe and run with USBPD_FW pointing at it. All fail, each at the check it aims at:

Change Test Caught by
GoodCRC always with MessageID 0 test_pd_contract the GoodCRC of the Accept (MessageID 1) has MessageID 0
HALF = 50 (250 kbit/s) test_pd_contract refBitRate 250.0 kbit/s, under 270
IFGT = 100 (no tInterFrameGap wait; the GoodCRC goes out when it is built) test_pd_contract GoodCRC preamble 24.95 us after the EOP, under 25 us
The transmitted CRC not complemented test_pd_contract the model finds the CRC of the first GoodCRC wrong
No duplicate check test_pd_errors the repeated Accept is reported again (events 31h, 01h, 03h, 03h)

The IFGT control shows that building the GoodCRC alone takes about 21 us: the firmware meets tInterFrameGap only because of the wait.

Limits

  • One fixed bit rate for sending (297.6 kbit/s); receiving is checked at 270, 300 and 330 kbit/s.
  • SOP only; no Hard Reset, Cable Reset, Soft_Reset, Not_Supported, BIST; no extended Messages. Messages of up to 7 data objects.
  • The Request takes the maximum current of the chosen PDO and does not check the PDO type (fixed supply assumed).
  • A Message other than GoodCRC that arrives while the Request waits for its GoodCRC restarts the timer (its GoodCRC uses it) and overwrites the stored Request symbols, so a later retry would be wrong; the source does not do that in a normal sequence.
  • The source model waits 2 ms between Accept and PS_RDY instead of tPSTransition (450 to 550 ms); the sink has no PSTransitionTimer.
  • Logic level only; vSwing, rise and fall times, the eye masks and the receiver thresholds (5.3.4.1 to 5.3.4.3, Table 5.11) belong to a transceiver.
  • Simulation only: no board, no gate-level run.
