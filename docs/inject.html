The host writes a small table into the data memory: at which byte (and bit) of a transfer, which error, how many times. The firmware that plays the protocol puts exactly that error there, and the counterpart under test has to notice it at that place and react (a NAK and a retransmission, a NACK, an error status). Three firmwares, one hart each, simulation only:

Firmware Role of the chip Words of 512 Errors it can put in
firmware/inject_uart.pe UART transmitter of a packet (8E1, CRC-8 trailer), retransmits on NAK 213 data byte flip (also of the CRC byte), parity bit flip, low stop bit (framing), one bit longer or shorter, a glitch in a bit
firmware/inject_i2c.pe I2C controller: write with SMBus PEC, then a read after a repeated START; repeats a failed attempt 309 byte flip (also of the PEC), early NACK of a read byte, STOP after a byte, repeated START before a byte, one SCL low phase longer or shorter, an SCL glitch
firmware/inject_spi.pe SPI master (mode 0): data frame with CRC-8, then a status frame; repeats while the status is not 0 198 byte flip (also of the CRC byte), CS raised early, one SCK low phase longer or shorter, one extra SCK pulse

Why the injector sits inside the emulating firmware

These firmwares were written on the 512-word RTL before the per-hart pin registers, where both harts wrote one shared pair of pin registers (pin_out, pin_oe) and the later write won. A second hart could therefore not add a fault to a line the first hart drives without taking the line over (its rel would also release the other hart's low). So the corruption is made by the same hart that runs the protocol: before each byte it looks up the table and changes that byte's bits, timing or framing itself. This covers the deliberately misbehaving device or controller of protocol exercisers (Prodigy, Corelis), but not "an independent second device that disturbs somebody else's traffic". The RTL now in src/ (commit 422ec10) has per-hart output registers combined as a wired AND (dual_role.md, firmware/glitch.pe), so a second hart could run this table against a foreign device's transfer; that is not done here, and the three injectors still corrupt their own traffic, unchanged.

Table (data memory 0x10 to 0x1F, written with DATA_W before the run)

Four entries of four bytes:

Byte Name Meaning
+0 POS wire byte index of the transfer, from 0 (see each protocol); 16 and above never match
+1 TB bits 3..0 the type, bits 7..4 the bit B the type acts on (only for the bit types)
+2 VAL value of the type (XOR mask, ticks)
+3 CNT how many more times; 0 = entry off. CNT drops by one each time an attempt reaches POS, so CNT = n corrupts n attempts that get that far. The host reads it back with DATA_R

At the start of every attempt the firmware copies the entries with CNT > 0 into a per-byte plan (frame buffer bytes 0x40 to 0x7F), so the per-byte lookup costs three loads; two entries for one POS: the later one wins. Every type code means the same thing in all three firmwares:

Type Name UART I2C (controller) SPI (master)
1 FLIP wire byte XOR VAL; parity and CRC stay those of the true byte (a line error) written byte, PEC or read address byte XOR VAL; the PEC stays that of the true bytes byte XOR VAL; the CRC stays that of the true payload
2 PAR parity bit inverted - -
3 NACK - a read byte that is not the last is NACKed (ACK to NACK), then STOP -
4 STOP stop bit sent low (framing error), then the line idles high STOP right after this byte's ACK clock CS raised after this byte (frame ends early)
5 RSTART - repeated START before this byte (written bytes 1 and up), then the byte unchanged -
6 LONG bit B lasts BIT + VAL ticks, all later edges move SCL low phase of clock B lasts 2Q + VAL ticks (SDA change to SCL rise Q + VAL) SCK low phase of bit B lasts H + VAL ticks
7 SHORT bit B lasts BIT - VAL ticks SCL low phase of clock B lasts 2Q - VAL ticks SCK low phase of bit B lasts H - VAL ticks
8 GLITCH the line inverted for VAL ticks from BIT/2 - VAL/2 ticks after the start of bit B SCL pulled low for VAL ticks, Q + 9 ticks after the rise of clock B (in its high phase, after the sample point) one extra SCK high pulse of VAL ticks, 10 ticks after the fall of bit B

Bit numbering: UART B = 0 start, 1 to 8 data bits 0 to 7, 9 parity, 10 stop. I2C B = 0 to 7 the data clocks (0 = first, MSB), 8 the ACK clock; the glitch takes B = 0 to 7. SPI B = 0 to 7 (0 = first, MSB). A type that has no meaning for the protocol (a dash above) does nothing but still uses one count. One tick is 40 ns, so glitch widths and timing steps are multiples of 40 ns.

UART (inject_uart.pe)

Pins: P0 = TX (to the receiver under test), P1 = RX (its one-byte answer, 8N1: 0x06 ACK, anything else NAK). One hart (CTRL = 1).

Address Name
0x00 BIT ticks per bit; 50 (500 kbit/s) in the tests. A GLITCH needs BIT/2 - VAL/2 >= 16
0x01 LEN payload bytes 1 to 8 (0x08 to 0x0F); wire byte LEN is the CRC-8
0x02 MAX attempts at most
0x03 TRY firmware: attempts made
0x04 RES firmware: the last answer (0x06, the NAK byte, 0 if none came within 4095 ticks)

One attempt: LEN + 1 characters, each start, 8 data bits LSB first, even parity, one stop bit, 150 ticks of idle before each; the CRC-8 is x^8 + x^2 + x + 1, start 0, over the payload, computed with the crc instruction (polynomial 0x0700 left aligned). Then the firmware waits for the answer, and starts the next attempt after a NAK while TRY < MAX. Any byte from the host FIFO starts a packet; RES goes back to the host at the end. Every bit edge comes from a twait followed by a tsetr two ticks later, so each bit's length is set on its own: the long or short bit is exact and no other bit changes.

I2C (inject_i2c.pe)

Pins: P0 = SCL, P1 = SDA, open drain (the firmware only pulls low or lets go; the test checks that it never drives high). No clock stretching is followed. One hart.

Address Name
0x00 Q quarter bit in ticks; 21 in the tests (tLOW = tHIGH = 2Q = 1680 ns, about 300 kHz). 14 or more, 18 + VAL or more for a GLITCH
0x01 WL written bytes, the address byte (A6..A0, 0) first, 1 to 8 (0x08 to 0x0F)
0x02 RL bytes read after the repeated START, 0 to 16, stored at 0xA0
0x03 MAX attempts at most
0x04 TRY firmware: attempts made
0x05 RES firmware, last attempt: bit 0 an ACK was due and SDA was high, bit 1 cut short by an injected STOP, Sr or NACK; 0 = clean
0x06 PEC 1: the SMBus PEC (CRC-8 over the written bytes, address byte included) follows the written bytes

Wire positions: 0 to WL - 1 the written bytes, WL the PEC (if PEC = 1), then the read address byte (address | 1, after a repeated START), then the bytes read (all ACKed but the last). Every clock is four events Q ticks apart: SCL falls, SDA changes, SCL rises, SDA is sampled (tHD;DAT = tSU;DAT = Q). Between bytes SCL stays high Q + 100 ticks (the ACK clock's high phase), the time the firmware needs for the next byte; START to the first fall and Sr to the next fall are 100 ticks too, and the bus is free 100 ticks after P. An attempt that got a NACK or was cut is repeated while TRY < MAX.

SPI (inject_spi.pe)

Pins: P0 = SCK, P1 = MOSI, P2 = MISO, P3 = CS_N. Mode 0, MSB first. One hart.

Address Name
0x00 H SCK half period in ticks; 20 in the tests (625 kHz). 18 + VAL or more for a GLITCH
0x01 LEN payload bytes 1 to 8 (0x08 to 0x0F); wire byte LEN is the CRC-8
0x02 MAX attempts at most
0x03 TRY firmware: attempts made
0x04 RES firmware: the device status read after the last data frame

One attempt: the data frame (CS low, the LEN + 1 bytes, CS high), then a status frame (CS low, 0x05, 0x00, CS high) whose second MISO byte is the device status. Status not 0: the next attempt while TRY < MAX. SCK falls and MOSI changes one tick later; SCK rises and MISO is sampled. After the last rise of each byte SCK stays high 80 ticks (time for the next byte). CS falls 80 + H ticks before the first rise and rises H after the last fall.

Counterpart models (in test/test_inject.py, from the protocol documents)

  • UART receiver: a 16450/16550-class receiver as the Intersil 82C50A data sheet describes it: it finds the start bit on the falling edge, checks it in its middle and samples every bit once in its middle (the model samples 10 ns past the middle, so it never meets an edge the chip makes on the 20 ns grid); parity error when the even parity does not match, framing error when the stop bit is low. After a framing error this model waits for the line to go high before it looks for the next start bit (the PC16550D instead takes the low stop bit as the next start bit). Then the packet check (CRC-8 over the payload, check value 0xF4 of "123456789" asserted in the test), and the answer 0x15 (any error) or 0x06, sent 8N1 two bit times after the last stop bit.
  • I2C target: NXP UM10204 Rev. 7.0: 3.1.3 (data stable while SCL is high), 3.1.4 (START, STOP), 3.1.5 (byte, ninth clock), 3.1.6 (ACK, NACK), 3.1.10 (address and R/W). Its SCL and SDA inputs pass a spike filter that suppresses pulses up to 50 ns (Table 10: tSP 0 to 50 ns in Fast-mode; note 8, "Input filters on the SDA and SCL inputs suppress noise spikes of less than 50 ns"); data valid 200 ns after a (filtered) SCL fall. It computes the SMBus PEC over every byte from the START and NACKs a wrong one (SMBus 3.2, 6.4 and 6.4.1: a target may NACK a wrong PEC, as docs/smbus.md cites). It records every byte with its position and ACK, every repeated START, the position of P, the controller's NACK of a read byte that was not the last, every SCL low phase and every suppressed spike. The test also measures every SCL low phase against Table 11 (Fast-mode tLOW 1.3 us).
  • SPI device: mode 0 (MOSI taken at the SCK rise, MISO changed 50 ns after the fall, frame = CS low). At CS rise a data frame gets a status: bit 1 when the bit count is not a multiple of 8, else bit 2 when it is not LEN + 1 bytes, else bit 0 when the CRC-8 is wrong; 0 otherwise. A 16-bit frame starting with 0x05 is a status read: the status comes as its second byte. The model also records every SCK low and high phase. Its minimum SCK low time is set to 700 ns in the test (a device parameter of this model, not of a named part).

Only the data memory layout, the table format and the meaning of the types (this page) were taken from the firmware side; the expected edges, bytes, errors and statuses are worked out in the test from that meaning and from the documents above.

Controls

Control Change in the copy Test Result
uart_table_ignored plan returns at once: no entry is ever copied into the per-byte plan test_uart_table caught: the receiver reports no error at all and ACKs the first attempt ([[]] instead of the four error lists)
uart_flip_wrong_bit FLIP shifts VAL left once: 0x10 flips data bit 5 instead of 4 test_uart_table caught: the error lists are the same (one wrong bit gives a parity and a CRC error either way), but the edges of byte 2 in attempt 1 are at clocks 0, 100, 500, 600 instead of 0, 100, 600, 1000

Limits

  • These firmwares corrupt only their own role: they do not disturb a transfer between two other devices. The RTL in src/ could (per-hart pin registers, firmware/glitch.pe, see above); that is not done here.
  • Glitch widths and timing steps are whole ticks (40 ns); one hart changes a pin only every other clock. A 1-tick (40 ns) SCL glitch is below the I2C Fast-mode tSP and a 2-tick one above, so the 50 ns filter boundary is checked at those two points only.
  • The I2C controller does not follow clock stretching and drives the line only low. The SCL high phase of every ACK clock is Q + 100 ticks.
  • Positions are whole bytes plus a bit (or clock) index; at most four entries, positions 0 to 15.
  • A type acts on one position per attempt; an entry is used up as soon as an attempt reaches its byte, even if an earlier entry in the same attempt makes the counterpart reject the transfer.
  • Simulation only, not run on a board.
