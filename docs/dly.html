Branch int5d, part D1 of the plan of int5 (int5.md). The chip's clock is 20 ns and every pin edge it makes or takes falls on a clock edge (10 ns for the two line units that use both edges). The delay lines add a step of about a nanosecond for four pins: the firmware can place the output edges of P0 to P3 later than the clock edge and can move the instant at which an input is sampled earlier, in taps of 0.5 to 1.2 ns depending on voltage, temperature and process. A calibration circuit measures how many taps one clock is on this chip right now, so a firmware can turn taps into nanoseconds and can notice a drift.

After reset every line is bypassed. A firmware that never writes a delay line register runs on a chip that behaves, clock for clock, like the one without the lines: one multiplexer cell was added to each of the twelve pin paths.

What is built is the hardware, the three instructions, the assembler and reference model rows and the tests (part D1), and a training firmware with retraining rules, firmware/dly_train.pe (part D3, below). The finer USB edges (part D2 of the plan) use the lines of P0 and P1 and bit 6 of register 0; they are described in usb_fs.md.

src/pe_dly.v (u_dly in the top level):

  • A tap is two sg13cmos5l_dlygate4sd3_1 cells in a row. A line is a chain of 46 taps, a tap multiplexer (sixteen sg13cmos5l_mux4_1 in three levels, 48 inputs) that picks the signal behind 0 to 46 taps, and a bypass multiplexer (sg13cmos5l_mux2_1) that picks the undelayed signal or the tap multiplexer's.
  • Each of P0 to P3 has three lines: one for its output bit, one for its output enable, one for its input. The output line and the enable line of a pin take the same tap from one register and the same enable, so the two pad bits are delayed alike. The pad rule of dual_role.md (a pad never changes its output and its enable at one edge in the two moves where the step in between would be low) therefore holds behind the lines: two changes that left the pad registers one clock apart reach the pad one clock apart.
  • The output lines sit behind the multiplexer that hands P0 and P1 to the USB line unit, so they delay whoever drives the pin. The input lines sit in front of both synchronizers of the pin (the rising-edge one for the cores, the capture and the launcher, and the falling-edge one of P0 and P1 for the USB receiver).
  • The lines are not gated: a bypassed line's chain still follows its pin.
  • Twelve lines and the calibration chain are 13 x 46 x 2 = 1,196 delay cells, 192 tap multiplexer cells and 12 bypass cells.
  • The chains had 44 taps (1,144 delay cells) until commit 9f0336f; the one layout with the lines, run H4d, is of that RTL (Calibration, Hardening).

Registers and instructions

Eight registers, one byte each: {enable, 0, tap[5:0]}. Bit 6 is not kept and reads 0, except in register 0, where it turns the fine USB edges on (part D2): while it is set and USB is selected, the output and enable lines of P0 and P1 are on with the enable bit of register 0 and take, transition by transition, tap 0, the tap of register 0 or the tap of register 1 (usb_fs.md). Outside USB the bit changes nothing.

Register Line
0 to 3 output bit and output enable of P0 to P3
4 to 7 input of P0 to P3
  • tap = k selects the signal behind k taps, k = 0 to 46; a value of 47 to 63 selects 46. With the line on and tap 0 the signal still passes the tap multiplexer (three cells) and is not the bypassed path.
  • enable = 0 bypasses the line. The registers are 0 after reset and after a soft reset (host CTRL bit 2).
  • A write that turns a line off takes effect one clock later (the line select is a flip-flop of its own, so the bypass multiplexers are driven from flip-flops). A write that turns a line on takes effect once the line's input has been still for three clocks and cal is in range, as a change of the calibration range does (Calibration); the tap register itself changes one clock after the write.
  • All four harts share the registers. Two cores writing the same register in the same clock: core 0's byte stays, as for the general outputs and the launcher reference. Writes of two different registers in one clock both land. A read in the clock of a write sees the old byte.

Instructions, on opcode 0xF beside ljmp, lcall, ldx and stx (architecture.md), one tick each, flags untouched:

Instruction Word Meaning
dlyw sel, rs 1111 0 sss 1000 1 ccc register sel (c) = rs (s)
dlyr rd, sel 1111 0 ddd 0000 1 ccc rd = register sel
dlyr.cal rd 1111 0 ddd 0100 1 000 rd = {in range, 0, cal[5:0]}

No firmware of the repository used opcode 0xF bit 3 before, and every firmware file assembles to the same words as before (test/check_asm_compat.py, below).

STATUS byte 11, the RTL revision, is 0x02 on an RTL with the delay lines, 0x03 since the fine USB edges of part D2, 0x04 since branch int6 and 0x05 since its fixes of 2026-11-14, which include the rule that a line follows the calibration range only while its pin is still (0x01 before, architecture.md). The host has no command for the delay line registers; the revision tells a host program whether a firmware that uses dlyw can run. host_read_steal.md, a design that is not built, had named revision 2 for its new read commands; it now names the revision after this one.

Rules for a firmware

  • Write a register only while its pin has been still for longer than the line is long, and keep the pin still for one more clock: the bypass multiplexer and the tap multiplexer then switch between equal levels. Three clocks of quiet cover the slow corner (46 taps are 54.7 ns there by the liberty). A write while an edge is inside the chain can make a short pulse on an output or a wrong sample on an input.
  • The chip's own switch between delaying and bypassed (when cal leaves or re-enters the range) waits for the same quiet, but it sees only the last two clock edges, so it is safe only for a line shorter than about three clocks: a tap of at most about 3 x cal taps. A line set to a longer tap (possible near the lower end of the range, cal 12 to 15, where 46 taps are more than three clocks, and below it) can still hold an edge when the range changes, and that switch can then cut a pulse on the pin. The taps of the fine USB edges (cal / 6 and cal / 3) are far below this. A firmware that sets a longer tap must accept a possible short pulse when the calibration leaves or re-enters the range while that line is in use.
  • A line whose input changes at least every two clocks is never still for three clocks, so it does not follow a change of the range: it keeps delaying with its tap after cal leaves the range, until its input pauses. dlyr.cal bit 7 tells that the range is left, not whether a line has followed; no register reads the line select. A firmware that must fall back to the 20 ns grid pauses the pin for three clocks, or writes the register with the enable bit clear.
  • Even between equal levels a multiplexer cell may show a very short pulse when its select changes (the simulation has none; whether the library's cells do is not known here). So write the registers of an output where such a pulse does no harm: before the pin is enabled, or between transfers on a line whose receiver is not listening. For an input the select changes right after a clock edge, a whole clock before the next sample.
  • An edge that goes through a line set to tap k comes k taps late in both directions; a pulse keeps its width. A pulse shorter than one tap (about a nanosecond) may not pass a chain.
  • A delay is given in taps. In nanoseconds it is tap x 20 / cal (next section), which a firmware or the host works out from dlyr.cal.
  • The delay of a line that is on with tap 0 is the tap multiplexer's, three mux4_1 (0.2 to 1.0 ns by the liberty, corner and input dependent), not 0.

Calibration

A delay cell's delay changes by a factor of 2.2 between the fast and the slow corner (table below), so a tap number alone says little. The calibration circuit measures the taps against the clock:

  • A chain of 46 taps of its own. Once in 64 clocks a flip-flop toggles into it; at the next clock edge all 46 taps are sampled. A tap the edge has passed shows the new level, the others the old one.
  • cal is the number of taps before the first one that differs from tap 1: the taps one edge passes in one clock, less the share of the flip-flop's clock-to-output and setup times. If no tap differs (the edge left the chain within a clock, or did not reach tap 1), cal is 46.
  • The samples go through two flip-flop stages before they are counted, since the tap the edge is passing at the clock edge can be metastable. cal and the "in range" flag are registers written once per measurement.
  • cal is in range from 12 to 45. Outside, dlyr.cal has bit 7 clear. Out of range a line is bypassed, whatever its register holds, once its input has been still for three clocks; back in range it delays again under the same condition. This is the rule the firmware keeps for its writes (Rules for a firmware), so the bypass multiplexer switches between equal levels. It has two limits. A line whose input changes at least every two clocks is never still and keeps its tap while cal is out of range, for as long as its input keeps changing. And the rule looks back two clock edges only, so a line longer than about three clocks (a tap of more than about 3 x cal taps) can still hold an edge at the switch, and the switch can cut that pulse. An output line watches its output and enable bits (the line of P0 also those of P1 while fine USB edges are on). An input line compares the two flip-flops in_m and in_s that follow its pin: a pin change in the clock before the switch is not seen there, and in_m, the first flip-flop after the asynchronous pin, feeds this check directly (a one-flip-flop synchronizer, the one exception to the two flip-flops of every other input path: a metastable in_m can reach the line select on_q in the same clock; it matters only in a clock in which the line select and the range disagree). A register write that turns a line off, and a soft reset, still bypass one clock later. Before this rule (panel review of 2026-11-14), an RTL simulation with the tap delay forced from 300 to 770 ps showed a 10.8 ns pulse on P0 in 4 of 6 returns into the range (test_dly_cal_switch_no_runt, tap 40, so a line of about 1.5 clocks at 770 ps); none since in that test. A line longer than three clocks is not covered by it. The rule costs 24 flip-flops. The upper limit is the last count the chain can tell from "no tap differs" (46 taps, so 45). The range holds the liberty's 16.8 (slow) to 37.3 (fast) taps per clock, which the RTL simulation reads as 16 and 37, and the values read with the delays of a layout: 16 in the slow corner, 4 above the lower limit, and 38 or 39 in the fast corner, 6 below the upper limit (SDF gate-level run of H4d). A value outside the range means the chain is broken or the corner is outside what the library describes, and the safe answer is the 20 ns grid the chip has without the lines, which a line reaches once its input pauses for three clocks (above).
  • Why 46 taps and a limit of 45. Until commit 9f0336f a chain had 44 taps and the range ended at 39. In the SDF simulation of the H4d layout, fast corner, dlyr.cal read 38 and 39 in turn (a tap of 502.5 ps on average for a rising edge, 39.8 taps in 20 ns). cal can step by one (last point below), so a chip one tap per clock faster than that corner would have read 40 at times, and every line would have been bypassed. With 44 taps the limit could not go above 43; two more taps put it at 45, where a tap would have to be 20 / 46 = 0.435 ns, 13 % less than the layout's fast corner figure, before the count leaves the range. The 46-tap RTL has one layout, hardening H5 of branch int5f (RTL f5f5660, with the fine USB edges, before the branch int6 changes): no setup or hold violation in the three corners after routing, the gate-level test.py 19 of 19, the Tiny Tapeout precheck passed, and in its SDF runs dlyr.cal read 38 and 39 (fast), 25 and 26 (typical), 15 and 16 (slow), all in range.
  • The first value is there four clocks after reset; a soft reset does not restart the calibration.
  • The measured edge alternates between rising and falling (the flip-flop toggles), so cal can step by one between measurements where the two edges differ; near a tap boundary it can also step by one from jitter. A firmware that needs a steady value reads it a few times.

Simulation model

In RTL simulation a tap is a delay of u_dly.tap_ps picoseconds (assign #), 770 after reset: the typical corner of the plan (the liberty gives 0.769 ns). A test sets the variable to another corner. The tap multiplexers and the bypass multiplexers are the same structure as in the netlist, without delay. So the simulation shows which tap a register value selects, that the three lines of a pin follow the right registers, the calibration count, the bypass rules and the firmware interface; it does not show the delay of the multiplexers, the difference between a rising and a falling edge, the mismatch between two chains, or anything of the layout.

In any other synthesis than the hardening flow (the formal scripts, an FPGA build) a tap is a wire: cal reads 46, out of range, and every line stays bypassed. The hardening flow defines PE_DLY_CELLS (src/config.json) and gets the library cells.

The reference model (tools/peiss) has the eight registers, the write rule of the two cores and a fixed dlyr.cal of 0x99 (in range, 25); it has no delay, so the lockstep tests write the registers with the enable bit 0.

Eye training

The routine the plan describes, as test/test_dly.py runs it inside the test (part D1; SCK on P3, data in on P2 through its input line, register 6). The firmware file that grew out of it is the next section.

cal = dlyr.cal & 0x3F
for tap in 0 .. cal:                 ; one clock of range
    dlyw 6, 0x80 | tap
    errors = 0
    repeat 8: pulse SCK, sample the pin, count a wrong level
    map[tap] = errors                ; data memory 0xA0 + tap, the host reads it with DATA_R
find the longest run of taps with 0 errors
dlyw 6, 0x80 | (last tap of the run - (length - 1) / 2)     ; line off if there is no such tap
report the tap, the run length (the eye width in taps) and cal to the host

It is 72 words. An input line makes the pin look later to the chip, so a larger tap samples an earlier instant of the pin: the routine moves the sampling instant back by up to one clock.

Training firmware

firmware/dly_train.pe (part D3 of the plan, 220 words, hart 0) is the routine above as a firmware of its own, for an input line and for an output line, with a report to the host and a rule for what to do when the calibration value moves afterwards. It runs a small serial link on which the chip is the clock source, so that the training and the transfers that use the trained tap share one bit routine: P3 = SCK, P2 = DIN through its input line (register 6), P1 = DOUT through its output line (register 1).

One byte on the link: DOUT gets the first bit a bit period before the first SCK rise; then per bit (8 ticks, 320 ns) SCK rises, one tick later DOUT gets the next bit, two ticks after the rise the firmware samples DIN, three ticks after it SCK falls. MSB first. In the simulation the chip takes the DIN pin 40 ns after the SCK rise at the pins with the line off (the test measures it).

Commands (bytes from the host FIFO) and what comes back:

Command What the firmware does Bytes to the host
1 trains the input line of DIN the report
2 trains the output line of DOUT with the host's help after each tap 0x80 \| tap, to which the host answers with the number of wrong bytes the receiver saw; then the report
3, n checks the calibration, then transfers n bytes (1 to 255): each byte from the host is sent on DOUT and the byte sampled on DIN goes back one status byte, then (status 0 or 1) n bytes

Training.

line off (after QUIET ticks of rest)
c = dlyr.cal
if bit 7 of c is clear:  report 1, c, 0, 0            ; out of range: the line stays off
cal = c & 0x3F
for tap in 0 .. cal:
    register = 0x80 | tap                             ; written while the link rests
    wrong = 0
    repeat M (4): send the byte PAT (0xA5) and receive a byte
        input line: wrong += 1 if the byte received is not PAT
    output line: send 0x80 | tap to the host, wrong = the host's answer
    MAP[tap] = wrong                                  ; data memory 0xA0 + tap
    keep the longest run of taps with wrong = 0 (the first of equal ones)
if there is such a run:
    register = 0x80 | (last tap of the run - (length - 1) / 2)
    report 0, 0x80 | cal, that tap, the length, MAP[0 .. cal]
else:
    line off
    report 2, 0x80 | cal, 0, 0, MAP[0 .. cal]

The report is code, the dlyr.cal byte, tap, eye width in taps and then the error map, one byte per tap from 0 to cal, except with code 1. The width and cal together give the eye in nanoseconds, width x 20 / cal, whatever the corner. The map and a record per line stay in the data memory for DATA_R: at 0x10 (input line) and 0x18 (output line) the bytes trained, trained tap, cal at the training, cal the present tap was set for, present tap, width.

For the output line the chip cannot see what the receiver took, so the host has to: it reads the receiver's result after the M bytes of each tap and passes the count of wrong bytes. That is the host-assisted training of the plan. The same sweep, map and choice are used.

The choice is the middle of the longest good run that the sweep saw. A run that touches tap 0 or tap cal may go on outside the range of one clock; the firmware then still takes the middle of the part it saw, which is a tap with at least half that run on either side, not the middle of the eye.

When the calibration value moves. A trained tap is a delay in taps; voltage and temperature change what a tap is. Before every transfer (command 3) the firmware reads dlyr.cal and answers with one status byte:

Status Condition What the firmware did
0 cal is less than DRIFT (2) taps from the value the present tap of each trained line was set for, or no line is trained nothing; the bytes move
1 cal is DRIFT or more from that value for a trained line, and less than RELIM (6) from its value at the training that line's register = round(trained tap x cal / cal at the training), written while the link rests; the bytes move
2 cal is RELIM or more from its value at the training of a line nothing is written and no byte moves, at every command 3 until the host trains that line again (or cal comes back)
3 cal is out of range, so the chip has bypassed every line both registers 0, both lines marked not trained, no byte moves; later transfers run bypassed with status 0

The new tap is always worked out from the trained pair, not from the last one, so rounding does not add up over several moves; it keeps tap x 20 / cal, the delay in nanoseconds, to half a tap. DRIFT is 2 because cal can step by one between two measurements with nothing having changed (Calibration); it is the plan's "more than one tap". RELIM is a choice: the proportion only follows the chip's own delay cells, not what the other device or the board did with the same change of temperature, so beyond a quarter of a typical cal the firmware asks for a new measurement instead. Both are .equ values of the file. The plan's other two reasons to train again, a fixed interval and too many receive errors, are left to the host, which sees the data and sends command 1 or 2 when it wants.

The rule for register writes. Every write of a register goes through one routine that first waits QUIET (4) ticks in which the hart changes no pin, with SCK low. The hart's next pin change is the first DOUT bit of the next byte, 8 ticks after the write at the earliest, and the next SCK rise comes a bit period after that. So the firmware's own pins are still for 160 ns before and 320 ns after a write (the rule above asks for three clocks before and one after); the other device must leave DIN alone in that time, that is, hold or release its data well within 160 ns of the last SCK fall. The status 3 path writes both registers 0 after the same wait. The output line's register is written between bytes, when SCK is low and a receiver that samples on SCK edges is not listening.

Deadlines. tools/petime.py firmware/dly_train.pe: PASS, 3 twait reached, all always in time, least margin 2 ticks (63,537 states, registers joined at anchors after 64 states). The tool does not model the instructions on opcode 0xF and steps over dlyr.cal r7 as if it wrote nothing; the verdict still covers every run because nothing else writes r7 before it, so the tool carries r7 as unknown from the start. To get a verdict at all, the two loops whose counts depend on data keep their counters in the data memory (the run lengths of the sweep, the quotient of the proportion), which the tool treats as unknown bytes instead of following every value. test/check_asm_compat.py --rev int5b: the 144 older files assemble to the same 32,624 words; the new file is listed as new.

What it is not. The link format is the firmware's own, made so that one bit routine serves the training and the transfers. A firmware for a real protocol would take the sweep, the choice and the status rule and put its own transfer in the place of the pattern bytes. The pins must be among P0 to P3.

Hardening

One layout with the delay lines closes timing in all three corners (run H4d, at the end of the section). This section is what src/config.json sets, what a hardening run has to show, and what the H4 runs showed.

Keeping the cells. The chains are library cells instantiated by name, so synthesis has nothing to optimize in them. RSZ_DONT_TOUCH_RX marks the delay cells (dlyc0, dlyc1), the tap multiplexers (dlyx), the bypass multiplexers (dlyb) and the nets inside the chains as "don't touch" for every resizer step (design repair, timing repair after placement, clock tree and routing), so no cell is resized, removed as a buffer or split by an inserted buffer, and the output line and the enable line of a pin stay the same cells.

Timing. A line that is on is late on purpose, and the calibration flip-flops sample taps the edge has not reached. Static timing analysis reports both as setup violations. In a flat synthesis of the 44-tap RTL without wires (container Yosys, OpenSTA 2.7.0, clock 20 ns, 4 ns input and output delay, 0.25 ns uncertainty, ideal clock; only the paths of the clock group, since without a buffer tree the reset of this RTL fails recovery in such a run with or without the lines):

Corner int5b worst slack With the lines, no exception With the two exceptions
slow 4.805 ns -49.149 ns, 43 endpoints 4.825 ns, 0 endpoints
typical 5.149 ns -28.582 ns, 33 endpoints 5.156 ns, 0 endpoints
fast 5.357 ns -17.312 ns, 20 endpoints 5.358 ns, 0 endpoints

The endpoints are uio_out[3:0], uio_oe[3:0], the six synchronizer flip-flops of P0 to P3 and the calibration flip-flops of the taps past one clock (29 slow, 19 typical, 6 fast). The two exceptions are at the end of src/pe_dly.sdc: a false path through input A1 of every bypass multiplexer (every path of a line that is on), and one through the calibration chain. The bypassed path stays constrained; it is one mux2_1 longer than before: uio_out[0], the falling-edge output of the USB unit, arrives at 10.853 ns instead of 10.598 ns in the slow run (+0.255 ns).

The flow stops on setup violations at the typical corner, so the delay lines need one of two things:

  • Without a user SDC (what src/config.json set until b620162, 2026-11-16; it now sets the user SDC of the next item, the official flow ran with it, and Tiny Tapeout has not said whether it accepts one): SETUP_VIOLATION_CORNERS with the match-nothing entry turns setup violations into warnings in every corner. Costs: the flow no longer stops on a real setup violation, its setup numbers include the delay line endpoints, and its timing repair works on paths it cannot fix. The real slack is then read from the flow's per-endpoint report with the endpoints above left out, or from an OpenSTA run on the final netlist and parasitics with the two exceptions.
  • With a user SDC: PNR_SDC_FILE and SIGNOFF_SDC_FILE set to src/pe_dly.sdc (the flow's default constraints, unchanged, plus the two exceptions) and SETUP_VIOLATION_CORNERS removed. The checker stays as strict as before and the repair steps do not see the delay line paths. This is the cleaner of the two and the only part that needs an SDC; the don't-touch setting and the cell instantiation do not.

To check in a hardening run:

  1. The lint step passes with PE_DLY_CELLS (without the define it must stop on the simulation model's delays).
  2. The resizer steps log 1,196 + 192 + 12 instances as matched by RSZ_DONT_TOUCH_RX, and the final netlist has 1,196 dlygate4sd3_1 in u_dly (1,144 with the 44-tap RTL of runs H4 to H4d) with the two cells of each tap still in a row (no buffer between two taps, no cell of another size).
  3. With way (a): the list of violating endpoints is the one above and nothing else; the slack of every other endpoint; how long the timing repair steps ran and how many cells they added compared with the last run without the lines. With way (b): no setup violation, and the slack of uio_out[0], uio_out[1], uo_out[6], uo_out[7] against the last run (half-clock outputs, the tightest paths of the design; each of the first two has one more cell).
  4. Hold at the synchronizers of P0 to P3, max slew and max capacitance inside the chains (the cells cannot be resized there), antenna on the chain nets.
  5. Where the placer put the three chains of a pin: the output line and the enable line of one pin should have the same wire lengths tap for tap; their difference is a skew between the two pad bits.
  6. The SDF gate-level run of the plan: dlyr.cal at the three corners (36 or 37 fast, 25 or 26 typical, about 16 slow by the liberty), and the edge of a pin moving by the corner's tap. Run H4d read 38 or 39, 25 or 26 and 16 (below).

Gate-level equivalence of H4d

The same netlist is proved sequentially equivalent to its RTL (formal/run_equiv_gl.sh, 2026-11-14, logs in formal/logs/equiv_gl_20261114/; method and tables in verification.md, section 5 and formal/README.md):

  • Default method: PROVED, 315 s. The RTL's taps are wires and the netlist's delay cells are buffers from the liberty. The calibration value is then 44 on both sides, out of range, so every line stays bypassed: the proof covers the bypassed chip and the line registers (which dlyr reads back) and says nothing about the tap multiplexers or the wiring from the tap registers to them.
  • CUT_DLY=1: PROVED, 335 s. The RTL is read with PE_DLY_CELLS, and the 1,144 delay cells are cut out of both sides like the SRAM macros: their 1,144 input pins are compared and their outputs are 1,144 free inputs shared by the two sides. The calibration value and every tap can then take any value, the lines switch on, and the proof holds for any delay of the chains. The 3,816 hold buffers of the same cell type stay buffers.
  • Control. A copy of the netlist with inputs A1 and A2 of the first tap multiplexer of P0's output line swapped (taps 1 and 2 exchanged) is PROVED by the default method (295 s), which cannot see it, and is NOT EQUIVALENT with CUT_DLY=1 (a trace in frame 83, 615 s).
  • The netlist's u_dly has 572 + 572 delay cells, all 559 tap-to-tap connections without a buffer, 192 mux4_1 and 12 bypass multiplexers, two of which the flow resized to mux2_2.

The proof is about logic, not delay: that a tap delays by the right amount is the SDF run above. It was made for the 44-tap RTL (src/ of bea5db6) and has not been repeated for 46 taps, for which no netlist exists.

Limits, and what only silicon shows

  • The tap is not a constant: 0.54 to 1.19 ns across the corners by the liberty, 0.50 to 1.22 ns with the delays of the H4d layout. cal gives the scale, to one tap.
  • Rising and falling edges take different times through a delay cell (the two ends of each range in the table), so a pulse changes its width slightly in a long chain; tap by tap the two cells of a tap do not cancel it.
  • The output line and the enable line of a pin are separate chains. Their mismatch (local variation, placement) is a skew between the output bit and the enable at the pad; the pad rule keeps the two changes a clock apart, so a skew far below a clock does not make a pulse.
  • The lines of different pins do not match either, and Tiny Tapeout's multiplexer and the pads add their own pin-to-pin differences, which the chip cannot measure.
  • The calibration chain is one more chain: it tells the taps per clock of itself, close to but not the same as each line's.
  • A sample of a tap in transition can be metastable; two flip-flop stages and the "first tap that differs" rule make a wrong cal unlikely and off by one tap, not excluded.
  • Supply noise and temperature move the delay while a line is in use. A firmware that depends on a trained tap reads dlyr.cal again from time to time and follows it or trains again when it has moved (Training firmware). The proportion follows the calibration chain only: how the other device, the board and the pads move with the same temperature is not in it.
  • Writing a register while an edge is in the chain can make a pulse (rule above); nothing in the chip prevents it. Whether the multiplexer cells pulse on a select change between equal inputs is a property of the cells that neither the simulation nor static timing shows.
  • The RTL simulation model has none of these effects. One layout (run H4d, 44 taps) was simulated with its SDF in three corners, which gives the taps of that layout, the rise and fall difference and the layout's share of the mismatch between chains; local variation, supply noise and the multiplexer pulse are not in an SDF. The 46-tap RTL has the layout H5 (branch int5f), whose SDF runs gave the calibration values above; no layout of the branch int6 RTL has passed yet. Silicon has not been seen. The training firmware was run against the RTL model only: its error maps have sharp edges because the model has no jitter but the one the test adds, and on silicon the 4 bytes per tap of the default setting may be too few to see a marginal tap.
