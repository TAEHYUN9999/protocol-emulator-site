File Role Words
firmware/hdlc.pe Bit-synchronous HDLC-like framing (RFC 1662 chapter 5). Hart 0 sends frames from the host with its own clock: flags as time fill, zero insertion, the 16-bit or 32-bit FCS, NRZ or NRZI, and an abort on request. Hart 1 receives on a clock from outside: flag hunt, zero deletion, FCS check, abort, short and misaligned frames; good frames go to two buffers in the data memory, or to the frame buffer (up to 128 octets), and are reported to the host. 506 of 512 (hart 1 starts at word 311)

This protocol was not part of the design when the RTL was written. It uses only existing instructions (low/high, shout.lsb, shin, waitp, tset/twait, the CRC unit, ld/st on the data memory and the frame buffer, host FIFO); the RTL is unchanged. Checked in simulation only, not on a board.

The host chooses the line coding, the FCS and the receive buffer with MODE (data memory 0x0C, written with DATA_W before the run; both harts read it at their start):

MODE bit Meaning
0 NRZI on TXD and RXD (a 0 bit changes the line level, a 1 keeps it), else NRZ
1 the 32-bit FCS (RFC 1662 C.3), else the 16-bit FCS (C.2)
2 long receive: one receive buffer, the frame buffer (128 octets with the FCS); the transmit buffer then moves to the data memory (95 octets)

Section numbers below are those of RFC 1662, PPP in HDLC-like Framing (W. Simpson, July 1994).

The physical layer is left to the DTE/DCE (5.5): the firmware uses the usual synchronous serial convention, data changed after the falling clock edge and sampled at the rising edge, NRZ or NRZI. Not implemented: address and control field checks (3.1 says frames with other values SHOULD be discarded; that is left to the host, which gets every frame with a good FCS), octet-stuffed framing (chapter 4).

32-bit FCS with a 16-bit CRC unit

The CRC unit holds 16 bits, so the 32-bit register R = H:L (C.3, reflected polynomial 0xEDB88320) is updated per octet d in two passes. With idx = L[7:0] ^ d and x = idx & 15 (the shifts kept to 8 bits):

  • Hinj = H[7:0] ^ x<<4 ^ x<<5 ^ x<<6, the bits of H that shift into L during the octet;
  • u = idx ^ H[7:0] ^ x<<4 ^ x<<5, chosen so that the second pass sees the feedback of the 32-bit register;
  • L' = pass(L, 0x8320, d) ^ (Hinj << 8), H' = pass(H, 0xEDB8, u), where pass is the unit's LSB-first CRC of 8 bits with that polynomial.

It follows from the low byte of the polynomial (0x20: the feedback of bit k is idx bit k ^ the feedback of bit k - 6) and from the bits 3 to 5 of 0xEDB8 that reach L within one octet. test_hdlc_model32 checks it against the C.3 table method for 20,000 random steps (and an offline run checked 200,000). One octet takes about 45 ticks (c32t, c32r).

Pins

Constant Default Use
TXC P0 transmit clock, driven by hart 0
TXD P1 transmit data, driven by hart 0
RXC P2 receive clock, from the other end
RXD P3 receive data

All are push-pull. Assembling with RXC = TXC and RXD = TXD (assemble(text, {"RXC": 0, "RXD": 1})) makes one chip receive its own frames; only hart 0 drives the pins and hart 1 leaves its own pin registers released, so the wired AND of the two harts' registers is hart 0's drive.

Timing

HALF is half a bit in ticks: 25 by default, 2 us per bit, 500 kbit/s. Every half bit is one twait period: TXC changes one tick after each period boundary and TXD one tick after the falling edge of TXC, so the clock halves are exactly HALF ticks and the data is stable for HALF - 1 ticks before the rising edge and HALF + 1 after it. The FCS is computed while the octets come from the host, during the time fill, and stored with the frame's pointer and count in three low halves of the flags that follow; the frame then needs no CRC work at all. The longest paths between two boundaries: 22 ticks for NRZ (preparing the frame start), 23 for NRZI (the first data bit after the opening flag), so HALF must be at least 23 (543 kbit/s) for NRZ and 24 (521 kbit/s) for NRZI; it was 21 before the FCS moved to the time fill. With the 32-bit FCS the half periods in which an octet arrives (about 45 more ticks for the two CRC passes) and the one storing the FCS are longer; this happens only in the time fill, between frames; inside a frame every half is HALF ticks.

The receiver has no timer: it waits for the rising edge of RXC (waitp RXC,0 then waitp RXC,1, in a subroutine rdb that also undoes NRZI), samples RXD in the next tick and does the bit's work before the next rising edge. The longest work is after the bit that ends a flag (counter, report, buffer switch, CRC reset) and, with the 32-bit FCS, after the last bit of an octet (the two CRC passes, about 50 ticks). Measured with back-to-back frames and one flag between them, 50 % duty cycle: every frame right up to 769 kbit/s with NRZ (wrong at 800), 625 kbit/s with NRZI (wrong at 714), 312 kbit/s with the 32-bit FCS (wrong at 357), 278 kbit/s with NRZI and the 32-bit FCS (wrong at 312). Before the modes the receiver took 909 kbit/s with NRZ; the bit read became a subroutine with the NRZ/NRZI choice, and the end of a frame handles the two FCS sizes and buffer kinds.

Transmitter (hart 0)

Host to chip (FIFO): n, then n & 0x7F data octets.

n Meaning
1 to 127 send a frame of n octets with its FCS
0x81 to 0xFF send n & 0x7F octets, then an abort (eight 1 bits, not stuffed) instead of the FCS and closing flag
0, 0x80 ignored

The octets are taken into the frame buffer (0x21 to 0x9F, n at 0x20; in long receive mode the data memory, 0xA1 to 0xFF, n at 0xA0, so n & 0x7F is at most 95 there) while flags go out, one octet at most per bit, so the line timing never waits for the host and the clock never stops. Each octet goes into the FCS as it arrives. Once all are in, three low halves of the following flags store the FCS as it will be sent (0x08 to 0x0B), set up the pointer, the count and the abort, and give the CRC registers their start values for the next frame; the frame starts after the flag in which the third step was done. A longer n than the buffer takes: its octets are read and dropped, nothing is sent. The frame counter TFRM (0x15) and the abort counter TABT (0x16) count what was sent; the transmitter answers nothing on the FIFO, which belongs to the receiver. The frame buffer is shared with the Ethernet blocks and the capture, which must stay idle while the transmitter runs (a store is dropped while they own it).

The transmitter does not refuse frames of fewer than 2 octets: a 1-octet frame has 3 octets with its FCS, and any receiver discards it (5.3).

Receiver (hart 1)

Each good frame (FCS right, at least 2 data octets, a whole number of octets, at most the buffer: 48 octets with the FCS, or 128 in long receive mode) is left in a buffer, and one byte is pushed to the host FIFO. Two buffers in the data memory (MODE bit 2 clear): bits 5..0 the number of data octets (2 to 46, or 44 with the 32-bit FCS), bit 6 the buffer (0: 0xA0, 1: 0xD0); the buffers alternate after each good frame, so the host has until the end of the next good frame to read one with DATA_R. Long receive: the report is the number of data octets (2 to 126, or 124 with the 32-bit FCS), the frame is in the frame buffer, read with CAP_R (frame byte 2k is the high byte of word k), and the next frame overwrites it, so the host must read it before the next frame starts. If the FIFO is full, the report is dropped and ROVR counts it.

Address Use
0xA0 to 0xCF buffer A, 48 octets (the frame and its FCS)
0xD0 to 0xFF buffer B
0x10 RGOOD good frames
0x11 RFCS frames with a wrong FCS
0x12 RABT aborts: seven 1 bits after at least one octet of a frame
0x13 RINV frames shorter than the FCS plus 2 octets, not a whole number of octets, or longer than the buffer
0x14 ROVR reports lost because the FIFO was full
0x15, 0x16 TFRM, TABT of the transmitter
0x00 to 0x0B 32-bit FCS registers of the receiver and the transmitter, the FCS octets to send
0x0C MODE
0x0D to 0x0F, 0x17 to 0x1F the firmware's own (buffer base, FCS length, frame start step, largest n, saved registers)

On six 1 bits the receiver judges the frame at once (octet alignment, length, FCS) and the next bit decides: 0 completes a flag and the judgement counts, 1 makes seven ones, an abort. A frame ending on an octet boundary leaves two bits of the current octet to go when the sixth 1 arrives (the flag's 0 and its first five 1 bits went in as data); any other count is a misaligned frame. Ones with no octet received (mark idle, or the receiver hunting) are not counted as aborts. After an abort the receiver hunts for the next flag.

Tests

test/test_hdlc.py (cocotb). The model is written from RFC 1662: the FCS table generators and computations of Appendix C (16-bit C.2, 32-bit C.3), an encoder (LSB first, zero insertion, flags), NRZI as the Zilog SCC/ESCC manual defines it, and a decoder that hunts flags bit by bit, deletes inserted zeros, finds aborts, and discards short frames, misaligned frames and empty frames as 3.1 and 5.3 say. Only the host interface (command, report byte, data memory addresses, assembler constants) is taken from this page. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T COCOTB_TESTCASE=<test> make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_hdlc

Limits

  • Frame sizes: to send, 127 octets (95 in long receive mode); to receive, 46 data octets in each of two buffers (44 with the 32-bit FCS), or in long receive mode 126 (124) in the frame buffer; a longer received frame is counted in RINV. The buffers take the upper data memory and the frame buffer, so Ethernet and the capture cannot run with this firmware, and the program takes 506 of the 512 words.
  • The receiver reports a frame by one FIFO byte; with two buffers the host must read one before the next good frame but one has ended, in long receive mode before the next frame starts.
  • Speed: sending 500 kbit/s by default, at most 543 kbit/s (NRZ) or 521 kbit/s (NRZI), lower than the 595 kbit/s before the modes; receiving up to 769 kbit/s (NRZ), 625 kbit/s (NRZI), 312 kbit/s (32-bit FCS), 278 kbit/s (NRZI and 32-bit FCS), against 909 kbit/s before the modes. RFC 1662 recommends 56 kbit/s to 2 Mbit/s for NRZ (5.5); the upper part of that range is out of reach.
  • With the 32-bit FCS the time fill is not regular (a longer half period for each octet taken from the host), and the receiver is slower (the CRC passes after each octet).
  • No address or control field checks, no octet-stuffed (asynchronous) framing. NRZI follows the SCC convention; the other one (a 1 changes the level) is not offered.
  • An abort with no octet received yet (fewer than 8 bits after the opening flag) is not counted, because it looks like mark idle.
  • Simulation only: no board, no gate-level run.
