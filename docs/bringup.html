What to run in the first hour after the chip comes back: a host library for the demo board's RP2040/RP2350 (MicroPython with the Tiny Tapeout SDK, the ttboard module) and a script that checks the chip step by step and prints PASS or FAIL with a diagnosis for each step.

Not run on hardware. There is no chip yet and no demo board was used. The library and the script are checked against the RTL in simulation and against a Python model (How it was checked); the board-side file pins_ttboard.py was written from the SDK's README and source and has never run on a board (SDK calls). What the first session on a real board still has to settle is in Not checked.

The package is called pehost, not ttboard, so that copying it to the board does not hide the SDK's own ttboard module. The library uses no typing, no dataclasses and no third-party module, so that MicroPython can run it; it was run on CPython 3.10 only.

On the board

  1. Put the demo board's input DIP switches off. In ASIC_RP_CONTROL mode the SDK leaves a ui pin as an input when it reads high at that moment (ttboard/pins/pins.py, begin_asiconboard), and the RP2 then cannot drive it. Step board reads the pins back and names any that do not follow.
  2. Copy host/pehost/ and host/main_bringup.py to the board's file system (for example mpremote cp -r host/pehost : && mpremote cp host/main_bringup.py :; pins_mock.py is not needed there).
  3. In the REPL:
>>> import main_bringup
>>> main_bringup.run()

run() selects the project in the mux (tt.shuttle.tt_um_taehyun9999_protocol_emulator.enable()), puts the board in ASIC_RP_CONTROL mode and runs the sequence twice: with a 10 MHz project clock, then with the design's 50 MHz. Every check counts in project clocks (bit times, capture dt, SCK periods), so both runs must give the same lines; a step that passes at 10 MHz and fails at 50 MHz points at the board's wiring or the clock, not at the logic. run(clocks=(1000000,)) runs at another clock, run(steps=("id", "progmem")) only some steps, main_bringup.chip() returns a Chip for the REPL.

No jumper is needed. The protocol firmware is assembled so that the chip reads its own pins: uart.pe with RX on the TX pin (RX = 0), spi_master.pe with MISO on the MOSI pin (MISO = 1), and for I2C the controller on hart 0 and the target on hart 1 on the same two pins (dual_role.md). The RP2 only reads the protocol pins, except in step uio_in, where it drives all eight while the chip has released them.

The I2C step is the one that needs a pull-up. The SDK configures every RP2 pin with a pull-down (gpio_map default_pull), so a released line reads low; the step asks for the RP2's pull-ups on uio[0] and uio[1] and runs the bus slowly (SCL low and high 250 ticks each, 10 us at 50 MHz), because those pull-ups are tens of kOhm. For Fast-mode timing put 2.2 to 4.7 kOhm on the two lines.

uart firmware/uart.pe: six bytes out of hart 0 on P0 come back through hart 1; then the capture records one frame and the host decodes it: 0xA3, every edge on the 100-clock bit grid; late flags 0 FIFO, CAP_*, STATUS The pad does not read its own output, or bit timing
spi firmware/spi_master.pe: three bytes come back; the capture of one byte (deep, 512 entries: the wait for the host's data byte writes a filler every 256 clocks) shows CS low around 8 SCK rises 40 clocks apart; late flags 0 FIFO, CAP_*, STATUS As above
i2c i2c_master_gen.pe on hart 0 and i2c_target_gen.pe on hart 1 on P0, P1: a write of four registers (checked in the data memory), a read back after a repeated START, and an address nobody answers DATA_W, DATA_R, FIFO No pull-ups on P0, P1 (the hint says whether the pin layer could switch them on), or the wired AND of the two harts

The memory steps use only what the chip has. Both cores' program memories are tested in full and core 1 is loaded, run and read through its own commands (progmem, core1); the data memory, the FIFOs and the other steps cover core 0 only (core 1's data memory and FIFOs are not tested by a step of their own), and the shared SRAM is tested only through the data memory and the frame buffer. There is no built-in self test and no way for the host to write the deep capture memory, so capmem fills it through the capture itself: each of its 512 words gets a pins byte that takes two different values in the two passes, and a dt byte that is 5 in both (the dt bits are therefore not all toggled).

The board has no assembler: tools/peasm.py needs re.fullmatch and argparse, which MicroPython does not have. Assemble on a PC and load the words, as host/build_images.py does for the bring-up images:

words, labels = assemble(open("firmware/uart.pe").read())      # on the PC, tools/peasm.py
c.load(words, hart1=labels.get("hart1", 0), harts=3)           # on the board
# a program for core 1 whose second hart starts at a label hart3 (peasm prints hart3=)
c.load(words1, hart1=labels1.get("hart3", 0), harts=RUN_HART2 | RUN_HART3, core=1)

Two things a host must know

test/test_host_bringup.py test_host_interface_notes shows both on the RTL.

  • Read MISO before SCK rises. The chip loads the next byte into its shift register a few clocks after the 8th SCK rise of a byte (byte_valid, load in src/pe_host_spi.v), not at the following SCK fall. A host that raises SCK and then reads MISO, which is a common way to bit-bang mode 0 and is far slower than 80 ns on MicroPython, gets the first bit of the next byte in place of the last bit of each byte: a program memory holding 0x0080 in every word reads as 0x0180. Chip.xfer() reads MISO before it raises SCK, as test/test.py does. A hardware SPI master that samples at the rising edge is not affected.
  • PROG_W and PROG_R work only while both harts are stopped. With a hart running, a PROG_W is dropped (since RTL revision 0x01 a sticky flag, STATUS byte 6 bit 4, Status.wdrop, says that a PROG_W or DATA_W was dropped since the last soft reset; the RTL of 422ec10 gave no sign), and a PROG_R does not return the program: the core owns the memory port, and with hart 0 waiting in the rxb at word 0 a PROG_R of three words read that word three times (b000 b000 b000). The command tables say this for DATA_W only. Chip.load() stops both harts first, and Bringup reads every image back before it runs it.

MISO timing margin (test/test_miso_margin.py)

The chip shifts MISO on the falling edge of SCK as it sees it: SCK goes through two flip-flops (sck_s in src/pe_host_spi.v), the fall is taken when sck_s[2:1] is 10, and tx_sr shifts at the next clock. A mode 0 host samples MISO at its next rising edge, half an SCK period after the fall, so the time left between the change and that edge must cover what the RTL does not have: the input path of SCK, the output path of MISO and the host's set-up. test_miso_margin is its own SPI host with edges in picoseconds. For each SCK it reads 12 pattern bytes with DATA_R at every phase of SCK against the clock (0 to 19 ns, 1 ns steps) and takes each MISO bit as the pin's level D before the rising edge; the margin is the largest D (1 ns steps) at which every phase reads right [measured, RTL, Icarus 11, 50 MHz]:

SCK Half period SCK fall to MISO change at the pins Margin D
clk/8 (6.25 MHz) 80 ns 40 to 59 ns 20 ns
clk/6 (8.33 MHz) 60 ns 40 to 59 ns 0 ns
clk/5 (10 MHz) 50 ns 40 to 59 ns none: wrong with D = 0 (0x55 read as 0x2A)

The change comes 2 to 3 clocks after the fall, depending on where the fall lands in the clock period (280 shifts over the 20 phases at each speed). Tiny Tapeout estimates about 10 ns round trip through the pads and mux and says it is not measured (Jane Street blog, competition FAQ, fetched 2026-11-14) [estimate]. With that, clk/8 leaves about 10 ns for the host's set-up and for any delay of the board between the chip and the host; clk/6 and faster leave nothing. On the ZCU104 FPGA build (full configuration with MBIST, bit 03fd016a, by the board session; log in fpga/zcu104_demo/logs/spi_speed of the L4d worktree, commit 79578a6, not on a branch of this tree yet) the demo host samples MISO in the clock that raises SCK, a half period after the fall with no pad delay to speak of: per speed 200 reads of the chip ID and 200 writes and read-backs of 32 random data memory bytes. clk/16 and clk/8 made no error (ID 0 of 200, bytes 0 of 6,400); at clk/6 and clk/4 the ID was wrong 200 of 200 times and 6,342 and 6,340 of the 6,400 bytes, as the 0 ns margin of clk/6 above predicts [measured, board]. The documented maximum stays clk/8, and a host with a hardware SPI should start lower and raise SCK while the id step still reads the ID. Shifting MISO right after the rising edge the chip sees instead (DEEP_TECH R2) would give about one SCK period minus 60 ns, enough for clk/5; that is an RTL change and not made.

Pin layer

Chip and Bringup reach the chip only through these methods of pehost/pins.py:

Method Meaning
clock(hz) Start the project clock, or stop it with 0
reset(active) rst_n low or high
ui(value) Drive ui_in[7:0]; returns after at least 5 project clocks, so SCK never exceeds clk/10
uo() Read uo_out[7:0]
uio() Read the eight protocol lines
uio_drive(oe, value) Host drive of the protocol lines (0 releases)
pullups(mask) Pull-ups on the protocol lines in mask; returns False if the layer cannot provide them
wait(clocks) Let at least that many project clocks pass

A layer that is wired to only some of the chip's pins says which in UI_MASK, UO_MASK and UIO_MASK (all 0xFF unless the layer sets them). Bringup then checks the wired lines only: gpio compares the wired gpi and gpo bits, uio_out leaves out the host's own read of lines it cannot read, and each lists what it left out in a skip: line under its result; uio_in is reported as SKIP when no protocol line is wired. PartialPins around any layer takes wires away, for the tests.

Four layers implement it: TTPins (the demo board), STM32Pins (a NUCLEO-G474RE wired to the FPGA build), MockPins (a Python model: the host SPI commands, the reference model tools/peiss as the core, and the capture without trigger at prescale 0) and CocotbPins (the RTL simulation). TracePins around any of them records the sequence, and replay() applies a recorded sequence to another layer.

Running the host library on a NUCLEO-G474RE against the FPGA build

Before there is a chip, the same library can drive the chip's RTL on a ZCU104 from a NUCLEO-G474RE running MicroPython: the Nucleo takes the place of the demo board's RP2040, the FPGA the place of the chip.

Not run on hardware. The pin layer, the entry script and the bitstream were prepared before the boards were wired. Nothing in this section was run on a Nucleo or on the ZCU104, and no MicroPython interpreter was used: pins_stm32.py was run on CPython against a stand-in for machine.Pin, the FPGA top in simulation with its Xilinx primitives replaced, and the bitstream was built and met timing but was not loaded (how this part was checked).

Wiring

The FPGA build fpga/zcu104/zcu104_pe_ext_top.v has the chip's host pins on J55 (PMOD0) and P0 to P7 on J87 (PMOD1), all LVCMOS33 in bank 87. Both boards are 3.3 V; connect ground, not 3.3 V.

The project clock is the FPGA's 50 MHz (from the board's 300 MHz); the Nucleo makes no clock. In the FPGA, SCK, CS_N, MOSI and gpi0 go to the chip's pins as they arrive, because the chip synchronizes them itself (src/pe_host_spi.v, src/project.v). RST_N is synchronized, and the chip's reset changes only after four equal samples (80 ns), so that a glitch picked up from the neighbouring wire does not reset the chip. The pulls hold the link idle and the chip out of reset while the Nucleo is not connected. The VIO has one output, 1 to hold the chip in reset (0 after configuration), and shows uo[7:0], the host pins, P0 to P7 and a count of CS_N falls; the ILA has P0 to P7 (in, out, enable), the host pins and uo[7:0]. Neither is needed to run the sequence.

Lines that have no wire, and what the library does about them:

Line In the FPGA Pin layer Bring-up
gpi1 to gpi4, ui[7:4] tied low UI_MASK = 0x0F; set_gpi() bits 1 to 4 go nowhere gpio checks gpi0 only and prints skip: gpi 1,2,3,4 (ui[3+n]) not wired
gpo1 to gpo5, uo[7:3] not on a connector (VIO and ILA only) UO_MASK = 0x07; uo() reads 0 in those bits gpio checks gpo0 only and prints skip: gpo 1,2,3,4,5 (uo[2+n]) not wired
P0 to P7 without the eight optional wires on J87 with pull-ups UIO_MASK = 0; uio() reads 0, uio_drive() and pullups() do nothing (pullups() returns False) uio_out passes on the chip's own read-back and prints skip: the host's own read of P0,...,P7 (not wired); uio_in is SKIP. capture, capmem, uart, spi and i2c run in full: the chip reads its own pins, and i2c uses the FPGA's pull-ups

clock() changes no pin; it returns False and prints once that the clock comes from the FPGA. Step board drives MOSI and gpi0 both ways with CS_N high and reads the five host outputs back at the Nucleo's own pins, which shows an output wire that sits on an FPGA output or is shorted; it cannot show an open wire.

A stuck line is found only where there is a wire: with nine wires the sequence says nothing about ui[7:4], uo[7:3] and the host's view of P0 to P7.

On the Nucleo

  1. MicroPython for the board: NUCLEO_G474RE on micropython.org/download (v1.29.0 of 2026-08-24 was the latest when this was written, as .hex and .dfu). That page gives st-flash --format ihex write firmware.hex and STM32CubeProgrammer as the ways to write it through the on-board ST-LINK.
  2. The REPL is on the ST-LINK's virtual COM port (LPUART1, 115200 baud). On the PC: pip install mpremote, then mpremote connect list to find the port.
  3. Copy the library (seven files, about 70 kB; the board's file system is 160 kB). pins_ttboard.py and pins_mock.py are not needed, and cp -r host/pehost would also copy the PC's __pycache__:
cd host
mpremote connect /dev/ttyACM0 mkdir :pehost
mpremote connect /dev/ttyACM0 cp pehost/__init__.py pehost/pins.py pehost/chip.py pehost/images.py pehost/bringup.py pehost/pins_stm32.py :pehost/
mpremote connect /dev/ttyACM0 cp main_stm32.py :main_stm32.py

Without copying, mpremote connect /dev/ttyACM0 mount host serves the folder to the board for one session. 4. Load the bitstream (zcu104_pe_ext.bit of fpga/zcu104/build_ext.tcl) into the ZCU104, wire the boards with both powered off, ground first. 5. In the REPL (mpremote connect /dev/ttyACM0 repl, Ctrl-] to leave):

>>> import main_stm32
>>> main_stm32.run()             # nine wires

If id fails with all 00: the bitstream is not loaded, the VIO holds the reset, or SCK/CS_N/MOSI/MISO are on the wrong J55 pins (odd pins 1, 3, 5, 7 are one row, even pins the other). The VIO's count of CS_N falls tells whether the Nucleo's wires reach the FPGA at all.
