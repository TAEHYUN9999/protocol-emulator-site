File Role Words
firmware/peci.pe Hart 0 is a PECI originator: any message from the host (address, write length, read length, write bytes), timing negotiation bits, bit times exact to the clock, the AW FCS added for an Assured Write, the client's Write FCS checked (good, no client, Abort FCS, wrong), read bytes and Read FCS. Hart 1 is a PECI client: measures tBIT from the negotiation bits, answers Ping, GetDIB, GetTemp, RdPkgConfig and WrPkgConfig (with the AW FCS check), drives the Write FCS, the read bytes and the Read FCS, and the Abort FCS for anything it does not take. The two pins sit on one PECI wire, so the two harts are a loopback. 387 of 512 (hart 0 148, hart 1 239)

No RTL change: existing instructions only (twait grid, high/rel, shin, waitp/waitp.to/waitp.frz, tgeth/tgetl to time the negotiation bits, the CRC unit as CRC-8, ld/st with a register address, host FIFO). Checked in simulation only, not on a board.

Sources

The PECI specification is not public (Linux Documentation/peci/peci.rst: "part of External Design Specification ... usually not publicly available"). Everything below comes from public documents that describe it; the bit order inside a byte and the value of the message timing bit were not found in any of them.

Pins

Pin Use
P0 (PO) originator, drives high or lets go
P1 (PC) client, drives high or lets go

Both pins go on the one PECI wire with a pull-down (on a real bus a level shifter to VTT). Since neither pin ever drives low, two harts can share the wire; on one pin they could not, because a rel by one hart would also drop the other's high (docs/jtag_tap.md, "Two harts on one chip"). The bench ties P0 and P1 into one wire for the loopback test.

Timing

Originator: data memory 0x00 holds tBIT/4 in ticks (0 = 50: tBIT 8 us, 125 kbit/s). Before each message it keeps the wire low for 2 tBIT. A 0 is high for one period, a 1 for three, a bit is four; the firmware raises and lowers the wire on that grid, exact to the clock (high pulses of 100 and 300 clocks at the default before the pad rule). Since branch int3 (revisions) a push-pull high from release is enabled one clock after the instruction (dual_role.md); the wire idles low, so it shows it: every high pulse is one clock shorter, 99 and 299 clocks (0.2475 and 0.7475 tBIT; Table 3-1: 0.2 to 0.4 and 0.6 to 0.8), and the bit period, rise to rise, stays 400 clocks. For client bits it is high for one period, lets go, and reads at the start of the third period. The longest code between two twait is the AW FCS step (22 ticks), so the quarter bit must be at least 24 ticks (tBIT 3.84 us, 260 kbit/s); the late flag shows when it is not.

Client: tBIT is the time from the rising edge of the first negotiation bit to that of the second, read with waitp.frz and tgeth/tgetl. It reads each bit at tBIT/2 after the rising edge; for a 1 it drives the line 8 to 9 clocks after the edge (7 to 8 before the pad rule; the wire is already high from the originator's pulse then) and lets go at 5/8 tBIT after it (about 0.65 tBIT of high time with the latency). Between the last write bit and the Write FCS it has half a bit for its decision, which sets the shortest tBIT it follows: 3 us works, 2 us does not. A message ends when the wire has no rising edge for 2 tBIT; the next negotiation bit is taken after that.

Parameter Value

Host interface

Originator (hart 0): host to chip address, WL, RL, write bytes; bit 7 of WL asks for an Assured Write, the chip then computes the last write byte (the AW FCS) and the host sends WL - 1 bytes. Chip to host: status, RL bytes. Status 0 good, 1 Write FCS all 0 (no client), 2 Abort FCS, 3 another wrong Write FCS (no read bits are sent after 1 to 3), 4 wrong Read FCS (the bytes are still given). Data memory 0x01 and 0x02: the Write FCS and Read FCS as received.

Command Host bytes Answer
Ping() 30 00 00 status
GetDIB() 30 01 08 F7 status, 8 bytes
GetTemp() 30 01 02 01 status, temperature LSB, MSB
RdPkgConfig() 30 05 05 A1 hostid index param_lo param_hi status, completion code, 4 bytes
WrPkgConfig() 30 8A 01 A5 hostid index param_lo param_hi d0 d1 d2 d3 status, completion code

Client (hart 1), data memory:

Address Use
0x03 client address (0 = 30h)
0x04, 0x05 GetTemp value, LSB first (host DATA_W, or two host bytes LSB, MSB while it waits for a message)
0x06-0x0D GetDIB bytes
0x0E messages answered
0x0F Abort FCS sent
0x1F package config writes
0xC0-0xD3 four package config dwords (index 0 to 3), each after its completion code 40h: 0xC1, 0xC6, 0xCB, 0xD0

RdPkgConfig and WrPkgConfig of another index answer completion code 90h. The four dwords are a store for the test, not Intel's index meanings.

Tests

test/test_peci.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_peci

The models are written from the sources above, not from the firmware: CRC-8 and the AW FCS, a client answer function (commands, lengths, completion codes, Abort FCS), a wire that ORs the two chip pins and the model (and records every chip drive, failing on a low drive), an originator model with any tBIT and high times, and a client model that measures tBIT, decodes at half a bit, waits for the 2 tBIT stop, and drives its 1s from 2 % to 70 % of tBIT. Only the pins, host bytes and data memory addresses come from the firmware header.

Limits

  • The bit order inside a byte (MSB first) and the value of the message timing bit (0) are choices; no public source states them. The Abort FCS as a complement is an SST rule carried over.
  • The client measures tBIT once per message from the address negotiation bits and does not stretch the negotiation pulse (a slow client may do so); the message timing bit is read as a data bit and not timed.
  • Client commands: Ping, GetDIB, GetTemp, RdPkgConfig and WrPkgConfig of four dwords; no PCI config, MSR or mailbox commands, no retry bit handling, no completion codes other than 40h and 90h.
  • The originator stops after a wrong Write FCS and does not retry; it does not check the client's high times.
  • tBIT: originator 3.84 us and up, client 3 us and up (the specification allows 0.495 us).
  • Simulation only: no board, no gate-level run.
