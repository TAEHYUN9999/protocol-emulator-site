The claim

A protocol chip with a predictive edge launcher: in a device's place it learns the clock of an unmodified vendor host and puts its reply edge at a chosen offset from the predicted clock edge, before or after it, in steps of one clock (20 ns). That is enough to find both ends of the host's sampling window.

A protocol emulator usually imitates a part: it answers like an EEPROM, a sensor or a debug target. This chip also uses the part's place to learn about the host. It learns the host's clock, moves its own reply edges in whole clocks, and so finds where an unmodified host stops accepting a reply; between those edges it can place its replies. Who does what in the evidence: on the boards the chip supplies the learned clock and the moving edge, a script on the bench PC chooses the offset of each step (it writes N to five input pins of the chip, fpga/board/skew_sweep.tcl), and pass or fail is the data the Linux host read. The host is vendor IP in a second FPGA (Xilinx AXI Quad SPI and AXI IIC), not a separate silicon part. The pass range of the launcher sweep was compared with a simulation result committed before that run. The chip stepping the offset and judging each step by itself, with no script in the loop, is the margin scan; it is shown in simulation only, with the chip as I2C controller and the author's model as the target.

How each page supports that sentence, one line each:

  • architecture.md, Predictive launcher: the mechanism. The launcher learns the period of a pin and changes a reply pin at the predicted edge plus a signed offset in clocks.
  • verification.md section 9 and section 8: the window of an unmodified vendor host. Xilinx AXI Quad SPI and AXI IIC under Linux, in the second FPGA board and in co-simulation with the unmodified vendor RTL (the Pin and Protocol rows below).
  • margin.md: the chip runs a whole scan by itself, in simulation. As I2C controller it steps its own SDA edge, runs a transfer at each step and writes an eye and a shmoo of the target model's window into the data memory.
  • can_dist.md: the same idea on a CAN bus, in simulation. It finds the sample point of another node, a model in the test bench whose sample point the test sets and the firmware is not given, by lengthening a dominant pulse on one bit of that node's frame.
  • inject.md: replies put outside the window on purpose. A host table places a chosen error at a chosen byte and bit, so the other side's handling is tested at a known place.
  • spec_tables.md: what "inside the window" means. One timing table per protocol and speed, with the clause of its source for each rule, generates the three judges that decide pass or fail.

Where the novelty is, and where it is not

Each part has prior art; the next section lists it. What is claimed here is narrower: an open chip that stands in a device's place against an unmodified third-party host (vendor IP under Linux), moves its own reply edges to find that host's window, and checks the result against the vendor RTL in co-simulation and against the board. Finding a timing margin by a sweep is not new, in this competition either: the table "The measuring idea" below lists four entries that do it in their own ways. Three things narrow what is claimed here. The side: a device's place, against a vendor host that was not modified. The means: a launcher that predicts the host's clock edge, so a reply can also be put before that edge, which firmware that reacts to the edge cannot do (on the board the SPI device without the launcher did not reach the early end of the window). The procedure: the pass range was a simulation result committed before the board run. On the boards a script outside the chip chose each offset; the chip closing that loop by itself is shown in simulation only. The barrel of two harts, the drift-free period timer and the proof that hart 1 cannot change hart 0 are the base this is built on; other entries to the competition have similar bases, so they are not claimed as new.

Time-predictable processors

The research line this chip's barrel and period timer come from. The late flag in particular has a precedent here, so the claim for it is narrowed below.

Prior work Same Different Our evidence
PRET, Edwards and Lee, DAC 2007 (paper) A machine that puts repeatable timing before speed and has no interrupts that break it PRET left precise I/O open; this chip is a small application of the idea to protocol pins architecture.md (Timing)
PTARM, Liu, thesis 2012 (EECS-2012-113) A thread-interleaved pipeline with timing instructions: "delay until", the counterpart of twait, and "exception on expire", the counterpart of the late flag An expired deadline there raises an exception that changes the program flow. Here a missed period changes nothing in the hart's flow: twait returns at once and a sticky flag is set that the host reads later in STATUS architecture.md (Timing); test/test.py
FlexPRET, Zimmer, thesis 2015 (EECS-2015-181) Hardware threads with timing instructions, among them an exception on expire "for run-time detection of unexpected timing violations"; its fixed round-robin configuration (Base-4T-RR) is the same design point as this chip's barrel with a fixed share per hart FlexPRET's exception changes the program flow, and it also has flexible schedules this chip does not. Its path analysis tool is proposed, not built; this chip has a static deadline checker, tools/petime.py, which gives a guarantee only where it says PASS (below) architecture.md (Timing), petime.md

So the late flag is not claimed as a new idea. What is left is a narrow combination: a sticky flag that does not change the program's flow and that the host reads later, on a barrel with a fixed share per hart, in an RTL with a proof that hart 1 cannot change hart 0 (verification.md C1).

What the four leave to this chip

Judging another device's timing on the chip, standing inline between two chips, and driving at the ends of a timing window are all done by other entries, and three of them have proofs this chip lacks. What is claimed here is narrower: in a device's place, a launcher that predicts the host's next clock edge puts the reply edge on either side of it, so both ends of an unmodified host's receive window are found from the device side. A relay or a reactive device can only add delay and reaches the late end; on the board, the device without the launcher did not reach the early end.

What this leaves

Not claimed as new, because the rows above already have it: the barrel of harts with a fixed share, waits with a timeout and drift-free period waits, a flag for a missed deadline as such (PTARM, FlexPRET), an on-chip judge of bus timing (Referee has one with a soundness proof), a static check that firmware is not late (other entries have stronger ones), line units under firmware for Manchester and NRZI links, a capture block beside the protocol engine, measuring another node's sample point by moving edges, and finding a timing margin by a sweep (four entries to this competition do it, each from another side).

Not claimed as new either: the four blocks the RTL gained last (revisions.md). Each has a precedent, and what this chip adds to each is a narrow combination:

Block Precedent What this chip combines
SRAM self test, March C- and March SS through the macros' BIST ports (mbist.md) Memory BIST is standard practice; another entry to this competition (TSE) has one The host starts it per macro over the same SPI link and reads the first failing address and bits, so a bad macro can be found on silicon before a protocol runs
Debug unit: breakpoints, single steps, injected instructions (debug.md) PIO SMx_INSTR, single stepping on the PRU and the Propeller 2; breakpoints in other entries Per hart, through the host SPI link, so that the reference model tools/peiss can follow a chip one instruction at a time from what a host on a board reads
Fractional tick generator per hart and twait.f (tickgen.md) PIO SMx_CLKDIV with its 8-bit fraction; fractional-N dividers One generator per hart, with a mean error of zero against the target rate, and the generator running in step with the hart's own clocks
Pin writes one clock later (.h), toggle on the period end (twait.t), waits on pin patterns and events (waitm, waite, evs, evc) (isa3.md) PIO's side-set delay and WAIT on pins and IRQ flags Edges on every clock (20 ns) for a hart that runs every second clock, with no change to the words of existing firmware

None of the four is used yet by a protocol firmware of the repository.
