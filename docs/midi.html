MIDI needs no new firmware: firmware/uart_gen.pe (docs/uart.md) runs it with these settings, written with DATA_W before the run:

Address Setting Value
0x00, 0x01 bit time 0x03, 0x20: 800 ticks = 32.000 us, 31,250 baud exactly at 50 MHz
0x02 data bits 8
0x03 parity 0 (none)
0x04 stop bits 1
0x05 autobaud 0

Hart 0 sends every byte the host writes to the FIFO on P0 (MIDI OUT through the usual current-loop driver), hart 1 receives P1 (MIDI IN, after the opto-isolator) and gives the host every byte (0xFF, System Reset, as 0xFF 0xFF, see docs/uart.md). Start both harts (CTRL = 3). 213 words; no RTL or firmware change.

Source

MIDI 1.0 Specification (International MIDI Association, 1983), text as posted to comp.music on 24 September 1990:

Item Specification
Serial format 31.25 (+/- 1 %) Kbaud, asynchronous, a start bit, 8 data bits (D0 to D7), a stop bit: 10 bits, 320 us per byte
Status and data bytes Table I: 8n Note Off 2 data bytes, 9n Note On 2 (velocity 0 = Note Off), An poly key pressure 2, Bn control change 2, Cn program change 1, Dn channel pressure 1, En pitch bend 2; system common F1 1, F2 2, F3 1, F6 0; F0 ... F7 system exclusive; Table V: F8 to FF real time, status only
Running status the receiver stays in a status until another status byte comes, so the status byte of the next message with the same status may be left out; any other status byte stops it, except real-time messages, which may come at any time, even between the bytes of another message, after which the receiver resumes under the previous status

Running status

The chip passes bytes: running status, real-time interleaving and system exclusive are message-level rules, kept by whoever builds or reads the messages. In this setup that is the host. parse() in test/test_midi.py is a reference receiver written from the rules above (a status buffer, real-time bytes taken out without touching it, system common and exclusive clearing it, data bytes without a status ignored), and every stream in the tests goes through it; encode() leaves out repeated status bytes the way a sender may.

The firmware's own handling matters in one place: a running-status stream has no idle time and no status byte to resynchronize on, so the receiver must take back-to-back bytes and the transmitter must send them back to back. uart_gen.pe does both (its start bit follows the previous stop bit directly when the next byte is waiting).

Tests

test/test_midi.py (cocotb). The line model is the serial format above; the message model is parse() and encode(). Only the settings and the report format of uart_gen.pe come from the firmware side. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T COCOTB_TESTCASE=<test> make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_midi

Limits

  • The chip does not interpret MIDI: no running status, note or clock handling in firmware; the host does it (above).
  • One MIDI IN and one MIDI OUT; no THRU (a third pin copying IN would need the transmitter hart).
  • The bit time is exact at a 50 MHz clock; with another clock the 1 % tolerance of the specification applies to the clock.
  • Simulation only: no board, no current-loop interface, no opto-isolator.
