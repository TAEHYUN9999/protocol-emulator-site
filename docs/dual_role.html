Each hart drives the protocol pins P0 to P7 through its own output and enable registers, and a pin is the wired AND of the two harts' drives. One chip therefore behaves like two devices on one open-drain bus: hart 0 can be an I2C controller and hart 1 an I2C target on the same SCL and SDA, with clock stretching, and one hart can put a fault on a line the other hart is using. Before this change the two harts shared one output/enable register pair and the later write won, so a hart releasing a line also released the other hart's drive.

Pin drive

For every pin, each hart is in one of three states: release (enable 0), drive low, drive high (push-pull). The pad:

Hart 0 Hart 1 Pad enable uio_oe Pad output uio_out Line with a pull-up
release release 0 0 high (pull-up)
low any 1 0 low
any low 1 0 low
high release or high 1 1 high
release or high high 1 1 high

So whichever hart drives low wins, as on a wired-AND bus (NXP UM10204 3.1.1). low, high, rel, shout[.od], wrp and woe change only the registers of the hart that runs them. Reading is unchanged: rdp, shin, waitp and the capture block see the pads after the two-flip-flop synchronizer, so both harts read the bus as it is, including what the other hart drives. test/test_dual_role.py test_wired_and_truth_table drives P2 from both harts in all nine combinations (and in both orders) and checks the pad, uio_oe and rdp.

uio_out and uio_oe are flip-flops. They are loaded from the next values of the four hart registers (src/pe_core.v, drive_low, drive_high) in the same clock as those registers, so a pin changes at the same clock edge as with the single register pair before; no firmware timing moved. The one exception: a push-pull high from release enables the pad one clock later (Pad timing), which a pulled-up line does not show and a line that idles low (a pull-down) shows as a rising edge one clock later. A combinational AND of the hart registers was tried first and rejected:

  • uio_out = (out0 | ~oe0) & (out1 | ~oe1) (also with uio_oe & in front) makes the output bit go from 1 to 0 when a hart starts pulling low (enable 0 to 1, output 0), in the same clock as the enable rises: the pad can drive high for a moment. The RTL simulation showed it as a zero-time SDA pulse, which the UM10204 bus monitor of the I2C test decoded as an extra START and STOP.
  • uio_out = drive_high & ~drive_low straight from the hart registers keeps the output bit at 0 for open drain, but a push-pull high from release (output and enable rising together) showed a zero-time low pulse, because the enable reaches the pad through fewer gates than the output.

With the registers, the pad pins come straight from flip-flops, as they did before. A hart that only pulls low and releases (open drain) keeps its output bit at 0, so uio_out stays 0 and only uio_oe changes, exactly as with one register.

Other drivers of the protocol pins and their priority:

Source Effect on the pins
Firmware of hart N (low, high, rel, shout, wrp, woe) Hart N's own output/enable registers
Predictive launcher fire (plaunch) One output bit of the hart that armed it (pe_pel keeps the arming hart with the pin and value). In the clock it fires, it wins over that hart's own write to the same bit, as before. The enable is left to the program
Soft reset Clears both harts' registers: all pins released
Host SPI Never drives uio
Ethernet Drives uo[6], uo[7] only, never uio

gpo (uo[2:7]) stays one shared register, and the launcher's reference pin (pelsel) is shared by both harts.

Since branch int5 there are four harts (two per core, architecture.md); a pin is the wired AND of all four, formed by core 0's pad registers from the drives of both cores, and everything on this page holds for four harts as for two (test/test_core1.py test_four_harts_wired_and, formal/run_formal_por.sh PAD claims). Since part D1 of that branch the output bit and the enable of P0 to P3 each pass a delay line between the pad registers and the pad (dly.md); both lines of a pin take the same tap, so the two bits keep the distance the pad registers gave them (test/test_dly.py test_dly_output_taps), and after reset the lines are bypassed.

Pad timing

A pad has two inputs, the output bit and the enable bit, and three useful states: released (enable 0), driven low (1, 0), driven high (1, 1). On a line with a pull-up a released pad reads high. A move that changes both bits at one clock edge is a race between two paths: if the pad sees the bits one after the other, it passes through one of the two mixed states for the difference of the two path delays.

What the int2 netlist showed. The gate-level run of test/test.py on the hardened int2 netlist (revisions) failed in test_uart_full_duplex only: the first frame on TX (P0) was [0, 0], a falling and a rising edge at the same time. The firmware's first instruction, high TX, moves P0 from released (0, 0) to high (1, 1). In the int2 RTL P0 and P1 pass one fixed-select mux of the top level (usb_mode ? usb : core, src/project.v), and synthesis built it differently for the two bits:

Port Cells after the flip-flop (int2 netlist 7a2a5ce1, the same in a plain Yosys synthesis of the int2 RTL) Gate primitives in the cell models
uio_oe[0] sg13cmos5l_mux2_1 (A0 = core_pin_oe[0], A1 = u_usb.oe, S = usb_mode) 1 (the mux UDP)
uio_out[0] sg13cmos5l_nor2_1 (core_pin_out[0], usb_mode) into B1 of sg13cmos5l_a21oi_1 (A1 = usb_mode, A2 = D+ = XOR of the USB unit's rising and falling flip-flops) 4 (or, not, or, not)

Both flip-flops hang on clock leaves five buffers deep, so they change in the same simulation step; the enable then reaches the port three evaluation steps before the output. A monitor on the bus of test/tb.v shows it at 135.400 us: oe0=1 out0=0 bus0=0, then out0=1 bus0=1.

The USB select is one way to get there, not the only one. In the int1 netlist (88a6c192) both P0 flip-flops drive the ports directly and the test passes. The deep-capture netlist (cap2_gds, fcbeeb95) has no USB select, but the hardening flow put a hold delay cell and two buffers (dlygate4sd3_1, buf_2, buf_2) between the output flip-flop and uio_out[0], while uio_oe[0] comes straight from its flip-flop: with the current test/test.py it fails in the same way ([0, 0], the same monitor trace). Its own gate-level run passed only because its test.py did not yet record the TX edges. So an RTL whose ports come "straight from flip-flops" does not decide it either; hold fixing and buffering are added by the flow. On silicon the same move would be a race between the two paths through the Tiny Tapeout mux to the pad, and the pad would drive low for as long as the enable leads, which nothing here bounds.

The rule. The pad registers (pin_out, pin_oe in src/pe_core.v) follow the wired AND of the hart registers, but no pad changes both bits at one edge where the state in between would be low:

Move Before At the edge One clock later
release -> high (0, 0) (0, 1): output first, still released (1, 1)
high -> release (also by a soft reset) (1, 1) (0, 1): enable first, released at once (0, 0)
release <-> low, low <-> high one bit
from (0, 1) to low (0, 1) (1, 0): both bits

The state (0, 1) lasts exactly one clock. The last row is the only edge with two bits; it comes only within one clock after a staged move (another hart or a launch pulls the pin low in the very next clock). Its two states in between are (1, 1), drive high, and (0, 0), released: both are high on a released pulled-up line, so the line goes from high to low once whatever the order.

Why the pad shows no pulse, in a netlist simulation and on silicon. In every other move one bit changes and the other is steady. One changing input whose other inputs are steady makes each gate on its path change at most once, as long as the input does not reach the port by two paths: here each pad bit reaches its port through one path (the select or a buffer chain in the netlist, then the Tiny Tapeout mux). The pad cell is a tristate output, pad = c2p_en ? c2p : z in the PDK model (sg13cmos5l_IOPadInOut*): with one of its two inputs steady it goes from the old state to the new one without passing the third. So the result does not depend on how synthesis builds the USB select, on cells the hardening flow adds to one path, on the clock skew between the two flip-flops or on the routing to the pad, only on the RTL rule above. What remains on silicon is the pad's own slew from one level to the other.

What it costs. A push-pull high (or shout of a 1) from release enables the pad one clock (20 ns) later than before. The line is high before and after on a pulled-up line, so the line, the edge timing and every read-back are unchanged; a difference shows only if an external device holds the line low at that moment (the chip then drives against it one clock later) or on a line without a pull-up, which floats one clock longer. A release is as early as before. All edges of low, rel, shout.od, shout between two driven levels, wrp on driven pins and launches keep their clocks.

Lines that idle low. On a line that a pull-down holds low while it is released, the late enable is the rising edge itself: a high pulse that starts from release is one clock shorter, and the low before it one clock longer; the falling edge (a release, or low from high) keeps its clock. Three firmware drive such a line, and their tests time those pulses to the clock. Every pulse stays inside its protocol's limit:

The tests check each pulse against the limit and, to the clock, against the firmware's grid with the rule's clock (test_j1850_tx, test_peci_originator, test_peci_originator_rfcs, test_rffe_master, test_rffe_master_fast). A firmware that moves one of those edges by one tick fails them although the pulse stays inside the limit, and so does the RTL without the first half of the rule. Timing alone cannot give the old width back: a high one tick earlier makes the pulse one clock longer instead (a tick is two clocks), and wrp before woe does not help, since the pads take the output bit of a hart only while it enables the pin. Driving the line low for a tick before the high would (release to low and low to high are one-bit moves), but on a wired-OR active-high bus such as J1850 or PECI that drives against another node, so no firmware does it.

Where it shows. The edge log of test/edge_log.v has the pads and the bench's drive of every pin at every clock, so each staged rise (a pad from (0, 0) to (0, 1) for one clock, then (1, 1)) can be found and checked for whether the bench held the line low during that clock. On the int3 RTL the log of 53 test modules (every module whose firmware raises a pin from release while it runs or writes wrp/woe, the ten modules of the firmware merged last, the modules whose bench holds a released line low, test/test.py, test_dual_role and test_uart) has 7,932 staged rises; 1,608 of them were on a line held low, all in four modules: test_j1850, test_peci and test_rffe above, and test_cjtag, where a keeper holds TMSC at its last level. That test does not time the rise; its speed sweep, which is reported and not required, reads IDCODE right at 500 kHz and, unlike before the rule, wrong at 833 kHz (cjtag.md). In every other module no staged clock found the line held low. The two-bit edge (0, 1) -> (1, 0) came only in test_dual_role, which makes it on purpose (8 times), never on a line held low; on such a line its state (1, 1) would be a high pulse. (The audit script and the logs are outside the repository.)

USB. While ETH_CFG bit 4 is set the USB line unit drives P0 and P1 (its own pins change on both clock edges and are glitch-free by construction, docs/usb_fs.md); the rule above applies to the hart registers behind the select and to P2 to P7. Switching ETH_CFG bit 4 while a hart drives P0 or P1 changes the select under a driven pin; switch it with both pins released.

Checks.

  • test/test_dual_role.py test_pad_one_bit_per_edge: both harts drive their own and shared pins (P0 to P7, P0 and P1 behind the USB select) through every move, the program is started twice one clock apart so that one run has hart 0's high 6 one clock before hart 1's low 6 (the two-bit row), and a soft reset meets two pins driven high and one low. At every rising edge after the outputs settle no pad may change both bits except (0, 1) -> (1, 0), and no bus line may have two edges at the same time. RTL: 265 staged ups, 321 staged downs, 8 two-bit moves, 806 one-bit moves, no error.
  • Gate level, netlists synthesized with Yosys 0.55 and the IHP typical library (no hardening), run in the tt-local-check container: the int3 netlist passes this test and all 19 tests of test/test.py; the netlist of the int2 RTL and the netlist of int3 without the rule fail test_uart_full_duplex with the same [0, 0] frame and this test with zero-width pulses on P0 (50) and P1 (62), the two pins behind the select. The RTL copy without the rule fails this test with two-bit moves.
  • test/controls.sh w12_up_both, w12_down_both: either half of the rule removed fails the test.
  • Lines that idle low: test_j1850_tx, test_peci_originator, test_peci_originator_rfcs, test_rffe_master and test_rffe_master_fast check the rule's clock on a rise from release to the clock, and the protocol's limit. They pass at RTL and on the Yosys netlist of the int3 RTL (27b260e5); on the RTL without the first half of the rule and on the netlist without the rule (0ae41ca6) each of the five fails with the int2 values (64.00 us, 100 / 300 and 48 / 144 clocks, an SSC of 100 and 52 clocks).
  • Reference model: tools/peiss keeps the pad registers with the same rule and the lockstep test compares them at every edge (test/iss_mutants.py pad_up_both must fail).
  • Power-on and stop proof (formal/run_formal_por.sh, PAD): at every edge no pad changes both bits except (0, 1) -> (1, 0), a driven pad shows the wired AND exactly, the staged state lasts one clock and then shows the wired AND; two planted bugs (each half of the rule removed) are caught.

Demonstration 1: I2C controller and target on the same two pins

Hart 0 runs firmware/i2c_master_gen.pe, hart 1 firmware/i2c_target_gen.pe, both unchanged, in one image:

text = open("firmware/i2c_master_gen.pe").read() + "\nhart1:\n" + open("firmware/i2c_target_gen.pe").read()
words, labels = assemble(text, {"SCL": 0, "SDA": 1, "S_ADDR": 0x10, "S_GC": 0x11, "S_STR": 0x12,
                                "S_STEP": 0x13, "S_TSU": 0x14, "S_PTR": 0x15, "S_AW": 0x16, "REG": 0xA0})

402 words, hart 1 starts at word 254. The .equ overrides move the target's settings to data bytes 0x10 to 0x16 and its sixteen registers to 0xA0 to 0xAF (the target reaches them through a register), out of the controller's bytes 0x00 to 0x0F. The only clashing label (start) was renamed in the target firmware (got_s); its binary did not change.

Host side (docs/i2c.md has both firmwares' settings and commands): write the controller's T_LOW/T_HIGH at 0x00 to 0x05, the target's address, stretching flag and TSU at 0x10 to 0x14, preset the registers at 0xA0, then run both harts (CTRL = 3) and send controller commands to the FIFO. Nothing outside the chip drives SCL or SDA; the bench only pulls released lines up.

test/test_dual_role.py, judged by the bus monitor of test/test_i2c.py (written from UM10204 Rev. 7.0, not from the RTL: START, repeated START, STOP, address and data bytes with ACK/NACK, Table 11 minimum times) and by the length of every SCL LOW phase:

Demonstration 2: a fault on the line the other hart uses

firmware/glitch.pe (hart 0) waits for the Nth falling edge of a trigger pin, waits D ticks, pulls a victim pin low for W ticks, releases it and halts. N, D and W are data bytes 0x08 to 0x0C; byte 0x0D turns 1 when the pulse is over. Hart 1 runs firmware/i2c_target_gen.pe at its defaults (address 0x42) on P0 = SCL, P1 = SDA, and the bench plays the I2C controller with the UM10204 controller model of test/test_i2c.py (Standard-mode, LOW and HIGH 5 us). The injector triggers on SCL and pulls SDA low from 3 us after the chosen SCL fall for 9 us, across the sampling rise and into the next LOW phase.

Test Fault What the counterpart sees

The pulse starts 180 ns plus D ticks after the SCL fall in both tests (two synchronizer clocks, the instructions between waitp and low, and the output register), so the fault lands on a chosen bit at a chosen time.

Checks

  • Weakened RTL copies (test/controls.sh, each made in a temporary folder): one shared register pair (the old behavior), hart 1's enable left out of the pad enable, "high wins" instead of "low wins", and the launcher writing the other hart's register. Each makes its test fail.
  • Hart isolation proof (formal/run_formal_iso.sh): hart 0's output and enable registers are now part of the claim, so hart 1 provably cannot change hart 0's drive. Before, the pin registers were shared and left out of the proof. Two planted bugs couple the pin registers of the harts and are caught.
  • Launcher proof (formal/run_formal_pel.sh): a fire carries the hart that armed it; a planted bug that drops it is caught.
  • Power-on and stop proof (formal/run_formal_por.sh): before START all four pin registers and the pads are 0; a hart that may not act keeps its own pin registers (but for a launch it armed); with neither hart acting the pad enable keeps its value and the pad output changes at most at the pin of a launch.
  • Reference model in lockstep (test/test_iss_diff.py, docs/iss.md): the model keeps each hart's pin registers and forms the pads as the wired AND; random programs on both harts drive the same pins in all nine pairs of (release, low, high) and the RTL agrees with the model at every clock edge. The controls "high wins" and "hart 1 starts from hart 0's enables" make it fail.

Compatibility

Every firmware in firmware/ and every program the tests and the FPGA self test assemble was checked for pins written by both harts (whole-port wrp/woe included). Programs run on one hart behave exactly as before. Two two-hart programs write the same pin, and neither relied on one hart's write releasing the other's drive:

  • The SWD host and SWD target in one image (FPGA self test section 15, test/test_mem512.py) share SWDIO and take turns: each side releases SWDIO (rel) at the turnaround before the other drives it.
  • firmware/lin.pe runs the LIN master (hart 0) and slave (hart 1) on the one wire P0. Only one node sends at a time and every write is a one-bit low, rel or shout.od. With the wired AND a hart's rel can no longer release a dominant level the other hart is driving, which is how a LIN bus behaves.

firmware/ps2_loop.pe puts the PS/2 host and keyboard on separate pins. test_mem512, test_lin and test_ps2 pass unchanged on the per-hart pin registers.

Firmware added later and read again on branch int3 for the same question (does one hart rely on releasing a drive the other hart made, or on clearing the other hart's output bits?):

  • firmware/eeprom93.pe (Microwire EEPROM): hart 0 drives DO with the read data and hart 1 shows the status and lets go of DO at each CS fall. On the per-hart registers hart 1's rel no longer releases hart 0's read data, and hart 0 could not wait for the next CLK rise and for CS low at once, so TCZ at the end of a read was 1000 to 1390 ns (data sheet 200 ns). Fixed with waitp2 (docs/architecture.md): hart 0's waits for CLK also end on CS low, TCZ 140 to 160 ns (eeprom93.md).
  • firmware/mdio.pe (STA on hart 0, PHY on hart 1, both on MDIO): no change needed. Each hart releases only what it drove: the STA lets go of MDIO at the falling MDC edge that starts the first turnaround bit of a read (and after the last bit of a write), the PHY starts driving one MDC rise later and lets go at the rising edge after the last data bit, at least HALF ticks (5 at 2.5 MHz) before the STA can drive the next frame. The two drives never overlap, so the wired AND changes nothing.
  • firmware/mil1553.pe (bus controller on hart 0, remote terminal on hart 1): no change needed. Each hart enables only its own transmit pair with low, and wrp now writes only the running hart's output bits: hart 0's 0s for P4/P5 land in bits it never enables. The other hart's transmit lines read 0 while one sends because every transmission ends with wrp of 0 (txend); the comment and docs/mil1553.md said instead that the sender cleared them, which was true only of the shared register, and were corrected (the binary is unchanged).

Limits

  • The wired AND is inside the chip. A hart that drives high with high or a push-pull shout still drives the pad high against an external device pulling low, as before; open-drain protocols use low/rel and shout.od.
  • The two harts still share the launcher, gpo, the FIFOs and the data memory.
