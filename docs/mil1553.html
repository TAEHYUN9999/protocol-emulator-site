File Role Words
firmware/mil1553.pe Hart 0 is a bus controller: it sends a command word and its data words from the host, waits for the status word (no-response time-out), receives the data words of a transmit command, checks the status address and the word count, and reports the status word, the response time it measured and the data. Hart 1 is a remote terminal: it receives commands for its address or broadcast, stores and returns data words, answers with a status word about 6 us after the end of the message, keeps the message error and broadcast-received bits and answers mode code 2 (transmit status word). Both work word by word at 1 Mbit/s Manchester II. 437 of 512 (BC 142, RT 120, shared 175)

No RTL change: existing instructions only (wrp for the two transmit lines at once, the twait grid, waitp.to.frz and tgetl for the sync, shin, the CRC unit as a parity generator). Checked in simulation only.

Pins

Constant Default Use
BTXP, BTXN P0, P1 BC transmitter: P0 high = drive positive, P1 high = negative, both low = off
RP, RN P2, P3 the receiver outputs of the bus (both harts listen here): P2 high = bus positive, P3 = negative, both low = idle
RTXP, RTXN P4, P5 RT transmitter

A transmitting hart writes the whole port (wrp) so that both of its lines change in the same clock; the other hart's transmit lines read 0 (off) meanwhile, which is right because the bus is half duplex. Since each hart has its own pin registers (docs/dual_role.md), wrp changes only the running hart's own output bits: hart 0's wrp writes 0 into its bits for P4/P5, which it never enables, and leaves hart 1's alone. The other hart's lines read 0 because it ends every transmission with wrp of 0 (txend), not because the sender clears them, so the program needs no change for the per-hart registers. A test bench or a real bus must feed P2/P3 from the bus (the model in the test ORs the chip's two transmitters and its own terminal).

Timing

A bit is 25 ticks (1 us). Half a bit, 12.5 ticks, is sent as 12 then 13 ticks, and the sync as 37 then 38 ticks, so every zero crossing is 20 ns from its ideal place at most (the standard allows 25 ns). The first-half and second-half levels of each bit are written by wrp exactly 12 ticks apart; the level of the next bit is computed in the fixed 11 instructions between them, and the byte and parity refills in the second half. Words of a message follow each other with no gap (txmsg).

The receiver (rxw, shared by both harts) waits for the mid-sync crossing with waitp.to.frz, checks the second half of the sync, then samples the first half of each bit 0.74 us after the previous mid-bit crossing and restarts its timer at that bit's own mid-bit crossing. 0.74 us after a crossing is the middle of the window that +-150 ns crossings leave (0.65 to 0.85 us). A bit without its crossing, with both lines or neither line high, a bad sync or even parity makes the word invalid.

Bus controller (hart 0)

Host to chip (FIFO): command word (high byte first), then the data words the BC sends: word count words for a receive command (T/R = 0, word count 0 = 32), one word for a mode code from 16 on with T/R = 0. The BC waits at least 4 us of idle bus, sends the command and its data words back to back and waits for the status sync to start within 12.6 us of its last mid-bit crossing.

Chip to host: code, status word (2 bytes), response time in ticks of 40 ns (2 bytes), then for code 0 the data words received (2 bytes each).

Code Meaning
0 status word and the right number of data words
1 no response
2 invalid response word (sync, Manchester, parity)
3 status word of another address
4 wrong number of data words, or a command/status sync instead of a data word
5 broadcast, the bus stayed idle
6 broadcast, something answered

Remote terminal (hart 1)

RTADR (data memory 11, read at start) is the address; 31 is broadcast. Received data words go to the buffer at 0xA0 (32 words, high byte first) whatever the subaddress, and transmit commands send words from the same buffer, so a receive then a transmit to any subaddress is a wrap-around. Rules:

  • An invalid command word is counted (RWERR) and the terminal waits for 2.6 us of idle bus.
  • A receive message with an invalid data word, too few or too many words, or followed by a command sync sets the message error bit and gets no answer (RMERR).
  • A valid receive or transmit command clears the message error and broadcast-received bits and is answered with the status word (and the data words). A valid broadcast receive message sets broadcast-received and gets no answer; a broadcast transmit command is a message error.
  • Mode code 2 (transmit status word) answers with the kept bits. Other mode codes are answered with a status word (one data word from the buffer, or one received, for codes from 16 on); they have no other effect.

Counters: RCMD (18) valid commands, RRSP (19) status words sent, RWERR (20), RMERR (21).

Tests

test/test_mil1553.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_mil1553

The model is written from MIL-STD-1553B, not from the firmware: an encoder of words into half-bit levels, a decoder that samples a recorded transmission in the middle of every ideal half bit, a timing check of every zero crossing against 4.5.2.1.1.2, a model RT that answers at a chosen response time, and a model BC that sends with chosen crossing displacements and bit rate and times the answer. A bus model feeds P2/P3 with the model terminal OR the chip's transmitters.

test_1553_rt_mode_codes was added on 2026-11-13 with a change of nwds. The static deadline check (petime.md) had found that a mode command through subaddress 31 with a mode code from 16 on ran 50 instructions between tset RTDLY and the twait before the answer, one more than the 49 that fit in the 50 ticks: the answer was still in the allowed range (6.08 us where the same command now takes 6.04 us) but hart 1's late flag was set, and no test sent such a command. The new test sends 12 mode commands (subaddress 0 and 31, both directions, mode codes 1, 15, 16, 17 and 31) and reads the late flag after each: on the firmware as it was it failed at the first of them through subaddress 31 with a code from 16 on (command 2ff0 (SA 31, T/R 1, mode code 16): late flags (0, 1)). nwds now takes the same number of instructions for every mode code (addi, ldi, rlc in place of a branch), which makes the longest path 48 instructions, and the checker passes both harts.

Limits

  • Word level only: no RT-to-RT transfers (a command sync right after a command is a message error), no superseding commands, no dynamic bus control, no busy, service request, subsystem or terminal flags, no illegal-command table.
  • One data buffer of 32 words for every subaddress; mode codes other than 2 do nothing beyond the status word.
  • The RT answers after about 6 us; the decision work after the end of a message takes up to 48 instructions and 49 fit in the 50 ticks of RTDLY (tools/petime.py gives a margin of 1 for that twait), so the response cannot be made shorter than about 6 us without a faster decision path.
  • The BC needs the host to deliver all data words of a receive command before it sends anything, and the host must read the reports; the FIFO is 4 bytes.
  • Logic level only: the transceiver, the coupling transformers and the stubs are outside. Transceiver delays (up to 500 ns in the HI-1573) add to the response time seen on the bus.
  • Simulation only: no board, no gate-level run.
