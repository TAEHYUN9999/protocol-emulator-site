Debug unit: breakpoints, single steps and injected instructions (branch int6)

src/pe_dbg.v lets the host stop a hart at a program address, run one instruction of a hart at a time, and run an instruction of its own on any hart, through the host SPI link that is already there. With it the same reference model that judges the RTL in simulation (tools/peiss) can follow a chip one instruction at a time, using only what a host on a board can read.

With every debug register at its reset value the cores take their run bits unchanged and no instruction is replaced: a host that never sends the two debug commands has the chip as it was.

What it does

Function How
Breakpoint, one per hart A hart whose PC is its breakpoint address does not run while its run bit is set. The instruction at that address has not run. A sticky bit records the stop
Step One tick of the hart: its own clock and the clock after, as if its run bit were set for those two clocks, whatever clock the host's write lands in (a tick generator that runs with the hart moves two clocks per step). A stalled instruction (twait, waitp, rxb on an empty FIFO) takes its tick and stays. A step also runs the instruction at a breakpoint; the hart then goes on if its run bit is set. A step written while the SRAM self test runs waits for its end
Injected instruction A 16-bit word replaces the fetched instruction of the chosen hart's next clock and runs whatever the run bit, a breakpoint or halt say. The PC stays where it is, unless the word is jmp or ljmp. The instruction the hart was about to run is fetched again and runs next
Flags Z and C of the four harts in one byte

There is no extra read port into the register file. The host reads a register by injecting txb rN and taking the byte from the core's output FIFO, and writes one by injecting ldi rN, value. The PCs, the run and halted bits and the late flags are in STATUS and STATUS2 as before.

What an injection costs the hart: one tick. Its timer counts in that tick like in any other, and a txb puts its byte in front of whatever the firmware sends next. The reference model runs the same word the same way, so a lockstep stays exact; a host that inspects a running protocol firmware should stop the hart first.

Host commands

Code Name Bytes
0x50 DBG_W register number (0 to 15), then bytes written with auto increment
0x51 DBG_R register number, then bytes read with auto increment
Register Write Read
0, 1 breakpoint of hart 0: {enable, 0, 0, 0, 0, 0, pc[9:8]}, pc[7:0] the same
2 to 7 the same for harts 1, 2 and 3 the same
8 bit h set: one step of hart h steps not yet taken
9 hart (0 to 3) of the instruction to inject the same
10 its high byte the same
11 its low byte; this write arms the injection bit 0: not yet taken
12 a 1 clears the stop bit of hart h bit h: hart h was held at its breakpoint since the last clear
13 {z3, c3, z2, c2, z1, c1, z0, c0}
14 0xDB

An injection is one transaction, 50 09 hh wh wl. Steps and injections are taken within three clocks, long before the host's next byte, except while the SRAM self test (MBIST) runs: then they wait until it ends. Registers 9, 10 and 11 are one group: a write of register 9 or 10 drops an injection that still waits, so a waiting word never runs on the hart or with the high byte of the next group. A soft reset drops a waiting step or injection and keeps the breakpoints.

How it is built

  • Breakpoint match as a flip-flop. A hart's PC only changes in its own clock, so the comparison of the PC with the breakpoint address is registered in the other hart's clock and is exact when the hart's clock comes. Around a soft reset the flip-flop is loaded from the addresses the reset sets (0 and the START1 or START3 value), so a breakpoint on a hart's first word holds it. The cores take go = (run and not match) or step in place of the run bits; nothing else in the run path changed. A step is one tick of the hart (its own clock and the clock after) at every write phase, but a start by CTRL, a stop by CTRL and the clear of a breakpoint act at the clock the host's byte or the match lands in: go can begin or end in the other hart's clock, so the hart's tick generator can count one clock more or less than whole ticks there (0 or 1 clock of phase per resume; test_int6_cross.test_go_phase_on_resume). The hart itself executes in the same clocks either way. Aligning the run part to the hart's tick (a flip-flop per hart loaded from the run bit the CTRL byte is about to write) was tried for the panel review of 2026-11-14 (R-6) and taken back: the reference model takes CTRL's run bits clock by clock, so test_iss_diff.test_iss_random_tick failed on a stop and restart with a running generator, and the review's rule was to keep the RTL then. A host-level lockstep across a resume with a running generator has to allow the one clock.
  • Injection at the instruction register. The fetched word of a hart is registered one clock before the hart runs it. The injected word goes into that register instead (one multiplexer in front of it, behind the program SRAM's output), together with a flag. In the flagged clock the hart executes, and the PC write is held unless the word is jmp or ljmp. Because the fetch address in that clock is the held PC, the replaced word comes back for the hart's next clock.
  • Size. 79 flip-flops in pe_dbg (four breakpoints, the match and stop bits, the steps and one injection) and one more per core.

Lockstep with the reference model

The host keeps the run bits clear and repeats: step a hart, read the PCs, the halted bits and the flags, read registers by injected txb, and take the firmware's own bytes from the FIFOs. The model gets the same step and the same injected words (Machine.step(inject=...), Chip.step(inject=...) in tools/peiss/machine.py) and must show the same values. A pin that another device drives is read by the chip and can be given to the model as its input, so a firmware can be followed while it talks to real hardware; the test below leaves the pins alone.

Verification

test/test_dbg.py, through the host SPI pins only:

Test What it judges
test_dbg_registers reset values, write and read back with auto increment, a write in the middle, soft reset keeps the breakpoints
test_dbg_breakpoint a hart stands at its breakpoint with the instruction there not run and the stop bit set, the other hart runs on; a step runs the instruction and the hart returns to the breakpoint round its loop, four times; breakpoints on the first words hold both harts after a soft reset; a breakpoint on a word that is never reached and one on the other hart's word stop nothing
test_dbg_step with the run bits clear every step moves one hart's PC along the program (a djnz loop, call, ret, ljmp to word 600, halt), the other hart stays; two steps in one write; a step does not outlive a soft reset
test_dbg_inject a word runs on the chosen hart only, on all four harts, also on a halted one; Z and C per hart; jmp and ljmp move the PC, jnz, call, djnz and ret do not; twelve injections into a running program lose and repeat none of its forty bytes
test_dbg_lockstep random programs of the model's generator on both cores, one random hart stepped at a time: after every step the four PCs, halted bits, Z and C, the bytes for the host and a register of the stepped hart are the model's (all eight registers every tenth step)

Planted bugs (test/controls.sh, entries dbg_*): each must make its test fail.

Not covered: the lockstep on an FPGA or on silicon (the test is RTL simulation), a breakpoint on a PEL launch or on a line unit event (breakpoints are on the PC only), and a trace of executed PCs.

Limits

  • One breakpoint per hart, on the PC. No watchpoint on data or pins.
  • An injected instruction that stalls has no effect beyond its tick: it is not tried again. A load or store that loses the shared SRAM to the host or a line unit at that edge is such a stall; with the harts stopped and no line unit running it does not happen.
  • An injected call writes the link register and does not jump. An injected conditional branch never jumps.
  • The injection register is shared by the four harts: one injection at a time.
