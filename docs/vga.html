File Role Words
firmware/vga.pe VGA output with the VESA DMT 640x480 at 60 Hz timing: HSYNC and VSYNC on hart 0, the picture on hart 1 through the general outputs: 8 colour bars, or 16 rows of 8 cells from the 128-byte frame buffer, 2 bits per colour. 114 of 512 (hart 1 starts at word 26)

Word counts are from tools/peasm.py. This protocol was not part of the design when the RTL was written. It uses only existing instructions (twait grid, wrp/woe for both sync pins at once, waitp on the chip's own sync pins, gpo, ld [r] from the data memory and the frame buffer); the RTL is unchanged. Checked in simulation only, not on a board.

Source

VESA, "VESA and Industry Standards and Guidelines for Computer Display Monitor Timing (DMT)", Version 1.0, Rev. 13, February 8, 2013 (105 pages; public PDF, read from the copy at glenwing.github.io/docs/VESA-DMT-1.13.pdf). The 640x480 at 60 Hz entry is on page 21 (section 4, DMT ID 04h); Table 1-1 (page 7) lists it as an industry standard, and the entry says "For Reference Only - Not a VESA Standard". The entry splits the blanking into borders and porches: the usual "front porch 16, back porch 48" are its right border 8 + front porch 8 and back porch 40 + left border 8, and vertically "front porch 10, back porch 33" are bottom border 8 + front porch 2 and back porch 25 + top border 8.

Lines are counted from their HSYNC leading edge, so the line that holds addressable line n starts 144 px (sync 96 + back porch 40 + left border 8) before that line's picture. VSYNC starts with the HSYNC leading edge of the line that holds line 490 (Ver Sync Start = 490 lines), 144 px before that line's addressable start: of the HSYNC leading edges (section 3.5 asks for coinciding edges) it is the one nearest to 490 lines after the start of addressable line 0. Measured: 777,835 clocks = 15.557 ms after the start of addressable line 0 (Ver Sync Start 15.571 ms; at exactly 25.175 MHz this edge would be at 15.565 ms).

Pins

Pin Use
uio[0] (P0) HSYNC, push-pull, negative (low during the sync)
uio[1] (P1) VSYNC, push-pull, negative
uio[2] to uio[7] not used, left as inputs
uo[7], uo[6] red, bits 1 and 0 (gpo bits 5, 4)
uo[5], uo[4] green, bits 1 and 0 (gpo bits 3, 2)
uo[3], uo[2] blue, bits 1 and 0 (gpo bits 1, 0)

Each colour takes a 2-bit resistor DAC into the monitor's 75 ohm input (outside the chip, not checked here). ETH_CFG bit 0 must stay 0 (its reset value), or uo[6]/uo[7] carry the Ethernet transmitter instead of red. Before hart 0 runs, P0 and P1 are inputs and the colour outputs are 0.

Why the colour is on the general outputs: gpo writes all six colour bits in one instruction and touches no protocol pin. Colour on P2 to P7 would need wrp, which writes P0 and P1 too, so the picture hart would overwrite the sync levels of the other hart, or six high/low instructions per colour change (six ticks, about 6 px).

Host interface and settings

Data memory, written by the host with DATA_W before the run (both harts stopped) and read with DATA_R at any time. Hart 1 reads MODE once at start.

Address Name Use
0x00 MODE 0: colour bars; any other value: the frame buffer
0x01 FRAMES hart 1 counts the frames it drew (mod 256)
0x08 to 0x0F bar colours, left to right; hart 1 writes them at start in mode 0
0x20 to 0x9F frame buffer: row r (addressable lines 30r to 30r + 29, r = 0 to 15), cell c (pixels 80c to 80c + 79, c = 0 to 7) at 0x20 + 8r + c

A colour byte is 00RRGGBB (bits 7 and 6 are ignored). The bars are, left to right, white 0x3F, yellow 0x3C, cyan 0x0F, green 0x0C, magenta 0x33, red 0x30, blue 0x03, black 0x00, each channel at full level.

The host writes the frame buffer with ETH_W (frame byte 2k is the high byte of word k, so cell 0x20 + i is frame byte i), before the run or while the picture runs: hart 1 reads every cell again in every line, so a change shows from the next line drawn. There is no double buffer: a frame drawn while the host writes shows the old cells above and the new ones below. The host FIFO is not used.

Run with CTRL 3 (both harts). CTRL 1 gives the sync with a black picture; hart 1 can be started later (CTRL 3 without a soft reset) and draws from the next frame on.

How it works

Hart 0 runs a twait grid of 794 ticks, one line per twait. Each line writes both sync pins with wrp at its leading edge (HSYNC low, VSYNC as the line type wants), counts 93 ticks with djnz, and writes HSYNC high again: 95 ticks low. A subroutine draws a given number of lines with given levels; the frame is five calls (2 VSYNC lines, 33, 240, 240, 10). Because each line starts at a twait, the line period is exact no matter how long the call and the loop counters take, as long as that stays below 794 ticks; the late flag of hart 0 would show any line that did not.

Hart 1 never writes a protocol pin. It reads HSYNC and VSYNC back through the input synchronizer (waitp on P0 and P1), which delays them by a fixed three clocks, so its picture stays locked to the sync without any drift. It waits for the end of VSYNC, skips 32 more HSYNC leading edges (33 back porch lines in all), then for each of 480 lines waits for the HSYNC leading edge, loads the first cell of the row, and starts a chain of tset/twait that puts each gpo exactly where its cell begins: 136 + 5 ticks after the waitp, then cells of 80, 79, 80, 79, 79, 80, 79 and 80 ticks, and black after the last one. The next cell is loaded during the current one. After 30 lines the row address moves on by 8 (by 0 in the bar mode, where every row is the same 8 bytes). After 480 lines it counts the frame and waits for the next VSYNC.

Hart 0 changes its pins on even clocks and hart 1 on odd clocks (the clocks after the HSYNC leading edge), so the two together place edges on a 20 ns grid. The widths 80/79 were picked to put each cell edge on the odd clock nearest to its DMT position on the grid of a monitor locked to the 794-tick line (pixel = 1588/800 clocks): 0.84 clocks (0.42 px) at most.

Tests

test/test_vga.py (cocotb). The monitor model is written from the DMT entry and sections 3.3 and 3.5 (module docstring), not from the firmware. It records every change of P0, P1 and uo[7:2] with its clock number (changes inside one clock are merged: the simulator can show uo_out changing in several delta steps) and judges whole frames, VSYNC leading edge to VSYNC leading edge:

  • HSYNC: leading edges are the falling ones (negative polarity); every line period within the DMT pixel clock tolerance (+-0.5 % of 800 px at 25.175 MHz); the low time within 1 px of 96 px on the pixel grid of that line (period / 800). One pixel because the chip's tick is 1.007 px: a width can only be a whole number of ticks.
  • VSYNC: low for 2.00 line periods, both edges within 1 px of an HSYNC leading edge (section 3.5); 525 HSYNC periods from one VSYNC leading edge to the next.
  • Picture: line 35 after the VSYNC leading edge (2 + 25 + 8) holds addressable line 0, and pixel x starts 144 + x px after the HSYNC leading edge. The model samples the colour in the middle of all 640 pixels of all 480 lines, and checks every colour edge: one per change of colour between cells, each less than 0.5 px from its cell boundary, with the new cell's colour. Half a pixel is the tolerance because a monitor sampling in the pixel middles then shows every pixel right, and the 40 ns tick (1.007 px) cannot do much better: an edge on the tick grid can be up to 0.5 tick from where it should be. The blanking (all other lines, and outside the 640 px) must be colour 0.
  • After the frames: both late flags clear (STATUS byte 3), FRAMES, and in mode 0 the bar table read back with DATA_R.

Only the firmware's host interface (pins, MODE, FRAMES, bar order, frame buffer layout) is taken from this document. Run from a private directory (FST=-none: no waveform dump):

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build FST=-none COCOTB_TEST_MODULES=test_vga

Limits

  • One timing only, DMT 640x480 at 60 Hz. The line is 794 ticks because the chip's 40 ns tick cannot make the 31.778 us line; 31.760 us (+553 ppm in frequency) is the nearest. The deviation is far inside the DMT pixel clock tolerance of +-0.5 %, but it is a monitor that must lock to it; the test's monitor model is not a real monitor.
  • Picture: 6-bit colour (64 colours) and at most 8 x 16 cells of 80 px x 30 lines. A hart changes the colour at most once per 40 ns tick (about one pixel), and the data memory and frame buffer hold 128 + 128 bytes, so pixel-level pictures are out of reach.
  • No double buffer: a frame drawn while the host writes the frame buffer mixes old and new cells.
  • The frame buffer is the capture memory and the Ethernet buffer: an armed capture, a received or a sent frame change or hide the picture's cells.
  • ETH_CFG bit 0 must stay 0 (red would go to the Ethernet transmitter otherwise).
  • Stopping hart 0 (CTRL) leaves the sync pins where they are. Hart 1 without hart 0 waits for VSYNC and draws nothing.
  • Not implemented: other DMT modes, DDC/EDID (the monitor's I2C bus), power management by sync blanking (DPMS).
  • Not tested: a real monitor, the resistor DACs, gate-level simulation, and the board.
