File Role Words
firmware/dali_gear.pe A DALI control gear: receives forward frames with half-bit timing checks, decodes the IEC 62386-102 address byte (short, group, broadcast, unaddressed) and a subset of the commands (direct arc power, OFF, RECALL MAX/MIN, the send-twice configuration commands, the usual queries), and answers queries with a backward frame after the settling time. Fits next to the pegen transmitter. 455 of 512 (one hart)
firmware/dali_gear_addr.pe Everything of dali_gear.pe, plus the addressing procedure: INITIALISE, RANDOMISE, SEARCHADDR H/M/L, COMPARE, WITHDRAW, PROGRAM, VERIFY and QUERY SHORT ADDRESS, TERMINATE. Runs alone (section "The two extended builds"). 489 of 512 (one hart)
firmware/dali_gear_scene.pe Everything of dali_gear.pe, plus scenes (GO TO SCENE, SET SCENE, REMOVE FROM SCENE, QUERY SCENE LEVEL) and fade time (SET FADE TIME, DAPC and GO TO SCENE fade, QUERY FADE TIME/FADE RATE, status bit 4). Runs alone. 512 of 512 (one hart)

The forward frame transmitter already exists as firmware/gen/dali_tx.pe, generated by tools/pegen.py (docs/pegen.md); the two run together on one chip in test_dali_loopback_pegen (503 words: 455 for the gear and 48 for the transmitter, which the test generates from dali_tx.json for times / 20 on pin P1). The checked-in dali_tx.pe is generated for real time and has 51 words: its gap of 229,174 ticks is longer than one timer period (at most 65,535 ticks), so pegen.py splits it into four periods and three more twait, while the gap for times / 20 (11,459 ticks) is one period. No RTL change: existing instructions only. Checked in simulation only.

Pins

Pin Use
uio[0] (P0) The DALI line at logic level (behind the usual bus interface): idle high, the gear pulls it low to send (open drain), and reads it

Receiver

Te = 10,417 ticks (416.68 us). The firmware measures every time between edges with the frozen timer (waitp.to.frz, restarted 7 ticks after each edge) and accepts only one half bit, 8,333 to 12,500 ticks (333.3 to 500 us), or two, 16,667 to 25,000 ticks (666.7 to 1000 us); the two-half-bit window is the half-bit window doubled (assumed; the sources give only the half bit). The decoding is a state machine over five places in the code (start bit, middle of a 1, middle of a 0, boundary after a 1, boundary after a 0): a run of two half bits from the middle of a bit flips the bit, two single runs repeat it. No edge for 3 Te with the line high ends the frame; with the line low, or any run outside the windows, the frame is dropped (NERR) and the receiver waits for 3 Te of idle line before it listens again, so one bad frame counts once. 16 data bits make a forward frame for control gear; other lengths (8: another gear's backward frame, 24: an IEC 62386-103 frame for control devices) are counted in NOTH and ignored.

Control gear (IEC 62386-102 subset)

Address byte Meaning
0AAAAAAS short address A (0 to 63)
100GGGGS group G (0 to 15)
1111110S broadcast to gear without a short address
1111111S broadcast
101xxxx1, 110xxxx1 special commands; only DTR0 (A3, data) is taken

S = 0: direct arc power with the second byte: FF (MASK) changes nothing, 0 switches off, 1 to 254 is clamped to MIN..MAX (the limit error bit is set when it was clamped). S = 1: a command.

Opcode Command Notes
00 OFF
05, 06 RECALL MAX LEVEL, RECALL MIN LEVEL
20 RESET twice; MAX 254, MIN 1, POWER ON 254, no groups, level 254
2A, 2B, 2D SET MAX LEVEL, SET MIN LEVEL, SET POWER ON LEVEL (DTR0) twice; MAX is kept at least MIN and at most 254, MIN at least 1 and at most MAX; the actual level follows
60+g, 70+g ADD TO GROUP g, REMOVE FROM GROUP g twice
80 SET SHORT ADDRESS (DTR0 = 0AAAAAA1, or FF for none) twice
90 QUERY STATUS bit 2 lamp on, 3 limit error, 5 reset state, 6 missing short address, 7 power failure; bits 0, 1, 4 are 0 (no gear or lamp failure, no fading)
91, 93, 94, 95, 96 QUERY CONTROL GEAR PRESENT, LAMP POWER ON, LIMIT ERROR, RESET STATE, MISSING SHORT ADDRESS FF for yes, no answer for no
98 QUERY CONTENT DTR0
A0 to A3 QUERY ACTUAL LEVEL, MAX LEVEL, MIN LEVEL, POWER ON LEVEL
C0, C1 QUERY GROUPS 0-7, 8-15

Every other opcode is ignored (no answer). A send-twice command is executed only when the same two bytes come again as the very next 16-bit frame and that frame starts at most 82 ms after the first one ended (so it ends within 100 ms); otherwise the second one counts as a new first one.

Backward frame: 18 Te (7.50 ms) after the end of the forward frame's last bit, inside both the 7 to 22 Te of edition 1 and the 5.5 to 10.5 ms of edition 2. The receiver's 3 Te timeout comes first, then the firmware counts out the rest on a Te grid, and every half bit of the answer is exactly Te (20,834 clocks).

Power-on: if MAGIC (data memory 0) is not DA, the settings get their defaults (no short address, no groups, MAX 254, MIN 1, POWER ON 254). The actual level becomes the POWER ON level (clamped), and the power failure bit is set until the first arc power command or RESET.

Data memory

Address Contents

14, 15, 16 NFRM 16-bit frames, NERR frame errors, NOTH frames of other lengths

Tests

test/test_dali.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_dali

The models are written from the sources above, not from the firmware: a bus master that sends forward frames with chosen half-bit lengths and decodes backward frames from the pin (Manchester, settling time, widths in clocks), and GearModel, the 102 subset above, which predicts every answer and the gear's settings after every frame; the test compares the chip's data memory with it after each frame. Two time scales: the firmware as it is (test_dali_realtime), and all time constants divided by 20 (the models use the same scale).

The two extended builds (2026-11-11)

The addressing procedure, scenes and fade time do not fit in 512 words together with the rest of the gear: one source with all of them assembled to 703 words. They are split into two builds that run alone (without the pegen transmitter; dali_gear.pe stays the build that runs with it):

Build Adds Words
dali_gear_addr.pe the addressing procedure 489
dali_gear_scene.pe scenes and fade time 512

Both use the same data memory layout, so a bus can be commissioned with the addressing build and run with the scene build after a program reload: loading a program does not touch the data memory, and a soft reset keeps it (test_dali_commission_then_scene). To make room, both builds share a shorter receiver than dali_gear.pe (the same half-bit windows and settling time): each run between edges is taken as one or two half bits of its level, the level of the second half of each bit is the bit, and a run of two half bits must start in the middle of a bit. The backward frame is sent with shout.od (first half the inverse of the bit, second half the bit).

Sources for the added commands: python-dali (sde1000) dali/gear/general.py, written from IEC 62386-102. What the firmware takes from it:

Command python-dali description Firmware
A5 INITIALISE (twice) the addressing commands are processed only after it; data 0: every gear, 0AAAAAA1: the gear with that short address, FF: gear without one enters the initialisation state (data memory 12 = 1, not withdrawn); no 15 minute timeout
A7 RANDOMISE (twice) a new 24-bit random address in the initialisation state; the three bytes are mixed with the timer value at the last edge of the frame (the master's bit timing), not a true random source
B1, B3, B5 SEARCHADDR H/M/L the search address bytes
A9 COMPARE yes if the random address <= the search address and the gear is not withdrawn
AB WITHDRAW the gear whose random address equals the search address no longer answers COMPARE data memory 12 = 3
B7 PROGRAM SHORT ADDRESS stored if random = search; MASK deletes it 0AAAAAA1 or FF
B9 VERIFY SHORT ADDRESS yes if it is the own short address (in the initialisation state)
BB QUERY SHORT ADDRESS the short address as 0AAAAAA1, or MASK, if random = search
A1 TERMINATE the addressing ends
10+n GO TO SCENE the scene level with the fade time; MASK: no change MIN..MAX clamping and the limit error as DAPC
40+n SET SCENE (DTR0, twice), 50+n REMOVE FROM SCENE (twice) DTR0, or MASK scenes at 0xB0 + n
B0+n QUERY SCENE LEVEL the level or MASK
2E SET FADE TIME (DTR0, twice) T = 0.5 s x sqrt(2^X), X = 1 to 15; 0: no fade X above 15 is taken as 15
2F SET FADE RATE not kept: QUERY FADE TIME/FADE RATE answers rate 7
A5 QUERY FADE TIME/FADE RATE fade time in the high nibble, rate in the low X << 4 | 7
DAPC, GO TO SCENE with X > 0 fade from the actual level to the new one in T one level step at a time, spread over T by an accumulator on a 2 ms grid; from off it starts at MIN, a fade to 0 runs to MIN and then switches off (assumed)
DAPC MASK stops a fade in progress
OFF, RECALL MAX/MIN without fading also stop a fade
QUERY STATUS bit 4 fade running

T is kept in 2 ms units: 125 (even X) or 177 (odd X) shifted left by X / 2 + 1, computed when SET FADE TIME runs (X = 3: 708 units = 1416 ms against 1414.2 ms; X = 15: 45312 units = 90.6 s against 90.5 s). RESET also sets the scenes to MASK, the fade time to 0 and the random and search addresses to FFFFFF; these reset values are assumed (the sources above do not list them).

  • dali_gear.pe: a subset of IEC 62386-102: no fading (fade time and rate, UP/DOWN, STEP commands), no scenes, no system failure level, no memory banks, no device type commands (QUERY DEVICE TYPE has no answer), no addressing procedure (INITIALISE, RANDOMISE, COMPARE, SEARCHADDR, PROGRAM SHORT ADDRESS), no IEC 62386-207 LED commands. The physical minimum is fixed at 1.
  • The extended builds: the addressing procedure and scenes with fade are in two programs, not one (703 words together); no fade rate (UP/DOWN, STEP), no extended fade time, no 15 minute limit on the initialisation state, no QUERY RANDOM ADDRESS, no PHYSICAL SELECTION; the random address is mixed from the master's bit timing, so two chips of this design with the same clock and the same frames would draw the same address. The fade is counted in the idle loop's 1 ms base period, so it waits while a frame is received or answered (about 24 ms per forward frame with its answer window); levels between 1 and MIN are skipped as described above. The settings of T come from SET FADE TIME: a host that writes the fade time byte with DATA_W must also write T.
  • No collision detection: the gear does not watch the line while it sends a backward frame (several gears answering a broadcast query overlap on the line, as on a real bus).
  • The settings live in data memory (kept over a soft reset, not over a power cycle of the chip).
  • The lamp output is only the ACTUAL LEVEL byte in data memory; no PWM pin.
  • The receiver's windows (334 to 500 us half bits) follow one secondary source; the two-half-bit window is derived from it.
