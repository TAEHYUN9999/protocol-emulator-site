How it works

Four small processors implement bus protocols in firmware. The chip has two barrel CPUs (cores) with two hardware threads (harts) each. The two harts of a core own alternating clock cycles, so one tick is two clocks (40 ns) and a stalled hart never disturbs another. The instruction set is built for pins: drive or release a line, shift a register bit out or in, wait for a level with an optional timeout, and wait on a drift-free period timer (with a per-hart prescaler, periods up to 335 ms). Each hart drives the pins through its own registers and a pin is the wired AND of all four, so two harts can be two devices on one open-drain bus, for example an I2C controller and an I2C target on the same two pins.

Each core has its own program memory, a 1024 word, 16 bit SRAM loaded over a host SPI link, so new protocols can be added after fabrication. Two four byte FIFOs per core move data between host and firmware, and two more between the cores. A 128 byte data memory per core, shared by its two harts, holds buffers and lets one hart hand data to the other; it is part of a 1 KB SRAM that firmware can also reach as a whole. Each hart also has a CRC unit with a programmable polynomial: any CRC up to 16 bits, fed a byte or a single bit per instruction.

Three features help debug unknown buses. An event capture block stores only pin changes with a time delta, so 32 entries can span a long trace; its deep mode keeps 512 entries, with a pin-pattern and edge trigger and up to 448 entries from before the trigger. A freeze-on-match timer lets firmware measure pulse widths, which gives UART auto-baud in firmware. A predictive launcher learns the period of a clock on a pin and changes a pin at the predicted edge plus an offset in clocks of 20 ns, before or after the edge. Delay lines on P0 to P3, calibrated against the clock, add steps of about a nanosecond; they are bypassed after reset. They are checked against a delay model in RTL simulation, and with the delays of two layouts of the RTL before the four blocks below in gate-level simulation (docs/dly.md); not on silicon.

Four further blocks serve bring-up and debugging. A self test runs March C- or March SS on any of the five SRAM macros through its BIST port and keeps the first failing address and bits for the host (commands 0x48, 0x49; docs/mbist.md). A debug unit gives each hart a breakpoint, single steps and instructions injected by the host (commands 0x50, 0x51; docs/debug.md). Each hart has a fractional tick generator, so a firmware can send at any baud or audio rate with a mean error of zero (docs/tickgen.md). Pin writes can land one clock later, so edges fall on every 20 ns clock, and harts can wait on pin patterns and on event flags (docs/isa3.md). Firmware copies show what they buy in simulation: S/PDIF and I2S at exact 32, 44.1 and 48 kHz on the tick generators, USB low-speed edges within 6.7 ns of the grid with the one-clock-late writes (inside the host jitter limits, the original was outside), and an I2C target that waits on SCL and SDA together; the event flags are not used by a protocol firmware yet.

Firmware included in firmware/. All of it is checked in simulation. The board results are of earlier designs with one core. On an FPGA board (the chip RTL on a ZCU104, a KD240 as peer and host) the self test runs sections 1 to 15 with the 512-word design: the fixed UART, SPI master and I2C master, the CRC unit, the general UART, I2C master, SPI master and SPI device, and the general SWD host debugging the general SWD target on the same chip (271 passes, 0 fails), and the same self test ran for 8 hours: 1,252,406 passes, 0 fails. The one-core design after it (commit 422ec10, with the per-hart pin registers, the deep capture and the USB line unit) runs sections 1 to 16 on the same boards: 279 passes, 0 fails. The RTL of this page (two cores, five SRAM macros, delay lines and the four blocks above; its revision is STATUS byte 11) has not been built for a board. The I2C target and the two mode 0 SPI devices were checked against the KD240's Xilinx AXI IIC and AXI Quad SPI on the earlier designs (last on the 256-word design, 2026-11-10); that design's self test (sections 1 to 14) also ran for 8 hours: 2,345,434 passes, 0 fails. Details are in docs/verification.md.

A 10BASE-T transmitter and receiver share a 128-byte frame buffer in the shared SRAM of core 0. The receiver takes one frame from ui[7] (through an external LVDS receiver), stores its first 128 bytes, and reports the length and whether the FCS is correct. Instead of them, a USB full-speed line unit can use the same buffer and commands on uio[0] (D+) and uio[1] (D-): NRZI, bit stuffing, clock recovery on both clock edges, CRC5 and CRC16 in hardware. An RMII line unit can take their place too: TX_EN and TXD0/1 on uo[5:7], CRS_DV and RXD0/1 on ui[5:7], 10 or 100 Mbit/s to an external PHY whose REF_CLK is the chip clock. A SpaceWire line unit (Data-Strobe encoding and decoding, parity, Nulls, disconnect detection) can use uo[6:7] and ui[6:7] through external LVDS parts; the firmware talks to it through registers in the load/store space. The line units and the capture serve core 0.

How to test

Run the clock at 50 MHz and hold SCK at or below clk/8 (6.25 MHz). Wait 130 clocks after reset. Using host SPI mode 0, write the program of core 0 with command 0x10, set hart 1 start with 0x02, soft reset with 0x01 value 0x04, then start with 0x01 value 0x01 or 0x03. Status command 0x03 returns ID 0x50 as its sixth byte and the RTL revision as its twelfth (byte 11; the values are listed in docs/architecture.md). Between two transactions hold CS_N high for at least four clocks (80 ns at 50 MHz): a shorter high pulse is taken as a glitch and ignored. Core 1 (harts 2 and 3) has the same commands at 0x14 (program), 0x04 (hart 3 start) and 0x05 (status, ID 0x51), and its run bits are bits 3 and 4 of command 0x01.

Add pull-ups on P0 to P7 for open-drain protocols. Assemble firmware with tools/peasm.py.
