File Role Words
firmware/margin_i2c.pe I2C controller that moves its own SDA change point in 20 ns steps from the SCL fall, runs a real transfer at every step (START, address with R/W = 1, ACK, one byte read, NACK, STOP) and counts which steps the target accepts. Result: a 1-D eye per SCL speed and a 2-D shmoo (SCL half period x SDA offset) in the data memory, plus the longest passing window per row computed on the chip. Hart 1 runs SCL, hart 0 runs the transfers. 161 of 512 (hart 0 132, hart 1 29)

No RTL change. Simulation only (RTL, Icarus Verilog 11.0, cocotb 2.0.1).

Until now the timing knob of the launcher (plaunch offset) existed but the pass/fail judgement was done outside the chip (the board's ILA and a host script, fpga/board/skew_sweep.tcl). Here the chip turns the knob, runs the protocol, reads the device's answer and writes the map; the host only reads one block of memory. The procedure is the one of receiver lane margining in PCIe and of a shmoo plot on an ATE: step one timing parameter (and optionally a second), count passes at each step, report the window. (The comparison is to the idea only; the PCIe and ATE documents listed under Prior art were not read for this page.)

Pins

Pin Use
P0 (uio[0]) SCL, open drain (low / rel), driven by hart 1
P1 (uio[1]) SDA. Push-pull from the START to the end of the address byte, because the launcher writes only the output bit of a pin (docs/architecture.md, Predictive launcher); open drain (released) from the ACK on, and open drain for the STOP

Pull-ups on both lines. Driving SDA push-pull during the address byte is safe on a real bus only because no other device drives SDA during the controller's address bits; it is not a general I2C controller.

How it works

  • SCL: hart 1 toggles SCL with exactly H ticks low and H ticks high (twait grid), between transfers too, so the launcher stays locked on SCL falling edges (pelsel SCL, 0). A target ignores clock pulses without a START. Before each new row (new H) hart 1 gives one short SCL period of 4 ticks. The launcher treats a short interval as a restart, the next long interval as a pause and learns the period afresh from the one after, so its estimate is exact (an integer number of clocks) when it locks. Without this a change of H by a few clocks counts as "consistent" and the estimate converges slowly: in a first version without it, the first two transfers of every new row had their SDA changes 1 to 4 clocks off and drifting within one byte. WARM SCL periods (48 in the tests) pass before the first transfer of a row.
  • The scanned edge: during the high phase before each SCL fall, hart 0 arms plaunchr SDA, bit, r0: the address bit appears at that fall plus r0 clocks. All seven SDA changes of the address byte 0xAB (A6..A0 = 0x55, R/W = 1; 1010 1011 changes SDA at bits 7 to 1, both directions) are placed this way; the START, the release before the ACK and the STOP are not scanned.
  • The judgement is the target's own: a trial passes when the target ACKs the address and the byte read back equals EXP. After a failed trial hart 0 gives nine more SCL clocks with SDA released (as for a bus clear) so that a confused target finishes whatever byte it thinks it is sending, then a STOP. Each trial is independent of the previous one.
  • The map: for each row r and each offset OFF0 + i, the number of passing trials out of K. At the end of the row the firmware finds the longest run of offsets where all K trials passed and stores its first offset (LEFT) and its length (WIDTH).

Settings and results (data memory)

Address Name Meaning
0x00 OFF0 first offset, signed clocks from the SCL fall
0x01 NOFF offsets per row, step 1 clock; NROW x NOFF <= 96
0x02 K trials per offset, 1 to 255
0x03 NROW rows, 1 to 8
0x04 ADDR address byte, bit 0 (R/W) must be 1
0x05 EXP data byte the target returns
0x06 WARM SCL periods before the first trial of a row, 48 or more
0x07 DONE 0 at start, 1 when the map is complete (poll with DATA_R)
0x08 to 0x0F H[r] SCL low time = high time of row r, in ticks (40 ns), 10 or more
0x10 + 2r LEFT[r] first offset (signed, commanded clocks) of the longest all-pass run
0x11 + 2r WIDTH[r] length of that run in clocks, 0 if no offset passed
0xA0 + r x NOFF + i map passing trials at offset OFF0 + i of row r

Work bytes are kept at 0x20 to 0x26 (frame buffer): Ethernet and the capture must stay unused. Run with CTRL = 3, START1 = label hart1 (word 132).

Launch latency (measured)

Every SDA change of every trial was measured at the pins against its SCL fall: all 1,428 launches of the three tests (504 + 252 + 672) landed exactly one clock after the commanded offset, none anywhere else. The launcher is tuned for a reference edge that arrives at a random point inside a clock (a host's SCK, test/test_pel.py, within one clock); SCL here is made by the chip itself on the clock grid, and the result is a constant +1 clock. So offset at the pins = commanded offset + 1 clock (20 ns). The map and LEFT are in commanded clocks; add 1 for the time at the pins. The test asserts this constant, so a change in the launcher or the firmware that moves it shows.

Counterpart model and expected window

WindowTarget in test/test_margin.py is an I2C target written from UM10204 Rev. 7.0 (START and STOP are SDA changes while SCL is high, data latched at the SCL rise, 7-bit address and R/W, ACK, the controller NACKs the last byte read) with two numbers for its data valid window:

  • T_SU: the target latches the level SDA had T_SU before the SCL rise. A change less than T_SU before the rise is missed (setup violation; the bit is the old level).
  • T_HD: the target's own view of SCL falls T_HD after the bus SCL. An SDA change less than T_HD after the fall happens while SCL is still high for the target, so it is a START (SDA falling) or a STOP (rising). This is how UM10204 describes the need for a hold time: Table 11 note [2] ("Ensure SCL drops below 0.3VDD on falling edge before SDA crosses into the indeterminate range") and Table 13 note [3] for Hs-mode ("A device must internally provide a data hold time to bridge the undefined part between VIH and VIL of the falling edge of the SCLH signal").

So an SDA change d after the SCL fall passes only if T_HD <= d <= T_LOW - T_SU. The test takes d and T_LOW from the pins (every SDA change and every SCL edge, in clocks), applies the rule, and checks for every single trial that the model's ACK agrees with the rule, that the chip's map count equals the number of trials the rule passes, and that LEFT and WIDTH equal the rule's window. Nothing in the expected values comes from the firmware. The values of T_HD and T_SU are model parameters, chosen off the 20 ns grid so that no edge sits exactly on a boundary; UM10204 Table 11 itself asks for tSU;DAT of at least 250 ns (Standard-mode), 100 ns (Fast-mode), 50 ns (Fast-mode Plus) and tHD;DAT of at least 0.

The model's own data bits come T_OUT after the SCL fall, with T_HD <= T_OUT <= T_LOW - T_SU, so the model never trips over its own changes.

The shmoo shows what the rule predicts: the left edge is the target's hold requirement and does not move with the SCL speed; the right edge moves 2 clocks per tick of T_LOW (T_LOW - T_SU), and the window closes at about T_LOW = T_HD + T_SU = 360 ns. Run of the whole module (2026-11-12, RTL, Icarus Verilog 11.0, cocotb 2.0.1, machine shared with other simulations): test_margin TESTS=3 PASS=3 FAIL=0, about 9.1 ms simulated, 57 s of simulation (72 + 36 + 96 trials; about 32 us per trial at H 16).

Controls

test/controls_margin.sh makes each broken copy with sed, runs the whole test_margin module on it (MARGIN_FW) and counts failing tests. All four were caught, each at the check it aims at:

Control Change in the copy Result First failing check
no_step the offset is never stepped (addi r0, 1 of the point loop removed) 3 of 3 tests FAIL launches no longer follow the commanded offset: "launch error not constant: -34 .. 1 clocks"
map_shift the map starts one entry late (ldi r0, MAP+1) 3 of 3 FAIL chip map vs the rule: the 14 passing entries one place to the right
eye_left LEFT computed one clock too far right 3 of 3 FAIL "chip window 13, 14; expected 12, 14" (commanded clocks)
no_launch SDA changed by the hart at once (low / high) instead of by the launcher 3 of 3 FAIL the address SDA changes come 15 to 19 clocks before the fall, in the high phase

The counterpart control is test_margin_eye_moves_with_target: the same firmware against a target with other T_HD and T_SU must report a window moved by exactly the predicted clocks, and it does (+4 on the left, -4 on the right).

Limits

  • Resolution 20 ns (one clock), the launcher's step. The window edges are exact only to that grid; a device whose T_HD is 250 ns and one whose T_HD is 241 ns give the same map.
  • Only the controller's SDA change point is scanned (the output side: where the chip puts its edge relative to its own clock). The pass/fail comes back through the protocol (ACK and read data), so no host help is needed. Scanning the chip's own SDA sample point (input side) at 20 ns needs the launcher to move the SCL edge against a fixed sample tick, or both harts' clock parities; not done here.
  • SDA is push-pull during the address byte (the launcher cannot change an output enable). START, STOP, the ACK release and the read sampling are at fixed points and are not scanned; the model does not check tSU;STA, tHD;STA, tSU;STO or tBUF.
  • SCL keeps running between transfers so that the launcher stays locked. A real target ignores clock pulses without a START, but an SMBus device that times out on long activity was not considered.
  • Offsets must leave the launcher time to arm: the arm comes about 14 clocks after hart 0 sees the SCL rise (18 clocks after the START for the first bit). Tested ranges: commanded -6..29 at H 16 and 4..27 at H 10 to 16, launcher err 0. An offset that is too early sets err and the bit is not launched, which the map shows as a failure; a host should check err (STATUS byte 4 bit 7).
  • H of at least 10 ticks; at most 8 rows and 96 map entries.
  • Simulation only. On silicon the pad and board delays add to every offset; the map then shows the window as seen at the device, which is what a margin scan should report, but the absolute numbers were only checked in RTL simulation.

Not used here: a scale below one clock

The delay lines of P0 to P3 (dly.md) are in the RTL since part D1 of branch int5, and SCL and SDA are on two of those pins, but this firmware does not use them: its offsets step by one clock. With dlyw it could step the output tap of SDA inside each clock as well as the launcher offset, so the window edges would be found finer than 20 ns; the open-drain release before the ACK could be scanned too, and on the input side the chip's own SDA sample point, the way firmware/dly_train.pe sweeps the input tap of its own link (dly.md). The same WindowTarget and controls would check it. None of this is written or measured.
