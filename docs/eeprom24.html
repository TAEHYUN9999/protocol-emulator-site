File Role Words
firmware/eeprom24.pe The chip answers on I2C as a Microchip 24LC02B 2-Kbit EEPROM: 256 bytes, byte and 8-byte page writes with the page roll-over, a self-timed write cycle after the STOP during which it does not acknowledge (ACK polling), current address, random and sequential reads. 99 of 512 (one hart)

Reference: Microchip DS20001709M, "24AA02/24LC02B/24FC02 2K I2C Serial EEPROM" (2021); section numbers below are from it. The software order checked is that of Linux drivers/misc/eeprom/at24.c. No RTL change. Checked in simulation only.

Why this device: the write cycle. An EEPROM that ACKs again right after a write (as the competing designs' EEPROM emulations do) never exercises the retry loop that every EEPROM driver has; this one NACKs for the write cycle time, like the real part, so ACK polling and the at24 retry run as they do on a board.

Pins

Pin Use
uio[6] (P6) SCL, input only
uio[7] (P7) SDA, open drain

Both need pull-ups. The control byte is 1010 xxx R/W and the three block bits are don't care (5.0), so the device answers on 0x50 to 0x57, as a 24LC02B does.

Memory

The array is the whole load/store address space of the core: EEPROM address e is ld/st address e (data memory at 0x00 to 0x1F and 0xA0 to 0xFF, the 128-byte frame buffer at 0x20 to 0x9F). The firmware keeps its own state in registers only (address pointer, data bytes of the current write, write cycle flag; the write cycle's end is the timer reaching 0). The host fills the array before the run with DATA_W (data memory) and ETH_W (frame buffer), and can read it at any time with DATA_R and CAP_R. Ethernet and the capture must not be used at the same time (they share the frame buffer). Like a real EEPROM's array, the contents survive a soft reset; unlike it, not a power cycle of the chip.

Behaviour

Datasheet Firmware
6.1 byte write: control, word address, data, STOP; the write cycle starts at the STOP as stated
6.2 page write: up to 8 bytes into the page buffer; the low 3 pointer bits count and roll over inside the page, more than 8 bytes overwrite the first ones; the page is written after the STOP each byte is stored as it arrives at the page-rolled address (same result after a STOP)
7.0 ACK polling: during the write cycle the device does not ACK; table 1-2: TWC 5 ms max no ACK for any control byte for 2.5 ms (62,500 ticks) after the STOP; the bus keeps being watched in that time
8.1 current address read: the pointer of the last access plus one as stated
8.2 random read: a word-address write, then a repeated START and a read as stated; the word-address-only write starts no write cycle
8.3 sequential read: the pointer increments after each byte, over the whole array rolls over from 0xFF to 0x00

Assumptions where the datasheet is silent ("All operations must be ended with a Stop condition"): a write that ends with a repeated START keeps the bytes already received and starts no write cycle.

Not implemented: WP (the array is always writable), the 24FC02's 1 MHz.

While SCL is high the receive loop reads SCL and SDA in one sample (rdp; so SCL must be P6 and SDA P7) every 5 ticks: UM10204 allows a data hold time of 0 (Table 10), and two separate reads one tick apart would take an SDA change just after the SCL fall for a START or STOP. The test includes a controller with a 20 ns hold time.

Tests

test/test_eeprom24.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_eeprom24

Eeprom is written from the datasheet sections above, not from the firmware. It accepts a NACK of the control byte only within 5 ms (TWC max) of the STOP that started a write cycle, and every byte read and the whole array (read back through DATA_R and CAP_R at the end) must equal the model. The array is filled with random bytes before the run. The controller and the bus monitor (UM10204 Table 11 minimums, and a check that the chip never drives SCL or SDA high) are those of test/test_i2c.py.

Linux at24 order

test_eeprom_linux_at24 replays at24.c (the copy read for this work) for a "24c02" on an adapter with I2C_FUNC_I2C (i2c-xiic): regmap-i2c writes S A0 off data P and reads S A0 off Sr A1 data P. at24_regmap_write and at24_regmap_read retry a transfer that fails (here: the control byte is not ACKed, -ENXIO) after usleep_range(1000, 1500) (the test waits 1.25 ms) until at24_write_timeout (25 ms) has passed; write chunks never cross a page (at24_adjust_write_count); the page size is 1 unless the device property pagesize is given (8 for a 24c02 in a device tree).

at24 step Bus Tries Why
probe: at24_read(0, 1) S A0 00 Sr A1 xx N P 1
write 8@0x10 (pagesize 8) S A0 10 30..37 P 1 starts a 2.5 ms write cycle
write 8@0x18 S A0 N P, 1.25 ms, S A0 N P, 1.25 ms, S A0 18 38..3F P 3 NACKed at 0 and 1346 us after the first chunk's STOP
read 16@0x10 NACK, NACK, then S A0 10 Sr A1 30..3F P 3 the second chunk's write cycle; at24_regmap_read retries the same way
write 1@0x2e, 1@0x2f, 1@0x30 (pagesize 1) 1, 3, 3 every single-byte write starts a write cycle

Every NACK came within 1.6 ms of a write STOP (the model allows 5 ms), and the last write cycle ended (first ACK) 3.03 ms after its STOP, well inside at24's 25 ms. The array read back through DATA_R and CAP_R equals the model.

Controls

Each control is a copy of eeprom24.pe with one planted bug, run with EEPROM_FW=<path>. All three fail.

Planted bug Test First failure
No write cycle (ACK at once after a write, as in the competing emulations) test_eeprom_linux_at24 the read-back succeeds at the first try: at24's retry path is never taken ("the read-back should meet the second write cycle")
No page roll-over (the pointer counts on across the page) test_eeprom_datasheet_400k the current address read after the 11-byte page write: chip b7 42 f2 6b, model c3 1c 81 ac
The read pointer does not increment test_eeprom_datasheet_400k same read: chip c3 c3 c3 c3, model c3 1c 81 ac

Limits

  • The write cycle is a fixed 2.5 ms (TWRH:TWRL), within the 5 ms maximum.
  • No write protect pin.
  • 400 kHz is the documented speed; the receive loop samples SCL and SDA every 5 ticks while SCL is high (one pass of the rx1 or rx0 loop: rdp, shl, a branch not taken, shl, the branch back).
  • The frame buffer belongs to the array, so the Ethernet transmitter and receiver and the capture cannot be used with this firmware.
