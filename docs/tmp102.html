File Role Words
firmware/tmp102.pe The chip answers on I2C as a TI TMP102: pointer, temperature, configuration, T_LOW and T_HIGH registers, conversions at the programmed rate in real time, shutdown and one-shot, comparator and interrupt mode with the fault queue on an ALERT pin, the SMBus alert response with arbitration, and the general call reset. Hart 0 is the bus, hart 1 is the inside of the device. 447 of 512 (hart 0 163, hart 1 284)

The reference is TI SBOS397I (August 2007, revised June 2024); section and table numbers below are from it. Unmodified Linux drivers/hwmon/tmp102.c (v5.15) and the alert loop of drivers/i2c/i2c-smbus.c are the software it was checked against. No RTL change: the firmware uses existing instructions only. Checked in simulation only, not on a board yet (see "Board demonstration" for the plan).

Why this device: a sensor whose internal time (conversion every 1/rate, a fault queue counted in conversions) drives a separate interrupt pin, plus an SMBus alert response where the target, not the controller, must arbitrate bit by bit.

Pins

Pin Use
uio[6] (P6) SCL, input only (a TMP102 never drives SCL, 6.3.6)
uio[7] (P7) SDA, open drain
uio[0] (P0) ALERT, open drain (5.5: VOL for SDA and ALERT). Pulled low when active with POL = 0, released when active with POL = 1

All three need pull-ups. The address is 1001000 (ADD0 = GND, Table 6-4), .equ AW in the source.

Host interface

The host is the temperature: it writes two bytes to the FIFO at any time, the temperature in the 13-bit format of Table 6-3 (left adjusted, high byte first; 25.0 C is 0C 80, -25 C is F3 80; the low 3 bits are ignored). The next conversion end takes the latest pair. Until the first pair arrives the input is 25.0 C. The host must always send both bytes (hart 1 waits for the second). No other host interaction is needed; DATA_R shows the registers at the addresses below.

How it works

Hart Does
0, bus START/STOP detection and byte receive (the same rxbyte as i2c_target.pe), ACK; write: pointer byte, then the register bytes stored one by one (6.5.3 "All registers are updated byte by byte"); read: MSB, LSB from the pointer; alert response; general call reset of the registers it owns. Sets event flags for hart 1
1, device A 100 us base period (tsetr, drift free). A conversion is 100 base periods (10 ms, 5.5 typical), then a delay so that a conversion starts every 1/rate (Table 6-5: 4 s, 1 s, 250 ms, 125 ms). Each base period: take the FIFO input, act on events (read, alert response, general call), drive ALERT and the AL bit. At each conversion end: format the result, compare with the limits, fault queue, comparator and interrupt state

The configuration register is split so that each byte has one writer: hart 0 stores the host's bits (F1 F0 POL TM SD, CR1 CR0 EM; R1 R0 forced to 11), hart 1 keeps OS and AL in two bytes that hart 0 ORs into the configuration bytes as it reads them. Events from hart 0 (read, alert response won, general call, one-shot request) are flags set to 1 by hart 0 and cleared by hart 1 after it acted on them. Hart 1 clears a flag only after it has seen it set, so the only loss is a second set of the same flag in the few instructions between that load and the clear; such a second event has the same effect as the first, so nothing is lost in behaviour. Hart 1 also sets the read flag itself when it enters shutdown, to reuse the same interrupt clear. Hart 0 answers the alert response only while the pending byte is set and neither the read flag nor the alert response flag is, so it never answers an alert that is about to be cleared.

Implemented

  • Pointer register P1 P0 (6.5.1), temperature (read only), configuration, T_LOW, T_HIGH; power-up 0000h (until the first conversion), 60A0h, 4B00h (75 C), 5000h (80 C).
  • Reads MSB then LSB (6.3.6.2); writes byte by byte; a pointer write alone sets the pointer for later reads (6.3.5).
  • Result formats: 12 bits (EM = 0) with 128 C and above reading 7FFh as in Table 6-2, and 13 bits (EM = 1) with D0 = 1 (Table 6-9). The limits are compared in the format of the moment.
  • Conversion 10 ms after power-up, general call reset, SD cleared or one-shot; then one conversion per 1/rate for CR = 00, 01, 10, 11 (Table 6-5). The rate is taken at each conversion end.
  • Shutdown (SD = 1): after the running conversion, or at once if the device is in the delay between conversions; OS reads 1 while shut down and 0 during a conversion. One-shot (OS = 1 with SD = 1) converts once and shuts down again (6.4.3, 6.4.4).
  • Comparator mode (TM = 0): ALERT active from Q consecutive results at or above T_HIGH until Q consecutive results below T_LOW, Q = 1, 2, 4, 6 from F1 F0 (Table 6-12). The AL bit shows this comparator state in both modes, inverted by POL (6.5.3.8).
  • Interrupt mode (TM = 1): ALERT active at T_HIGH; cleared by a read of any register, by a successful alert response or by entering shutdown; then active again only at T_LOW, and so on (6.5.4, Figure 6-7).
  • POL inverts the ALERT pin and the AL bit (6.5.3.3).
  • SMBus alert response (address 0001 100, 6.3.7): ACK while an interrupt is pending, then the address byte with LSB 0 for T_HIGH and 1 for T_LOW (POL inverts it). Every 1 bit is read back; when it reads 0 a device with a lower address has won, the chip lets go and keeps ALERT active.
  • General call (6.3.8): 06h resets every register to its power-up value, returns to comparator mode, the temperature reads 0 until the new first conversion.
  • No ACK for other addresses, including the HS-mode controller code 0000 1xxx (6.3.9).

Not implemented, and assumptions

Not implemented:

  • HS mode (up to 2.85 MHz): the master code gets no ACK as on the real device, but the transfer that follows is too fast for the firmware. Fast mode is the limit (see Tests).
  • Timeout (6.3.10, SCL held low 30 ms resets the interface).
  • The sensor itself: the temperature comes from the host FIFO. Accuracy, noise and self heating are not modelled.
  • ADD0 pin: the address is fixed in the source (.equ AW).
  • Event latency: hart 1 acts on reads, alert responses and register writes once per base period, so ALERT follows them up to 100 us later, and a conversion started by a one-shot, a general call or clearing SD begins up to 100 us after the command.

Where the datasheet is silent, the firmware and the test model take the same assumption:

  • A third and later data byte of a write is acknowledged and ignored; a read goes on MSB, LSB, MSB, ... while the controller acknowledges.
  • Pointer bits P7 to P2 are ignored.
  • The limit registers keep 13 bits: the LSB is stored with D2 to D0 cleared. In normal mode the comparison ignores D3 as well.
  • The temperature register keeps the format of the conversion that wrote it; changing EM takes effect at the next conversion end. Linux saw exactly this on a real TMP102: commit d0725439 ("hwmon: (tmp102) Fix first temperature reading", 2017, kernel bug 197167) reports readings of about double the real value after the driver switches to 13 bits, until the next conversion.
  • A one-shot request is OS = 1 written together with SD = 1. It is kept until the device is shut down, so writing 81h in continuous mode shuts down (after the running conversion, if one is running) and then converts once more.
  • Entering shutdown from continuous conversion clears a pending interrupt; the end of a one-shot does not.
  • The alert response is answered only in interrupt mode (6.3.7 describes it for TM = 1).
  • A general call with a second byte other than 06h is acknowledged on the address byte and not on the second byte.
  • The rate (CR1 CR0) is read at each conversion end, so a new rate starts with the delay after the next conversion.

Tests

test/test_tmp102.py; run from test/ with make COCOTB_TEST_MODULES=test_tmp102 (all eight tests; the two real-time ones simulate about 390 ms and 285 ms and take most of the time; COCOTB_TEST_FILTER=<name> runs one). TMP102_FW selects another firmware file for the controls.

The reference is Tmp102Model, written from the datasheet text, not from the firmware. Every operation (FIFO input, register write, read, alert response, general call) goes to the chip and to the model, and the chip's ACKs, bytes and its own drive of the ALERT pin must equal the model's. The model also has to reproduce the datasheet's example values (Tables 6-2, 6-3, power-up values) where the test asserts them directly. The model is time driven; since the firmware works on a 100 us base period, operations are placed at least three base periods away from every conversion start and end, where the result would depend on that latency. The I2C controller and the bus monitor (every edge against UM10204 Table 11, and a check that the chip never drives SCL, SDA or ALERT high) are the models of test/test_i2c.py.

Two time scales:

  • Real time: the firmware as it is. 10 ms conversion, 4 Hz and 8 Hz periods, the Linux driver's 35 ms.
  • Scaled: the same firmware with only its time constants changed through the assembler's .equ override: base period 10 us instead of 100 us and all counts divided by 10, so every time is 100 times shorter (100 us conversion; 40, 10, 2.5, 1.25 ms periods for 0.25, 1, 4, 8 Hz). The model uses the datasheet times divided by 100. 0.25 Hz and 1 Hz are checked only this way (4 s of real time is about 6 hours of simulation).

Linux driver order

test_tmp102_linux_driver (scaled, 100 kHz like the KD240 AXI IIC) and test_tmp102_realtime_linux_driver (real time) replay the bus accesses of drivers/hwmon/tmp102.c (v5.15) in its order and with its arithmetic (tmp102_reg_to_mC, tmp102_mC_to_reg, the probe check and the bits it sets and clears). With an adapter that has I2C_FUNC_I2C (i2c-xiic does), regmap-i2c reads a register as S 90 reg Sr 91 MSB LSB P and writes it as S 90 reg MSB LSB P. The driver's register cache (REGCACHE_RBTREE, no defaults) keeps T_LOW, T_HIGH and the configuration after their first access, so only temp1_input reaches the bus every time; the test keeps the same cache.

Board demonstration (plan, not run)

Goal: the KD240's Ubuntu takes the chip on the ZCU104 for a real TMP102 and reads it through the unmodified tmp102 hwmon driver. Nothing below has been run.

What exists (fpga/):

  • ZCU104 (fpga/zcu104/zcu104_pe_top.v): the chip RTL with the host sequencer pe_fpga_host as its SPI host. The sequencer script is $readmemh("host_script.hex"), fixed at synthesis, and the VIO mode input is 2 bits; all four modes are taken (0 self test, 1 I2C target, 2 SPI device, 3 SPI device with the launcher, fpga/gen_script.py). Chip pins P0 to P7 go to J87, with pull-ups.
  • KD240 host bit (fpga/kd240/kd240_host_top.v, overlay fpga/kd240/pe_host.dts): AXI IIC at 0xA0000000 on Pmod J2 P6 (SCL) and P7 (SDA), open drain with pull-ups, clock-frequency = <100000>; this is the only I2C path from these pins that Linux sees (bus i2c-2 in fpga/board/pe_xfer.py; the number is given at load time). P0 is an input with a pull-up that goes only to the 300 MHz host ILA (smp_pad_q[0]); it reaches neither a PS GPIO nor an interrupt, so Linux cannot see ALERT.

Steps:

  1. Chip side. Add a sequencer mode that loads tmp102.pe, starts both harts (load() in gen_script.py already sets START1 and runs both when the file has hart1), then feeds a temperature profile with send(hi, lo) and WAIT steps, and halts. Either replace a mode (mode 1 serves the same KD240 I2C bus) or widen the mode input to 3 bits (VIO change). The script has 5,074 of 8,192 words; loading takes about 900 words; one WAIT is at most 4,095 x 256 clocks (21 ms), so a profile costs about 48 words per second of waiting (about 45 s in the free space, or add a repeat op to the FPGA-only sequencer). Then regenerate host_script.hex and rebuild the ZCU104 bit (Vivado).
  2. KD240: load the host app with fpga/board/host_load.sh (it stops the QSPI bridge daemon, copies the bit and overlay and runs xmutil loadapp pe-host; restore_bridge.sh afterwards).
  3. On the KD240:
