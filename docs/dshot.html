File Role Words
firmware/dshot.pe Flight controller side of DShot600: sends one 16-bit ESC frame (11-bit throttle, telemetry bit, checksum) per host command. Assembled with BIDIR = 1 it sends the inverted bidirectional frame and receives the ESC's GCR-coded eRPM reply: run lengths, transition decoding, GCR 5b/4b, the reply checksum. 196 of 512 (one hart)

No RTL change: existing instructions only (twait grid with tset per bit part, shout push-pull, waitp.to.frz with tgetl for the reply's run lengths). Checked in simulation only, not against a real ESC.

Sources. DShot has no standard document; these are the references used by flight controller and ESC firmware authors:

Source Used for
brushlesswhoop.com, "DShot and Bidirectional DShot" DShot600 bit 1.67 us, T1H 1.25 us, T0H 0.625 us; frame = 11-bit throttle (0 disarmed, 1 to 47 commands, 48 to 2047 throttle), telemetry request bit, checksum (v ^ v >> 4 ^ v >> 8) & 0xF, MSB first; the worked example (throttle 1046: 1000001011000110, bidirectional 1000001011001001); bidirectional: inverted signal and checksum, 30 us turnaround, reply of 21 bits at 5/4 of the bit rate, GCR table, 21-bit transition coding, eRPM value eeemmmmmmmmmcccc (period in us = m << e)
Betaflight src/main/drivers/dshot_bitbang_decode.c the reply's first bit is a start bit followed by 20 GCR bits; decode table; a reply is valid when the XOR of its four nibbles is 0xF

The two disagree on the reply checksum: brushlesswhoop says it is computed as in uninverted DShot, Betaflight's decoder (which reads real ESCs) requires the XOR of all four nibbles to be 0xF, i.e. an inverted checksum. The firmware and the test follow Betaflight.

Pins

Pin Use
uio[0] (P0) DShot signal to the ESC. BIDIR = 0: push-pull, idle low. BIDIR = 1: push-pull during the frame, idle high, released (pull-up) while the ESC answers

Frame timing

DShot600 Firmware Clocks
Bit 1.67 us (600 kbit/s) 42 ticks = 1.68 us (595.2 kbit/s, +0.8 %) 84
T1H 1.25 us 31 ticks = 1.24 us 62
T0H 0.625 us 16 ticks = 0.64 us 32
Frame 26.7 us 26.88 us 1344

600 kbit/s is 41.67 ticks; 42 is the nearest whole tick. Each bit has three parts (leading level, data bit, trailing level); each part ends with a twait and the pin changes in the next tick, and the next part's period is set two ticks after the edge (tset T - 2), so all widths are exact. edge_audit.py on test_dshot_normal: intervals 32, 52, 62, 22 clocks only (0 bit: 32 + 52; 1 bit: 62 + 22), plus the gaps between frames.

Host interface

Direction Bytes
Host to chip (FIFO) 2 bytes per frame: the 12-bit value throttle << 1 \| telemetry, high nibble first (bits 11..8 in the low nibble of the first byte, then bits 7..0)
Chip to host (BIDIR = 1 only) 3 bytes per frame: status, reply value high byte, low byte

Status: 0 ok; 1 no reply within 200 us after the frame; 2 a time between edges longer than 3.5 reply bits, or an edge after the 21st bit; 3 a 5-bit group that is no GCR code; 4 the reply checksum is wrong (the value is still given). The value bytes are 0 for status 1 and 2.

One frame per command: the host sets the frame rate (an ESC needs a steady stream, for example every 125 us at 8 kHz).

Reply decoding (BIDIR = 1)

After the last bit the chip releases the line and waits for the start bit (falling edge). From then on each edge is caught with waitp.to.frz (the timer is restarted 3 ticks after every edge, with a 133-tick timeout, 4 reply bits), and the time since the previous edge is rounded to 1, 2 or 3 reply bits (thresholds 49, 82, 116 ticks for 33.3-tick bits); GCR never has more than two 0 in a row, so no run is longer. A timeout ends the reply. Only the run lengths are stored during the reply (one byte each); the decoding runs afterwards:

  1. Runs to bits: each edge after the start bit is a 1 at the end of its run, the other positions of the run are 0; positions after the last edge are 0; an edge at position 21 is the line going back to idle and is ignored.
  2. Four groups of 5 bits, high nibble first, through the GCR table (as compare branches, no table in memory).
  3. Checksum: XOR of the four nibbles must be 0xF.

The rounding allows the ESC's bit time to be off by about -18 % to +16 % (3-bit runs set both limits), less the edge jitter; the test passes at -10 %, 0, +5 %, +10 % with +-80 ns jitter per edge.

Tests

test/test_dshot.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_dshot

The ESC model (written from the sources above, not from the firmware) decodes each frame by pulse width: a bit is accepted when its period is 1.67 us +-3 % and its pulse is within +-5 % of T0H or T1H (these windows are the test's own; no document gives them), checks the checksum (inverted in bidirectional mode), and in bidirectional mode answers 30 us after the frame with a GCR reply built from the table, at 750 kbit/s times (1 + clock error), with jitter per edge. It does not answer a frame with a wrong checksum. Separately the test asserts the exact widths in clocks.

Controls

Each control is a copy of dshot.pe with one planted bug, run with DSHOT_FW=<path>. All three fail.

Planted bug Test First failure
Checksum not inverted in bidirectional mode test_dshot_bidir the ESC model rejects the frame and does not answer: status 1, want 0
T1H one tick long (32 ticks, the bit still 42) test_dshot_normal pulse widths 64 clocks where 62 are expected (the ESC model's +-5 % window alone would accept 1.28 us)
Reply checksum checked against 0 instead of 0xF test_dshot_bidir first reply: status 4, want 0

Limits

  • No automatic frame repetition: the host sends every frame. A host that is slower than the ESC's failsafe timeout disarms the motor.
  • Only DShot600 timing is built in; DShot150/300/1200 need other T0H/T1H/BIT constants (and DShot1200's 0.83 us bit is 20.8 ticks, so its widths are coarser).
  • Extended DShot Telemetry frames are returned as raw values; the host interprets them.
  • Bidirectional mode is chosen at assembly (BIDIR with LEAD, TRAIL, DX, CX), not per frame.

Gate level

Not run at gate level: test_dshot was not among the modules run on the netlist of commit 7c40aac on 2026-11-11 (docs/verification.md, section 6).
