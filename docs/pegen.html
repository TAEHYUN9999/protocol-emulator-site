pegen: firmware from a table of levels

On this page (5 sections)
  1. Table
  2. What the generated firmware does
  3. Examples (firmware/gen/)
  4. Tests
  5. Gate level

tools/pegen.py turns a short JSON table into a transmit firmware for one-line protocols whose bits are fixed patterns of levels on a slot grid: pulse-width codes (WS2812B), pulse-distance codes (NEC infrared), bi-phase codes (DALI Manchester). The table says what the line looks like; the generator writes the .pe that makes the chip draw it. Nothing in the RTL knows these protocols.

python3 tools/pegen.py firmware/gen/dali_tx.json -o firmware/gen/dali_tx.pe

Table

Key Meaning
pin protocol pin 0 to 7
slot_ticks slot length in ticks (40 ns), 2 to 65535
idle line level between frames
drive push (high/low) or od (release for 1, low for 0)
order msb or lsb first inside each byte
zero, one levels of a 0 bit and a 1 bit, one entry per slot; the two may have different lengths
preamble, postamble levels before the first bit and after the last
gap_ticks idle time after a frame before the chip answers

What the generated firmware does

Host interface: n (1 to 128), then n bytes; the chip stores them in the frame buffer, sends the frame and answers n after the gap. Every slot is twait then the level, so each change sits one tick after a slot boundary and every width is an exact multiple of the slot. The slots that both symbols start with are sent before the branch on the bit; the bit test, the loop counters and the next byte load run inside the last slot of a symbol. The generator refuses a table whose last slot is too short for that code.

Examples (firmware/gen/)

Table Protocol Slot Words
ws2812.json WS2812B: 0 = 1000, 1 = 1100, MSB first, 300 us latch 8 ticks, 320 ns 41
nec_ir.json NEC infrared envelope (mark = 1): 16 + 8 slot leader, 0 = 10, 1 = 1000, LSB first, end burst 14062 ticks, 562.5 us 68
dali_tx.json DALI forward frame: idle high, Manchester 1 = low then high, start bit, MSB first, 4 Te stop, 22 Te gap 10417 ticks, Te = 416.7 us 51

The hand-written firmware/ws2812.pe (36 words) and the generated one (41 words) pass the same datasheet model.

Tests

test/test_pegen.py (cocotb) generates each firmware from its table at run time, so the generator itself is under test, and checks the pin with a receiver written from the protocol definition. Each test also generates a wrong variant and checks that the same receiver rejects it. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_pegen
Test Receiver model Result (2026-11-10) Wrong variant
test_pegen_ws2812 WS2812B-V5 datasheet windows and LED chain (from test_ws2812.py) PASS: 6-byte and 128-byte frames inside every window, late flag 0 slot 10 ticks: 16 datasheet errors
test_pegen_nec NEC: 9 ms / 4.5 ms leader, 562.5 us marks, 562.5 / 1687.5 us spaces, LSB first, end burst, every width within 2 % PASS: frame 04 FB 08 F7 decoded, marks 562.5 and 8999.7 us MSB first: decodes as 20 DF 10 EF
test_pegen_dali DALI: idle high, half bits within 10 % of Te, Manchester 1 = low then high, start bit, 16 bits MSB first, 4 Te stop, 22 Te gap PASS: 0xFE80, 0x01A5 in a row, 9,676 us from the end of the stop bits to the next start bit 0 and 1 swapped: decodes as the inverse 0x017F

Sources for the timing: WS2812B-V5 datasheet (Worldsemi); NEC timing as described in the Altium NEC infrared protocol note and the Linux img-ir NEC decoder; DALI 1200 bit/s, Te 416.67 us, 19-bit forward frame, 22 Te settling as described by Teledyne LeCroy and Microchip application notes (IEC 62386-101 itself was not read).

Board: none of the generated firmwares has been run on the FPGA board or against a real LED, infrared receiver or DALI gear; simulation only.
