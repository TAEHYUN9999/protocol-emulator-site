firmware/nrf24.pe The nRF24L01+ seen from its MCU: SPI commands with STATUS shifted out during the command byte, the register map with its reset values, two-level TX and RX FIFOs, CE timing (Thce, Tstby2a), auto acknowledgement with retransmissions, MAX_RT, REUSE_TX_PL, IRQ with the CONFIG masks. The chip's host plays the air. One hart. 511 of 512
firmware/nrf24_drv.pe The MCU side: power-on wait, power-up delay, the Appendix A setup, one payload sent with a CE pulse, IRQ awaited, STATUS cleared (FLUSH_TX after MAX_RT), then PRX, the payload read, RX_DR cleared. One hart. 160 of 512

These protocols were not part of the design when the RTL was written. They use only existing instructions (shin as a pin test, shout, low/high/rel, tset/tsetr/twait, tgeth/tgetl for a polled timer, waitp.to, the host FIFO, ld/st on the data memory and the frame buffer); the RTL is unchanged. The device and the driver do not fit in one program together (671 words), so they run against models, not against each other. Checked in simulation only, not on a board.

There is no radio. The device hands each payload it transmits to the host as [length, bytes] and waits for a verdict byte when auto acknowledgement is on (non-zero: ACK received, 0: lost); the host sends a received packet as [pipe, length, bytes] and gets 1 (stored) or 0 (not received) back. Addresses are not sent over this "air": the host names the pipe.

Section and table numbers are those of the Nordic nRF24L01+ Product Specification v1.0 (September 2008).

Timing

Hart 0 polls CSN, SCK and CE with shin into a scratch register (Z = the pin is low), four ticks per poll, so the timer is free for Thce, Tstby2a and ARD while SPI runs. The emulation is slower than the chip in three places, which an MCU driving it must allow for:

  • The first STATUS bit is out about 1 us after the CSN fall (the idle loop and the transaction start), so the first SCK rise must come at least 2 us after the CSN fall (Tcc is 2 ns on the chip). nrf24_drv.pe waits two half periods.
  • After a CSN rise the device finishes the command (copies a W_REGISTER, moves a FIFO, recomputes STATUS and IRQ) for up to about 4 us; the next command's first SCK rise must come at least 5 us after the CSN rise. The tests use 3 us of CSN high plus 2 us of setup. IRQ goes high 3.3 us after the CSN rise of the STATUS write.
  • The command decode must end before the first rise of the next byte. At 500 kHz (50 ticks per period) the first data bit of an R_REGISTER is on MISO 17 clocks (0.34 us) before the SCK rise, so 500 kHz is near the limit; the chip itself runs to 10 MHz.

While the device hands a payload to the host or reads a host packet it does not watch the SPI pins (a few us when the host keeps up).

Limits

  • No radio: the host stands for the air, there is no air time, address matching or CRC on the air, and the device does not acknowledge towards the host.
  • Two FIFO levels instead of three; static payload width only.
  • SCK checked at 500 kHz, near the limit of the command decode; at least 2 us from CSN fall to the first SCK rise and 5 us from a CSN rise to the next command's first SCK rise (the chip needs nanoseconds).
  • The device firmware leaves one word free; the driver does not fit beside it, so there is no loopback on one chip.
  • Simulation only: no board, no gate-level run.
