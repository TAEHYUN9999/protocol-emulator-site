Found while the test modules were read for evidence_grades.md (2026-11-12, read-only, no simulation run). A gap here is a place where a test could pass although the firmware or the RTL were wrong: no control that can be rerun, an expectation taken from the firmware's own constants, an assertion that only logs, a loop that may run zero times. None of them is a known fault of the design; they say where a passing test proves less than its name suggests. One item has been fixed since: test_spec now fails when SPEC_TABLES selects no table of the protocol or when the judge reports none of the planted violations (test/controls_spec.sh). On 2026-11-13 (branch gaps_k) 62 more bullets were worked on, each marked at its end: 35 Fixed (the missing check is in the test), 13 Partly fixed, 14 Control added (a bullet that said the test has no control that can be rerun; the test is unchanged). The planted bugs are the 76 entries of test/controls_gaps.sh. In one run of that script on 2026-11-13 all of them were caught, and the 39 test modules whose files changed were run whole on the same tree: 214 tests, 213 pass, the one failure being the finding named next. The script counts any failing test as caught; that each planted bug fails at the added check and not elsewhere was looked at in the log when the control was written. One of the new checks failed on the firmware as it was then: the bus access time of j1708.pe when the host packet arrives during another node's last character. The firmware was changed on branch int5e and the check passes (j1708.md). The other bullets stand as written. A gap that the reading did not list was found by the static deadline check and closed on 2026-11-13: no test of test_can read the late flag, and it was set at every frame the chip sent; the five tests read it now (can.md, petime.md). How many tests read the late flag at all is counted in verification.md. The line numbers in the bullets are those of the files as they were read; test/test.py, test_can.py, test_mil1553.py, test_usb_gen.py, test_cec.py, test_dcc.py and test_onewire.py have had lines added since.

Each confirmed bullet was verified in the code by the review session that read the module (431 bullets); the author's session checked five of them again (test_spec tables, test_eth_rx jitter cases, test_eeprom24 at 100 kHz, test_qi short preamble, test_i3c SDA changes) and all five held. The "Unconfirmed" bullets (41) depend on files the reviewers did not read and are suspicions only.

Patterns across modules

  • Controls that cannot be rerun. Scripted controls exist for test_capture_deep, test_isa2, test_dual_role, test_eth, test_usb_fs, test_pel, test_eeprom93 (test/controls.sh), test_symmetry (controls_symmetry.sh), test_margin, test_inject, test_can_fc, test_can_dist and test_iss_diff (iss_mutants.py). For most other modules the control is a *_FW variable plus a table on the protocol page: the broken firmware copies, a runner and the logs are not in the repository.
  • Expectations that mirror the firmware. Timing read from the firmware's .equ constants or written into it by the test; one-chip loopbacks that check only that what was sent was received.
  • Assertions that cannot fail or only log. Sweeps where a few cases are asserted and the rest printed; values computed and logged without a comparison; docstrings naming a check the code does not make.
  • Tests that assert the chip's deviation from a standard, so a correct implementation would fail them (test_can_gen, test_can_fc, test_i2s).
  • A document claim without a test: verification.md says the Ethernet receiver fails at +-14 ns of jitter "as expected"; test/test_eth_rx.py has only the passing cases (+-8 and +-9 ns). Fixed on 2026-11-13: the +-14 ns case is asserted now.
