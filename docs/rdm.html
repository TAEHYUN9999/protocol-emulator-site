File Role Words
firmware/rdm.pe RDM (Remote Device Management, ANSI E1.20) responder on hart 0, on the DMX512 line of an RS-485 transceiver: break detection, RDM packets with start codes 0xCC 0x01, checksum, destination UID (own, all devices, own manufacturer), DISC_UNIQUE_BRANCH with the encoded response and no break, DISC_MUTE / DISC_UN_MUTE, GET DEVICE_INFO, GET/SET DMX_START_ADDRESS, GET/SET IDENTIFY_DEVICE with an ID pin, NACK_REASON for unknown PIDs, wrong command classes, bad data and sub-devices; responses start 200 us after the request; nothing is sent for broadcasts except discovery. 381 of 512

firmware/dmx.pe (controller and fixture) is unchanged; the responder is a separate file because the two together would not fit. No RTL change: tset/twait bit grid, shin.lsb, shout.lsb, waitp.to, ld/st on the frame buffer. Checked in simulation only, not on a board.

Pins

Constant Default Use
TX P0 to the DI pin of the RS-485 transceiver, high when idle
RX P1 from its RO pin
DE P2 driver enable: high only from the start of a response to the end of its last stop bit
ID P3 high while IDENTIFY_DEVICE is on

Data memory

Address Name Use
0x00-0x05 UID own UID, manufacturer ID first (host writes it)
0x06, 0x07 ADRH, ADRL DMX512 start address, 1 to 512 (host sets it; SET DMX_START_ADDRESS changes it)
0x08 IDENT identify, 0 or 1
0x09 MUTE discovery mute flag
0x0A RPKT RDM requests for this responder with a good checksum (broadcasts included)
0x0B RCSE requests with a wrong checksum
0x0C ROTH packets with another start code (DMX512 data)
0x0D RACK responses sent, discovery responses included
0x0E RNAK NACK_REASON responses
0x0F RFRM framing errors, inter-slot time-outs, lengths outside 24 to 60
0x20-0x9F frame buffer: request, then response
0xA0-0xB2 DINFO DEVICE_INFO template, 19 bytes; bytes 12 and 13 (start address) are taken from ADRH/ADRL when it is sent

Timing

One bit is 100 ticks (4 us, 250 kbit/s). The receiver samples each bit in its middle from the start edge and checks the first stop bit. At the middle of the last first stop bit of a request the responder starts a 16-bit timer of 5,150 ticks; the response (break, or the first start bit of a discovery response) begins when it ends: 200.9 us after the end of the last stop bit (176 us minimum). The processing in between (checks, building the response, its checksum) takes far less. The break is 45 bits (180 us), the mark after break 3 periods plus the set-up of the first slot (16 us), the slots have 2 stop bits and follow each other without a gap. DE rises with the break and falls in the clock the last stop bit ends.

Tests

test/test_rdm.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_rdm

The controller model is written from the sources above, not from the firmware: packet builder with length and checksum, response parser, DUB encoder and decoder, a line driver for breaks, marks after break, slots and gaps, and a recorder of TX and DE that finds the break, the mark after break and the slots, checks every edge on the 4 us grid and measures the turnaround.

Since 2026-11-13 (a gap of test_gaps.md) the search of test_rdm_discovery no longer stops at the first response it can decode: it halves the range 8 times, each probe must be answered exactly when the UID lies in its range, and the range must end as 7a0000000000..7affffffffff. The module then sends 16 packets and gets 7 discovery responses (counters pkt 16, resp 7). Control: with the early exit of the UID comparison removed (only the last UID byte decides) the test fails at the second probe, a response to 000000000000..3fffffffffff; the four DUB cases before the search pass with that bug.

Limits

  • Only the root device, the PIDs above and response type ACK or NACK_REASON: no ACK_TIMER, no queued messages, no SUPPORTED_PARAMETERS, SOFTWARE_VERSION_LABEL (required by E1.20) or other PIDs; the message count is always 0.
  • Requests with a message length above 60 are not taken (the parameter data of the supported PIDs is at most 12 bytes).
  • The responder does not take the DMX512 data (start code 0) itself; dmx.pe's fixture does that on another chip or after a change of pins.
  • The break threshold is fixed at 84 us; marks after break longer than 2.1 ms are not taken (E1.20 allows up to 1 s).
  • The DE timing around discovery responses (E1.20 has its own limits for them) was not available and is not checked beyond DE being high over the response.
  • Simulation only: no board, no gate-level run.
