The two older files and their tests (test/test.py test_i2c_master, test/test_device.py) are unchanged; i2c_target.pe keeps its board-checked timing. Each new firmware runs on hart 0 alone (CTRL = 1). Load it, write its settings with DATA_W (0x12) while both harts are stopped, soft reset, run. A setting left at 0 means the default; the firmware writes the default back, so DATA_R shows the values in use.

Specification: NXP UM10204, I2C-bus specification and user manual, Rev. 7.0, 1 October 2021. Section numbers below refer to it.

Pins

Pin Master Target
uio[0] (P0) SCL
uio[1] (P1) SDA
uio[6] (P6) SCL
uio[7] (P7) SDA
ui_in[7:3] N, the skew knob (0 to 31)

Both firmwares only pull a line low or release it (open drain); the lines need pull-up resistors (UM10204 7.1). The cocotb bench models released lines as pulled high and fails a test if the chip ever drives SCL or SDA high.

Master (firmware/i2c_master_gen.pe)

Settings (data memory)

Address Name Meaning Default
0x00, 0x01 T_LOW SCL LOW phase in ticks (40 ns), high byte first. Also the bus free time before a START (tBUF) and the SCL HIGH time before a repeated START (tSU;STA) 120
0x02, 0x03 T_HIGH SCL HIGH phase in ticks, counted from the rise the chip sees. Also tHD;STA and tSU;STO 122
0x04, 0x05 T_TO Clock stretching timeout: the longest wait for SCL to rise after the chip releases it, in ticks (65535 = 2.6 ms) 65535
0x08 to 0x0F Firmware work bytes

Times on the bus, measured in simulation (no stretching): tLOW = T_LOW + 2 ticks, tHIGH = T_HIGH + 7 ticks, tHD;STA = T_HIGH + 4, tSU;STO = T_HIGH + 7, tSU;STA = T_LOW + 9, tBUF ≥ T_LOW. The firmware changes SDA 2 to 3 ticks after its own SCL fall (tHD;DAT 80 to 120 ns; UM10204 asks for 0 ns or more, Table 11). Because tLOW ≥ 4.7 us also covers tSU;STA and tBUF, and tHIGH covers tHD;STA and tSU;STO, two values are enough for every Table 11 minimum.

Speed T_LOW, T_HIGH Measured fSCL (max) tLOW / tHIGH tVD;DAT (longest) Table 11 check
Standard-mode (default) 120, 122 99.6 kHz 4.88 / 5.16 us 0.76 us pass (Sm)
Fast-mode 34, 20 396.8 kHz 1.44 / 1.08 us 0.76 us pass (Fm)
Fast-mode Plus 11, 4 1000 kHz 0.52 / 0.44 us 13 us the minimums pass (Fm+); tVD;DAT is above the Fm+ maximum of 0.45 us
Fastest the firmware can clock 1, 1 1316 kHz 0.28 / 0.44 us 15 us data correct; tLOW is below the Fm+ minimum, so outside every mode

At Fast-mode Plus the first bit after a START comes from the command parsing code, which is longer than T_LOW: that LOW phase is longer (still legal) and the hart's late flag (STATUS byte 3 bit 3) is set. SDA changes late in that LOW phase, 13 us after the SCL fall (15 us at the fastest setting), so the controller does not meet the Fm+ tVD;DAT maximum of 0.45 us there; test_i2c_master_speeds judges tVD;DAT at Sm and Fm (0.76 us against 3.45 and 0.9 us) and only logs it at Fm+ and at the fastest setting. At 100 and 400 kHz the late flag stays clear. The numbers are those of the full regression of branch int5e (tree of 2f8eae4, 2026-11-13).

Commands (host FIFO)

Command Bytes Bus sequence
7-bit transaction 0x01, A, WL, RL, d1 .. dWL WL > 0: S, A+W, WL bytes. RL > 0: then Sr (S when WL = 0), A+R, RL bytes, the last one NACKed. Then P. WL = RL = 0: S, A+W, P
10-bit transaction 0x02, AH, AL, WL, RL, d1 .. dWL S, 11110 AH W, AL, WL bytes; RL > 0: Sr, 11110 AH R, RL bytes; P (3.1.11, Figures 14 and 15). AH = A9..A8, AL = A7..A0
Scan 0x03, F, L For each 7-bit address F to L: S, address+W, P
Bus clear 0x04 SCL low, nine clock pulses with SDA released, P (3.1.16). No bus free check first

WL and RL are 0 to 255. The write bytes may follow at any pace: while the FIFO is empty the chip holds SCL low (a master may), then gives a full T_LOW again so that tSU;DAT still holds. Read bytes go to the host as they arrive; a full output FIFO also holds SCL low. Command byte values are not checked further: 0 runs as 0x01, 5 and above as 0x04.

Replies (chip to host):

Command Reply
0x01, 0x02 RL data bytes, then STATUS. Bytes not read because of an error come as 0xFF
0x03 Each address that ACKed (0 to 127), then STATUS (bit 7 set, so the host reads until a byte ≥ 0x80)
0x04 STATUS
STATUS Meaning Bus action
0xA0 done P sent
0xA1 address NACK (first or, for 10-bit, second address byte, or the read address after Sr) P sent
0xA2 data NACK on a write byte P sent
0xA3 arbitration lost SDA and SCL released at once, no P (the winner owns the bus)
0xA4 clock stretching timeout (SCL not high within T_TO) SDA and SCL released
0xA5 bus busy: SDA low, or SCL low within T_LOW, before the START nothing sent

After any error the write bytes still in the FIFO are read and dropped, so the next command is in step.

Bus behavior

  • START only on a free bus: SDA high, SCL high for T_LOW, SDA still high; else 0xA5. There is no START/STOP monitor, so another master that holds both lines high for longer than T_LOW in the middle of its transfer is not seen as busy.
  • Clock synchronization (3.1.7): the HIGH phase ends after T_HIGH or as soon as SCL is low, whichever comes first (another master pulled it low); the LOW phase counts from the chip's own pull, and the release waits for SCL to go high, so a slower master or a stretching target keeps SCL low as long as it wants. Clock stretching (3.1.9) at bit and byte level is followed the same way, up to T_TO.
  • Arbitration (3.1.8): on every bit the chip sends (address bytes, write data), SDA is read in the HIGH phase; when the chip released SDA but reads 0, it stops driving both lines and reports 0xA3. It is not checked on bits it reads, on its ACK/NACK bits or on Sr and P (3.1.8 calls those cases undefined). A repeated START also checks that SDA is still high before pulling it low.
  • Device ID (3.1.17) and other combined formats with one write and one read part fit the 0x01 command (for example device ID = 0x01, 0x7C, 1, 3, target address byte); this use was not tested.

Target (firmware/i2c_target_gen.pe)

Simulation only, not checked on a board. The board-checked target is firmware/i2c_target.pe.

Settings (data memory)

Address Name Meaning Default
0x00 ADDR Own 7-bit address 0x42
0x01 GC Nonzero: answer the general call address 0 (ignore)
0x02 STR Nonzero: clock stretching 0 (never touches SCL)
0x03 STEP Skew step in ticks, 2 or more 4
0x04 TSU Ticks SDA is held before a stretched SCL is released 32 (1.28 us)
0x05 PTR Register pointer. The host may preset it; the firmware keeps it current 0
0x06 Own address byte, write form (firmware work byte)
0x10 to 0x1F Registers 0 to 15. Register index = pointer mod 16

The host presets registers with DATA_W before the run and reads them with DATA_R at any time, also while a master writes them.

Protocol

  • Write: S, ADDR+W, register address byte, data bytes. Each data byte goes to register (pointer mod 16) and the pointer counts up.
  • Read: S, ADDR+R, then registers from the pointer on, while the master ACKs. With a register address first: S, ADDR+W, register address, Sr, ADDR+R, data.
  • Another address gets no ACK. A START or STOP inside a byte the target receives ends the transfer (3.1.10 note 4).
  • General call (3.1.13), only with GC set. The address byte 0x00 is ACKed, then the second byte:
Second byte Target
0x06 ACK, software reset (3.1.14): pointer = 0, given to the host. Further bytes: no ACK
0x04 ACK, given to the host (the target has no hardware address part to take in). Further bytes: no ACK
odd (hardware general call, bit B = 1) ACK, the byte (master address) and every following data byte go to the host, each ACKed
0x00 and other even codes no ACK (3.1.13: "devices must ignore them")

General call bytes go to the host output FIFO (4 bytes). When it is full, the byte gets no ACK; with STR set the target holds SCL low until the host has read a byte (measured: SCL held 0.28 ms by a host that started reading 0.4 ms after the transfer began). Header 0x01 (START byte, 3.1.15) is never ACKed.

Clock stretching (STR)

At every SCL fall after which the target changes SDA (ACK, release after ACK, each data bit it sends, release for the master's ACK), the target pulls SCL low as soon as it sees the fall, waits the skew delay, decides (address, general call, FIFO), changes SDA, keeps SDA stable for TSU and releases SCL. After the 8th bit of an address it pulls SCL low before it knows whether the address is its own and lets go again if not. With TSU = 32 ticks a stretched release meets the 1250 ns set-up time that UM10204 Table 11 note 4 asks of a stretching device on a Standard-mode bus. Received bytes are stored during the 9th clock, after the ACK, so storing never delays the ACK.

Skew knob

N = ui_in[7:3] is read at every SCL fall where the target changes SDA. That change comes N x STEP ticks later than with N = 0 (measured exact for STEP 4 and 6, N up to 31 and 20, both hart phases). Without stretching a large N moves SDA past the next SCL rise, which is what the knob is for (find where a master samples). With stretching the master waits instead. Unlike i2c_target.pe, N = 0 adds no STEP delay, so the N = 0 response is faster: SCL fall (at the pin) to SDA change (at the pin) 410 to 830 ns, against 450 to 910 ns for i2c_target.pe (test_device.py test_i2c_target_skew); both measured with SCL LOW = HIGH = 6.4 us and the host changing SDA 160 ns after its SCL fall.

Waiting on SCL and SDA together (i2c_target_gen_m.pe, int6)

While SCL is high, i2c_target_gen.pe polls SCL and SDA in turn (waitp.to with an expired timer, a loop of five instructions, 10 clocks) to tell the end of the bit from a repeated START or a STOP. i2c_target_gen_m.pe sleeps in one waitm.ne on both pins instead and reads SCL with shin when it wakes (two instructions to the end of a bit, as the original after its poll); the rest of the firmware is the same. With it every target test of test/test_i2c.py passes (I2C_TARGET_FW=i2c_target_gen_m.pe, 6 of 6). A first form read the pins with rdp and tested the SCL bit, three instructions more: the general call test then failed on tSU;DAT (SDA 60 ns before the SCL rise at Fast-mode), because that path already needs about 900 ns from the eighth SCL fall to its ACK.

test_i2c_target_sr_hold writes two registers and reads them back through a repeated START at LOW and HIGH of 500 ns with stretching on. The target enters its receive loop when it releases SCL, so the SDA fall of the Sr comes tSU;STA after that; tSU;STA is swept over 260 to 450 ns in 10 ns steps (one polling loop) for every hold [measured, RTL, Icarus 11]:

Firmware Hold of the Sr read right at every set-up First failure
i2c_target_gen.pe 300, 260, 200, 160, 120 ns 100 ns at tSU;STA 320 ns
i2c_target_gen_m.pe 300 down to 80 ns 60 ns at tSU;STA 260 ns

UM10204 Table 11 asks tHD;STA of at least 260 ns in Fast-mode Plus, so both are inside it; the waitm form takes about 40 ns off the worst case and no longer depends on where the SDA change falls in a loop.

Tests

test/test_i2c.py, run as COCOTB_TEST_MODULES=test_i2c from a private build folder. The models are written from UM10204, not from the firmware:

  • Target: decodes the bus edge by edge (3.1.4 START/STOP, 3.1.5 bytes, 3.1.6 ACK), 7-bit or 10-bit address (3.1.11, including the rule that only the target addressed before an Sr answers 11110XX R), register pointer with auto increment, optional byte-level and bit-level stretching (3.1.9), optional NACK after k bytes.
  • Controller: a master that counts its own LOW and HIGH periods, waits while SCL is held low, follows an earlier SCL fall (3.1.7), checks arbitration on every bit it sends (3.1.8) and can join another master's START in the same moment. It is the second master that wins arbitration, and the host for the target tests.
  • Monitor: records every SCL/SDA edge, decodes S, Sr, P and bytes with ACK/NACK, and checks fSCL, tLOW, tHIGH, tHD;STA, tSU;STA, tSU;STO, tBUF and tSU;DAT against Table 11 for the mode under test.
