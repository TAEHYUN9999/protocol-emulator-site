File Role Words
firmware/sdspi.pe An SD memory card seen from an SPI host: SPI mode entry with CMD0, CMD8 (R7), CMD55 + ACMD41 initialisation, CMD58 (R3, OCR with CCS), CMD59 CRC checking, CMD17 block read and CMD24 block write with CRC7, CRC16, data token, data response and busy. Hart 0 runs the bus, hart 1 times the programming busy period. 335 of 512 (hart 1 starts at word 325)

This protocol was not part of the design when the RTL was written. It uses only existing instructions (shout/shin, waitp.to, tset/twait, the CRC unit for both CRC7 and CRC16, ld/st on the data memory and the frame buffer); the RTL is unchanged. Checked in simulation only, not on a board.

Section numbers are those of the SD Specifications Part 1 Physical Layer Simplified Specification, Version 9.10 (December 2023), downloaded from sdcard.org.

The card answers one byte after the command: one FFh byte (NCR = 1), then R1. The SPI timing section 7.5 is removed from the simplified edition; NCR of 0 to 8 bytes is taken from a secondary source (ChaN, "How to Use MMC/SDC").

Block contents: block 0 holds a 64-byte window in its first bytes; the rest of every block reads 00h and is not stored. The window is double buffered in the frame buffer (0x20 and 0x60; ACT at 0x09 says which one is current), so a block rejected for its CRC changes nothing. Ethernet and the capture cannot run with this firmware.

Not implemented: SDSC byte addressing and CMD16, multiple block commands (CMD18, CMD25, CMD12), CMD9/CMD10 (CSD, CID), CMD13 and ACMD13 (status), erase, write protection, lock/unlock, data error tokens, the SD bus mode.

Pins

Constant Default Use
SCK P2 from the host
DI P3 host to card, taken at each SCK rise
DO P4 card to host, changed after each SCK fall, push-pull while CS is low, released while CS is high
CS P5 active low

The pins are those of spi_device.pe and w25q.pe. SPI mode 0, MSB first.

Timing

Every SCK wait times out after TMO = 32 ticks and then looks at CS once, so CS high ends a transfer at any point. The decode of a command (CRC, index, R1) runs between the eighth rise of the CRC byte and the first rise of the next byte, one SCK period: 125 ticks at 400 kHz. The longest decode, ACMD41, takes about 52 ticks, so the limit is near 480 kHz: a run of the same initialisation at 500 kHz (50 ticks per period) lost the ACMD41 answer. The host must keep CS high for more than TMO ticks to end a transfer.

Tests

test/test_sdspi.py (cocotb). The host model is written from the simplified specification (sections in the module docstring): CRC7 and CRC16 checked against the examples of 4.5, commands built from Table 7-1, the initialisation flow of Figure 7-2, R1/R3/R7 and the data tokens. It records every DO change and fails on any DO change while SCK is high. Only the host interface above is taken from this page. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T COCOTB_TESTCASE=<test> make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_sdspi

Limits

  • One block size (512) and block addressing; only the first 64 bytes of block 0 are stored.
  • SCK up to 400 kHz (checked); 500 kHz fails at ACMD41 because the command decode does not fit one SCK period. The identification clock fOD is at most 400 kHz anyway, but a host that speeds up after initialisation must stay at 400 kHz.
  • NCR is always 1 byte, the read access time always one FFh byte.
  • Simulation only: no board, no gate-level run.
