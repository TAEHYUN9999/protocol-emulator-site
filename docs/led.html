File Role Words
firmware/apa102.pe Drives a chain of APA102 LEDs on a clock and a data line: the host sends brightness, blue, green and red per LED; the chip sends the start frame (32 zero bits), one LED frame per LED (flag 111, 5-bit brightness, blue, green, red) and the end frame (32 one bits), MSB first, data set while the clock is low. 94 of 512 (one hart)
firmware/ws2812.pe (unchanged) Drives SK6812 RGBW LEDs as it is: the host sends 4 bytes per LED instead of 3. The default 320 ns slot meets every SK6812RGBW window. 36 of 512

No RTL change. Checked in simulation only.

Sources

Document Original or secondary Used for
APA ELECTRONIC, APA102C data sheet (2018-10-11) original (a copy hosted by LCD-module.de) "Communication protocol and timing": start frame of 32 bits 0 entered at the rising edge of CIN, DIN set up before CIN; LED frame: flag 111, brightness D4..D0, then blue, green, red, high bit first; recommended working parameters: data clock 0 to 5 MHz, clock high and low width above 30 ns, data setup above 10 ns
APA102 end frame: 32 bits of 1 secondary, two public descriptions that agree (the Bus Pirate APA102/SK9822 page; Tim's "Understanding the APA102 superled" analysis, which also shows that a chain needs n/2 more clock edges after the last LED frame) the end frame; 32 ones cover the n/2 extra edges of up to 64 LEDs
OPSCO SK6812RGBW specification, Rev. 01 original (Adafruit product file) T0H 0.3 us, T1H 0.6 us, T0L 0.9 us, T1L 0.6 us, each +-0.15 us; Trst 80 us or more; section 13: 32 bits per LED sent R7 first, in the order R, G, B, W

The SK6812RGBW specification lists the bytes as R, G, B, W; libraries for these parts commonly send G, R, B, W. ws2812.pe sends the bytes in the order the host gives them, so the host decides; the test follows the specification.

APA102 (apa102.pe)

Pin Use
P0 CKI, clock to the first LED (low between frames)
P1 SDI, data (low between frames)

Host to chip (FIFO): n (1 to 32; 0 and values above 32 are ignored), then 4 bytes per LED, first LED first: brightness (the low 5 bits are used), blue, green, red. The chip answers n when the frame has been sent. The bytes are stored first (start frame at data memory 0x1C-0x1F, LED frames from the frame buffer 0x20, end frame right after them, for n = 32 in data memory 0xA0-0xA3), so the clock does not depend on the host.

Data memory 0x00 HALF: ticks per clock half period (DATA_W before the run; 0 = 5 = 2.5 MHz). Each bit is a falling edge with the bit on SDI and a rising edge HALF ticks later; the 8 bits of a byte are written out, and the next byte is fetched in the low half of bit 0, so no half holds more than 4 instructions: HALF = 5 is the shortest that keeps the late flag 0.

Data sheet Firmware (HALF = 5)

data setup > 10 ns 160 ns (SDI changes one tick after the falling edge)

Tests

test/test_led.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_led

The models are written from the data sheets: the APA102 chain takes the bits at the CKI rising edges, wants the 32-bit start frame and gives LED k the k-th LED frame; the SK6812 decoder classifies each high time with the T0H/T1H windows, checks every low against T0L/T1L, ends a frame at a low of 80 us or more, and gives LED k bits 32k to 32k+31 as R, G, B, W.

Limits

  • APA102: 32 LEDs per frame (the frame buffer), one global clock rate per run, no LED-side (receiving) emulation.
  • SK6812 RGBW: 32 LEDs (128 bytes) per frame, as ws2812.pe; no LED-side emulation.
