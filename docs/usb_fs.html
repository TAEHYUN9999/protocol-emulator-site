USB 2.0 full speed (12 Mb/s) needs 4.17 clocks per bit at the fixed 50 MHz chip clock, about two hart ticks, so the bit-level work (NRZI, bit stuffing, SYNC, EOP, clock recovery, CRC) is done by a hardware line unit and the firmware handles whole packets. The unit takes the place of the Ethernet transmitter and receiver when ETH_CFG bit 4 is set: the same frame buffer, the same host commands (ETH_TX, ETH_RXC, ETH_RXS) and the same hart instructions (etx, erxon, erxw, erxl). No instruction and no host command was added, so tools/peasm.py and the reference model tools/peiss are unchanged.

firmware/usb_fs.pe is a full-speed HID device on that unit: it answers every request of a Linux-like enumeration within the bus turnaround and sends interrupt IN reports. Simulation only: it has not been on a board, and no real host has enumerated it. What a board test needs is in Demonstration with a Linux host.

Spec references are to USB 2.0 (usb_20.pdf from usb.org, the 2025-06-03 package used for docs/usb_ls.md).

1. Bit timing at 50 MHz

One full-speed bit is 83.33 ns, 4.167 clocks. The chip clock stays at 50 MHz (10BASE-T needs 5 clocks per bit), so every edge the chip sends is on a clock grid and off the ideal USB grid by a quantization error.

Source jitter: what the spec asks and what the grid gives

USB 2.0 7.1.13.1.1 measures data jitter as the time between transitions minus N x TPERIOD. Table 7-9 limits it for a full-speed source to TDJ1 = +-3.5 ns between consecutive transitions and TDJ2 = +-4 ns between paired transitions (J-to-K to the next J-to-K), frequency tolerance included; TFDEOP = -2 to +5 ns from the last transition to the SE0 of the EOP. A receiver must decode transitions with TJR1 = +-18.5 ns (consecutive) and TJR2 = +-9 ns (paired) of jitter (Table 7-9; Table 7-4 derives these from the source plus five hubs at 3.0 / 1.0 ns each), within a quarter bit of the nominal edge (7.1.15.1).

Output grid Bit lengths Edge error, peak to peak Any interval vs N bits vs source TDJ1 / TDJ2 vs receiver TJR1 / TJR2
Rising edges only (20 ns) 80, 100 ns (4 or 5 clocks, 25 clocks per 6 bits) 16.67 ns up to 16.67 ns exceeds both 16.67 < 18.5, but 16.67 > 9: paired fails
Both edges (10 ns) 90, 80, 80 ns (25 half clocks per 3 bits) 6.67 ns up to 6.67 ns exceeds by 3.17 / 2.67 ns 6.67 < 18.5 and 6.67 < 9

(test_usb_fs_model computes the second row from the bit pattern. The first row is the same calculation on a 20 ns grid, and the planted bug usb_tx_rising_edge_only (section 7) measures exactly 16.67 ns at the pins. Frequency adds nothing: 250 ns per 3 bits is exactly 12.000 Mb/s, so the rate error is the clock crystal's, a few tens of ppm against +-2500 ppm of TFDRATE, 7.1.11.)

Decision: send on both clock edges. The rising-edge-only output is outside the receiver's paired-transition tolerance (16.67 ns against TJR2 9 ns), so a compliant host would not be required to decode it. With both edges every transition is 0, 3.33 or 6.67 ns after the ideal grid. That is outside the source limits of Table 7-9 (TDJ1 3.5 ns, TDJ2 4 ns, TFDEOP -2 to +5 ns) by at most 3.2 ns, so the chip is not a compliant full-speed source. It is inside what every compliant receiver must accept (TJR1 18.5 ns, TJR2 9 ns) with 11.8 ns and 2.3 ns to spare. In the budget of Table 7-4 the excess (6.67 - 4.0 = 2.67 ns paired) uses the allowance of three hubs (1.0 ns each), so the chip should be connected directly to the host or through at most two hubs (6.67 + 2 x 1.0 = 8.67 ns <= 9 ns).

Other ways considered:

  • 48 MHz clock (4 clocks per bit, no quantization). Rejected: the clock is fixed at 50 MHz for 10BASE-T and the timing of every other firmware.
  • Finer steps from delay lines (buffer chains on the pins): their delay changes with process, voltage and temperature, and Tiny Tapeout gives no way to calibrate them. Rejected at the time; since the chip has delay lines that calibrate themselves (dly.md), the fine edges below use them.
  • External transceiver: a USB transceiver chip (VP/VM/OE type) does not retime the data, so the quantization stays; it only helps the electrical side (see section 3).

How the edges are made

  • A 5-bit phase ph counts in thirds of a half clock (3.33 ns), 0 to 24; each half clock adds 3. A bit starts in the half clock where the phase wraps, which gives the 9, 8, 8 pattern.
  • Each pin is a ^ b: a changes only on rising edges, b only on falling edges, so a pin never shows a glitch (the same structure as TD+/TD- in pe_eth_tx.v). At each rising edge the unit computes the line state of both halves of the next clock.
  • The EOP's SE0 starts on the grid; its phase is then set as if it started at phase 0, so the SE0 is always 17 half clocks, 170 ns (TFEOPT 160 to 175 ns). Without this it would be 160 ns for one packet in three, at the lower limit.
  • The pins are enabled with J one clock before the first K; after the EOP's SE0 the unit drives J for 80 ns and releases the pins at the next rising edge, keeping the output value J so that the data never changes in the clock the driver turns off.
  • Outside USB mode the select of the top level passes the core's pad registers for P0 and P1. In the int2 netlist (revisions) synthesis built that select with two more gates on the output path than on the enable path, and a push-pull high from release then showed a zero-width low pulse at gate level; since branch int3 the core's pad registers never change both bits of a pin at one edge in that direction, so the result no longer depends on how the select is built (dual_role.md).

Measured at the pins over 56 packets of the enumeration test (1,762 transitions): consecutive and paired interval errors at most 6.667 ns, every edge 0 to 6.667 ns after the grid of its packet's SOP, SE0 170.0 ns in every packet, last transition to SE0 -6.67 to +6.67 ns.

Fine edges with the delay lines (branch int5 part D2)

The quantization error is known for every transition: its bit boundary is 0, 3.33 or 6.67 ns after the ideal grid, and the phase counter says which. Delaying a transition by 6.67, 3.33 or 0 ns puts all of them on one grid, 6.67 ns after the ideal one. The delay lines of P0 and P1 (dly.md) can do that, and the calibration value says how many taps 3.33 and 6.67 ns are on this chip at this moment.

  • Hardware. pe_usb_fs gives a 2-bit tsel, the delay the next transition needs (0, 1 or 2 thirds of a half clock). With bit 6 of delay line register 0 set and USB selected, the output and enable lines of P0 and P1 both take one tap, chosen by tsel: 0, the tap of register 0, or the tap of register 1. The enable bit of register 0 turns the four lines on. A firmware that leaves bit 6 clear gets the chip as it was.
  • Firmware. It reads dlyr.cal and writes the taps: (2 cal + 7) / 12 for 3.33 ns into register 0 with bits 7 and 6, (2 cal + 4) / 6 for 6.67 ns into register 1 (cal + 0.5 over 6 and over 3, rounded; two subtraction loops, 21 words, FINE_PRE in test/test_usb_fs.py). Out of range, it leaves the lines off.
  • When the tap changes. The lines switch at the third rising edge after the clock of a bit boundary: the boundary's transition entered them 40 ns (rising edge) or 30 ns (falling edge) before and has left (at most 6.67 ns of taps and four multiplexer cells), and the next transition cannot enter before 40 ns later (a bit is at least 80 ns). The tap select comes from flip-flops, and the multiplexers switch between taps that hold the same level. The lines hold the 6.67 ns tap between packets, which is what the first K needs.
  • EOP. Both edges of the SE0 take the delay of the first, so the SE0 is 170 ns as before.

Measured in RTL simulation, where a tap is a delay model (test_usb_fs_fine_edges, test_usb_fs_fine_enumeration): with taps of 770, 1,188 and 536 ps (typical, slow and fast corner of the liberty) the worst consecutive and paired interval errors are 0.517, 0.461 and 0.419 ns, against 6.667 ns without, and the SE0 is 170.0 ns. With the firmware lines in front of usb_fs.pe, over the 54 packets of the enumeration (1,710 transitions): 0.517 ns consecutive and paired (TDJ1 3.5 ns, TDJ2 4 ns), last transition to SE0 -0.26 to +0.52 ns (TFDEOP -2 to +5 ns), turnaround 4.24 to 5.96 bit times. What is left is the tap quantization.

2. Receiver: clock recovery and tolerance

  • D+ and D- pass through the two-flip-flop synchronizer of the protocol pins (rising edge) and a second one on the falling edge (project.v, as for the Ethernet receive line), so every clock brings two samples 10 ns apart: rx_a, then rx_b.
  • The same phase counter runs while receiving. A change of D+ sets the phase of the sample that shows it to 2 (the edge was 0 to 10 ns before). The one sample of each bit whose phase is in [12, 15) decides the bit: 40 ns after the edge sample for the first bit after an edge, then every 8 or 9 samples. J/K is read from D+ (a skew between D+ and D- at a transition, up to 14 ns TFST, never reaches a decision sample), SE0 from both lines.
  • A decision is at most 8.3 ns from the middle of its bit when the edges come on time, so an edge may move by about 33 ns before a bit is lost (a quarter bit is 20.8 ns, 7.1.15.1). The phase restarts at every edge, and at most seven bit times pass without one (six 1s and a stuffed 0), so a rate error of +-0.25 % moves the last decision by 1.5 ns.
  • SYNC: in HUNT, the 0 bits (J/K changes) are counted; a 1 bit in K after at least three of them ends SYNC (KJKJKJKK, 7.1.10, has seven). Three allows the receiver to be armed up to four bits into a SYNC, which the firmware needs after a SETUP or OUT token.
  • Stuffing: the last 1 of SYNC counts. After six 1s the next bit must be a 0 and is dropped; a 1 there is a stuffing error, and the rest of the packet up to the EOP is ignored (7.1.9.1).
  • EOP: the SE0 seen at a bit decision ends the packet. From J (D+ falls) that is 40 to 50 ns after the edge; from K it is the next decision. An SE0 of 82 ns (TFEOPR) is found. Bits after the last whole byte (dribble, 7.1.9.1) are ignored, because the CRC residues are checked at each byte boundary.

Measured (test_usb_fs_rate_jitter, test_usb_fs_rx_margin): enumeration and reports pass with the host at +0.25 % and -0.25 % (TFDRATE) and with duty-cycle distortion of +-9.25 ns (every J-to-K edge 9.25 ns late and every K-to-J edge 9.25 ns early, so consecutive transitions are 18.5 ns off: TJR1), with uniform +-4.5 ns on every edge (paired transitions up to 9 ns off: TJR2), and with +-7 ns distortion plus +-2.25 ns uniform. The margin sweep on the receiver alone decodes up to +-15 ns of distortion (30 ns between consecutive transitions) at both rates and fails at +-17.5 ns; uniform jitter on every edge passes to +-20 ns at -0.25 % and +-17.5 ns at +0.25 % (3 seeds of 3 packets per point; random edges rarely line up for the worst case).

3. Pins and electrical side

Pin Use while ETH_CFG bit 4 is set
uio[0] (P0) D+ (line unit, bidirectional)
uio[1] (P1) D- (line unit, bidirectional)
uio[2] (P2) firmware: drives the 1.5 kOhm D+ pull-up (high = attached)

While USB is selected the line unit owns P0 and P1: their output and enable come from the unit, and the harts' pin registers for them have no effect (the harts still read both lines, as the firmware does to recognize a bus reset). The other six protocol pins work as before. With bit 4 clear (the reset value) nothing changes.

Decision: D+ and D- directly on two uio pins, not an external transceiver interface. D+ and D- must be driven and read on the same wire, and only uio pins are bidirectional. The IHP IO cells run at 3.3 V (iovdd 3.3 V in the PDK's IO library), the level full speed uses (VOH 2.8 V or more), and the single-ended inputs give J, K and SE0 directly; the same two pins are used by the low-speed firmware (docs/usb_ls.md), so one board wiring serves both. An external transceiver (VP/VM/OE type) would give a differential receiver, a defined driver impedance and edge rate, but needs about six fixed-direction pins (data and SE0 out, enable, receive, and the two single-ended inputs) of the eight protocol pins and does not reduce the timing quantization. What the direct connection leaves to the board: a series resistor per line so that the driver impedance is near ZDRV 28 to 44 Ohm (Table 7-9), the 1.5 kOhm pull-up, and edge rates of 4 to 20 ns (TFR, TFF); the pad drive strength in the Tiny Tapeout pad ring is not known here, so these are to be measured on the board.

4. Interface

Host commands (ETH_CFG bit 4 set)

Command Use
ETH_CFG 0x42 bit 4: USB line unit instead of Ethernet. In USB mode bit 2 appends the CRC16 to DATA packets, bit 3 drops SOF packets. A device uses 0x1C
ETH_TX 0x41 send a packet of n bytes (1 to 96) from frame byte 32
ETH_RXC 0x43 1 arms the receiver for one packet, 0 cancels
ETH_RXS 0x44 {receiving, done, ok, 0, 0, len[10:8]}, len[7:0]
ETH_W 0x40, CAP_R 0x32 the frame buffer: received packet at words 0 to 15, packet to send from word 16

Change bit 4 only while both units are idle (after a soft reset or ETH_RXC 0). In USB mode the Ethernet transmitter and receiver cannot start; with bit 4 clear the USB unit cannot.

Hart instructions

Instruction USB mode
erxon arm the receiver for one packet (waits while the transmitter is busy)
erxw wait until the receiver has stopped; Z=0 if the packet is good
erxl rd received length in bytes, PID and CRC included (255 if longer)
etx rs rs bit 7 = 0: send rs bytes from frame byte 32 (0x40); bit 7 = 1: send the handshake PID {~rs[3:0], rs[3:0]} without touching the buffer: 0x82 ACK, 0x8A NAK, 0x8E STALL

A packet is good when its PID check passes and: a token (PID[1:0] = 01) has 3 bytes and a good CRC5; a DATA packet (11) has at least 3 bytes and a good CRC16; a handshake (10) has 1 byte. Anything else (special PIDs, stuffing error, short packets) is not good. In HUNT, an SE0 that lasts 32 bit decisions (2.67 us, more than TDETRST 2.5 us, 7.1.7.5) also stops the receiver: done, length 0, not good; the firmware then reads SE0 on the pins and takes it as a bus reset.

Frame buffer and the two directions

Frame bytes ld/st Use
0 to 31 0x20 to 0x3F the received packet, PID first (the first 32 bytes; len counts all)
32 to 127 0x40 to 0x9F the packet to send, PID first (up to 96 bytes, CRC16 not included)

The receiver writes only bytes 0 to 31, so in USB mode stores (st) and ETH_W to the frame buffer are allowed while the receiver is armed, unlike Ethernet: the firmware prepares its next packet while it listens. If a store or an ETH_W word takes the buffer's write port in the clock the receiver wants it, the receiver's word waits one clock (the next byte comes 32 clocks later at the earliest); test_usb_fs_store_while_rx stores on nearly every tick while a 23-byte packet arrives. Stores are still dropped while the transmitter is busy, as for Ethernet, and the capture cannot be armed while the receiver is.

CRC: why in hardware

Both CRCs are checked by the unit, and the CRC16 of a DATA packet is appended by it. A device must answer within 6.5 bit times (TRSPIPD1, 7.1.18.1) of the host's EOP: 542 ns, 13.5 hart ticks. Checking a CRC16 in firmware takes two ticks per byte (ld and crc.lsb), 20 ticks for the 8 data and 2 CRC bytes of a SETUP's DATA0 before the answer is even decided; the firmware sends its ACK 10 ticks after erxw returns. The receive check costs a 5-bit and a 16-bit register; the 16-bit register is shared with the transmitter, which never runs at the same time. The per-hart CRC unit stays free for firmware that needs other CRCs (for example the CRC5 of tokens it sends as a host).

SOF drop

With bit 3 set, a good SOF token is not reported: the receiver hunts for the next packet at once. The host sends an SOF every millisecond, and a token for the device may follow it after two bit times (TIPD). A firmware that is preparing a packet when an SOF ends would otherwise re-arm late and miss the SYNC of that token.

5. Ethernet and USB

The two share the frame buffer, the busy and receive status, the host commands and the instructions, so only one works at a time, chosen by ETH_CFG bit 4. The Ethernet pins (ui[7], uo[6], uo[7]) are not touched by USB mode; ETH_CFG bit 0 still controls TD+/TD-, which stay low because the Ethernet transmitter cannot start. A soft reset stops both units at once and releases D+ and D- in the next clock (test_usb_fs_line_tx, and the POR proof, section 8).

6. Device firmware (firmware/usb_fs.pe)

One hart (hart 0), 426 of 512 words, of which 120 write the descriptors into memory at start. The host loads it, sets ETH_CFG to 0x1C and starts hart 0; the firmware writes its descriptors, drives P2 high (attach) and waits for the bus reset.

Item Value
Device VID 0x1209 PID 0x0001 (pid.codes test PID), bcdUSB 2.00, full speed, bMaxPacketSize0 8, no strings
Configuration 1, bus powered, 100 mA; one HID interface (class 3, no boot protocol)
HID report descriptor of 21 bytes: vendor usage page 0xFF00, one input report of 2 bytes
Endpoint 1 interrupt IN, 2 bytes, every 10 ms: {sequence number, gpi} (gpi = ui[7:3] when the report was prepared)
Requests GET_DESCRIPTOR (device, configuration, HID report), SET_ADDRESS, SET_CONFIGURATION (0 or 1), GET_CONFIGURATION, GET_STATUS; any other request is answered with STALL in its data or status stage (9.2.7), for example SET_IDLE and GET_DESCRIPTOR(string)

How it meets the turnaround

  • The answer to the next IN of each endpoint is ready before the token comes: r3 (endpoint 0) and r4 (endpoint 1) hold the etx operand, a packet length or 0x8A/0x8E. The packet itself is already in the buffer from byte 32.
  • Ticks from erxw returning to etx: IN to endpoint 0 11, IN to endpoint 1 13, DATA0 10, DATA1 12. Measured from the host's SE0-to-J to the chip's first K (test_usb_fs_enumeration): SETUP ACK 4.20 to 4.28 bit times, DATA to IN on endpoint 0 4.72 to 4.92, ACK of the status OUT 5.16 to 5.52, STALL 4.92 (to IN) and 5.20 (to OUT data), report on endpoint 1 5.64 to 5.88, NAK on endpoint 1 5.88. All are inside 2 to 6.5 bit times (TIPD, TRSPIPD1). The receiver reports the EOP about one bit before the SE0-to-J, which is time the firmware gets for free.
  • Everything that is not an IN or a DATA re-arms the receiver within 10 ticks, so a DATA that follows a SETUP or OUT two bit times later is not missed. The setup request is decoded while the ACK is being sent (stores then go to the data memory, which is not blocked); the first data packet is written into the buffer after erxon, while listening.
  • One packet buffer serves both endpoints: during a control transfer it holds the endpoint 0 packet and endpoint 1 answers NAK; afterwards the report is put back. Data toggles: endpoint 0 starts every data and status stage with DATA1; endpoint 1 starts with DATA0 after SET_CONFIGURATION; a packet not acknowledged is sent again with the same toggle, and PTR/REM move once per packet (ADV), so a lost ACK cannot skip data.
  • SET_ADDRESS takes effect when the host acknowledges the status packet (9.4.6). If that ACK is lost, the next SETUP to the new address commits it.
  • Bus reset: the receiver stops after 2.67 us of SE0; with no byte received and SE0 on both pins, the firmware returns to address 0, unconfigured, and waits for J.

Memory

Address Content
0x00 to 0x0C state: pending handshake, endpoint waiting for ACK, data pointer, bytes left, last packet size, toggles, pending action and value, configuration, report sequence, SETUP flag, advance flag
0x0E to 0x1F device descriptor (its bytes 4 and 5 serve as the two zero bytes of GET_STATUS)

All of it is reached with absolute ld/st (0 to 127), so writing the descriptors costs two words per byte.

8. Formal (formal/run_formal_usb_fs.sh)

  • Inside pe_usb_fs.v (ifdef FORMAL), with every input free: the two directions never overlap; receive writes only to words 0 to 15; done only when stopped, ok only with done; a cancel or a soft reset stops the receiver at once and a soft reset the transmitter; while sending, never more than six 1s on the line (the stuffing rule, checked on the line states, and the stuffing counter equals that run); every bit is 8 or 9 half clocks, any three bits are exactly 25 (12.000 Mb/s), the EOP's SE0 is 17 half clocks. k-induction (unbounded) and BMC from reset.
  • Loopback (formal/pe_usb_fs_loop.sv): one copy sends, a second receives its pin values. For any 2-byte packet and any handshake PID, and for a DATA PID with one byte and the CRC16 appended, the receiver stops with the bytes sent, the right length and the right ok, within 130 (220) clocks. ABC bmc3 to 135 (220) clocks.
  • Fine edges of part D2 (ifdef FORMAL in pe_usb_fs.v, added after the panel review of 2026-11-14): between packets tsel is 2; at every boundary tsel is the delay that boundary's lateness needs (2 minus lat thirds of a half clock), and the SE0's second edge keeps the first edge's delay; and in time, the delay lines take tsel one clock later (ftap_q in pe_dly), so a line switches with no transition of D+, D- or their enable in the clock before it and the two clocks from it: the last transition is at least 1.5 clocks before the switch and the next one 2 clocks (40 ns) after it. A soft reset, which ends a packet at once, is left out. (A stricter form, no transition in the clock before tsel itself changes, is false by design: the boundary's transition is in that clock, and a BMC of it fails at once.)
  • Planted bugs: 10 for the module properties (3 of them on the D2 rules: the mapping from lateness to delay swapped, tsel changed at the boundary clock instead of one clock later, the SE0's second edge given a new delay), 3 for the loopback (stuffed bit kept, NRZI inverted in either direction); each must give a failing trace from reset. The unchanged design must first pass the same bmc3 check, so a check that fails for every design cannot count as a catch.

Result on branch int6 with the D2 rules (formal/logs/usb_fs_20261114_230257): k-induction PASS (inductive at step 9 of 24), BMC from reset 24 clocks and bmc3 100 clocks PASS, loopback PASS to 135 and 220 clocks, 13 of 13 planted bugs caught with traces of 3 to 112 clocks (the three D2 ones at clocks 10, 3 and 77). Earlier result, before part D2 (formal/logs/usb_fs_20261111_163629): k-induction PASS (inductive at step 9 of 24), BMC from reset 24 clocks and bmc3 100 clocks PASS, loopback PASS to 135 clocks (110 s), loopback with CRC16 PASS to 220 clocks (321 s), 10 of 10 planted bugs caught with traces of 3 to 112 clocks. On int2 (formal/logs/int2_20261111/usb_fs_20261111_192837) the same results in 188 s (loopback 29 s, with CRC16 78 s). The loopback is bounded: it covers packets of two bytes (all 65,536 values, so every stuffing position) and the DATA packet with one byte, not longer packets; the simulation covers those.

The chip-level power-on proof (formal/pe_por_props.sv) now includes the USB unit: its arm and start are sinks that only the host may drive before START, and a soft reset leaves it not busy with D+/D- released. While ETH_CFG bit 4 is set, uio_out[1:0] and uio_oe[1:0] are not checked (a host setting hands them to the unit, like uo_out[7:6] with Ethernet enabled).

10. Limits

  • Not a compliant full-speed source without the fine edges: transitions are up to 6.67 ns off (TDJ1 3.5 ns, TDJ2 4 ns, TFDEOP -2 to +5 ns), inside the receiver tolerance of a host connected directly or through at most two hubs (section 1). With the fine edges of part D2 the error is about 0.5 ns in RTL simulation with a delay model; that has not been run with layout delays or on silicon.
  • The electrical side (driver impedance, edge rates, crossover voltage) depends on the pads and the board and is not verified.
  • Packets: up to 32 received bytes are stored (29 data bytes after PID, before CRC; longer packets are still checked and counted); up to 96 bytes are sent. The device firmware uses 8-byte packets on both endpoints.
  • The firmware does not handle suspend, resume or remote wakeup, has no string descriptors, supports one configuration and one interface, and has no OUT endpoint besides endpoint 0. Control writes with a data stage are answered with STALL.
  • Answers on endpoint 1 come 5.64 to 5.88 bit times after the EOP, 0.6 bit inside TRSPIPD1.
  • With SOF drop on, the frame number is not available to the firmware.
  • Simulation only; the receiver's clock recovery and the falling-edge output have not run on silicon or an FPGA.

Not done. What it needs:

  • The chip on the Tiny Tapeout demo board with a 50 MHz clock from the RP2040 (12 MHz crystal, PLL 1500 MHz / 6 / 5 = 50.000 MHz exactly; the crystal's tens of ppm are far inside +-0.25 %).
  • A USB device connector (micro-B or a cut cable) wired to the uio PMOD with short leads (less than 10 cm): D+ through a 22 to 27 Ohm series resistor to uio[0], D- through the same to uio[1], a 1.5 kOhm resistor from D+ (connector side of the series resistor) to uio[2], ground to the board ground.
