Sends and receives USB low-speed (1.5 Mb/s) packets. The host supplies and checks PID and CRC; the firmware does the line coding. 106 of 512 words, one hart (harts=1), so the receiver never decodes the chip's own packet.

firmware/usb_ls_h.pe is the same with its transmitter edges on the 20 ns grid of the int6 .h pin writes (section ".h bit boundaries" under TX timing).

A second firmware, firmware/usb_dev.pe, is a low-speed device that checks and makes the CRCs and answers within the bus turnaround by itself; see "Device firmware" below.

Pins and framing

Pin Line
P0 D+
P1 D-
  • Low-speed J = D- high, D+ low (differential 0); K = D+ high, D- low; SE0 = both low (USB 2.0 Table 7-2). The pins are released when idle; the bus pull-up holds J.
  • TX: the host writes L, then L packet bytes (PID first, CRC included). The chip drives J for 20 ticks (40 clocks, measured with test/edge_log.v), then SYNC, data LSB first, EOP (SE0 2 bits, J 1 bit), then releases both pins.
  • RX: the first K starts a packet. Bytes from the PID on go to the host FIFO as they complete (SYNC is not passed). After EOP one trailer byte follows: the number of bytes decoded, plus 0x80 on a bit stuffing error. A byte that finds the host FIFO full is dropped, so trailer > bytes read means bytes were lost.

TX timing

twait is absolute, and tset X issued k ticks after a twait ends the next one k + X ticks later. wbit issues tset 3 or 4 ticks after twait so the bit times repeat 17, 17, 16 ticks (680, 680, 640 ns): 50 ticks = 3 bits = 2.000 us, an exact mean of 1.5 Mb/s. Each edge is 0, 13.3 or 26.7 ns after the ideal grid. The worst code path between two twaits (byte boundary: rxb, reload, next bit) is 15 ticks, under the 16-tick period.

Measured (test_usb_tx, edges in ps from the pins):

Result
Mean rate error over a packet 0.000 % to -0.059 % (finite span; exact over 3 bits)
Edge vs nominal grid from SOP 26.7 ns max
Edge vs best-fit line 17.2 ns max
Any edge-to-edge interval vs N bits 26.7 ns max
EOP SE0 1320 or 1360 ns (TLEOPT 1.25 to 1.50 us)
J after SE0 680 or 640 ns, then pins released

This meets the function (upstream port) limits, +-95 / +-150 ns. It does not meet the host (downstream port) limits of +-25 ns next / +-14 ns paired: 26.7 ns is the 40 ns tick quantization of a 666.7 ns bit. That needs a 20 ns step, which the ISA of int6 has: the .h pin writes land one clock later (docs/isa3.md), used by usb_ls_h.pe below.

.h bit boundaries (firmware/usb_ls_h.pe, int6)

usb_ls_h.pe is usb_ls.pe with another wbit and the release at the end of a packet; the receiver is the same. 118 of 512 words. The bit times repeat 16, 17, 17 ticks and the second and third pin writes of each three bits are wrp.h (one clock late), so the boundaries fall on clocks 0, 33, 67 and 100 of every three bits (ideal 0, 33.33, 66.67, 100): each edge is within 1/3 clock (6.7 ns) of the ideal grid. Every path of wbit writes in the third tick after its twait, so only .h moves an edge; the release at the end (wend) takes the same tick and form. tools/petime.py gives the same verdict as for usb_ls.pe (UNDECIDED only on the host FIFO rxb, least margin 7 timer units against 9).

test_usb_tx_h sends the five packets of test_usb_tx from both firmwares and measures every data transition before the EOP as an interval minus N bit times, consecutive and paired (USB 2.0 7.1.13.1.1: J-to-K to the next J-to-K) [measured, RTL, Icarus 11]:

usb_ls.pe 26.7 ns 26.7 ns (outside) 26.7 ns (outside) 1320 to 1360 / 640 to 680 ns
usb_ls_h.pe 6.7 ns 13.3 ns 13.3 ns 1320 to 1340 / 660 to 680 ns

The whole module with this test: TESTS=7 PASS=7 FAIL=0 (2026-11-18, RTL of int6 8574ae4, Icarus Verilog 11.0, cocotb 2.0.1). The first run of the test found a fault in the firmware, not the test: the two 17-tick tset values were one tick long (18-tick periods, a J of 720 ns after the EOP); petime cannot see it because a long period is never late.

On the board (by the board session; logs, the judging script and the feeding program in fpga/zcu104_demo/logs/usbtx and fpga/zcu104_demo/host of the L4d worktree, commit 5eba042, not on a branch of this tree yet): the ZCU104 demo build of the full configuration with MBIST and the run-time SPI speed (bit 03fd016a) ran both firmwares, the same words as here, with the five packets of test_usb_tx_h, and an ILA took 16,384 samples of D+ and D- at 50 MHz. In all 10 captures the bytes of the script's own NRZI decoding, the SYNC, and the PID, address and endpoint, CRC5 and data bytes of sigrok-cli's usb_packet decoder equal the packet sent, with no CRC error. The largest distance of an edge from the 1.5 Mb/s grid is 26.7 ns for usb_ls.pe and 6.7 ns for usb_ls_h.pe, the values of the table, and the 8 x 0xFF packet shows its stuffed bits as 7-bit intervals (232 and 234 clocks) [measured, board]. The host fed the FIFO by the bit stream's timing (Host FIFO limits below). Later the board session added a third verdict to the judging script: every edge within the design grid (26.7 ns for usb_ls.pe, 6.7 ns for usb_ls_h.pe), else GRID FAIL. Run again on the 10 captures above, it gives GRID OK for all; on the build with the MBIST collars (bit 32814bfd, L4d worktree commit 4fbcaa7, fpga/zcu104_demo/logs/mbloc_531cc01/usbtx_r4 to usbtx_r6) three rounds of the 10 packets, 30 captures, pass the bytes, sigrok and the grid, with the largest grid distance again 26.7 and 6.7 ns [measured, board]. The bus must idle at J: D+ low (the host's pull-down) and D- pulled up. A pin model that pulls both lines up shows D+ high, which the firmware's idle loop takes for a K, the start of a received packet, so it never empties the transmit FIFO.

RX timing

Each edge restarts the timer. The decision for the next bit is a waitp.to timeout about 1.5 bit after the edge (EDGE); an edge before the timeout is a 0, none is a 1. Further 1s use 16-tick steps, so the decision drifts early by up to 0.3 bit over six 1s at -1.5 %. That is the safe direction: code after a timeout takes up to 10 ticks before the next waitp, so a late decision would detect the next edge late. After six 1s the stuffed edge gets its own longer timeout (STUFF).

test_usb_rx_margin (11-byte DATA0 of 0xFF, 12 stuffed bits, 3 seeds per point, uniform random edge jitter):

Edge jitter Rates that decode
0 -6.0 % to +4.5 %
+-75 ns -3.0 % to +4.5 %
+-150 ns -1.5 % to +3.0 %

The spec points (+-1.5 % with up to +-150 ns, close to TUJR1 = 152 ns) pass. test_usb_rx also passes all seven packets at 0 and +-1.5 %.

EOP: from J, SE0 is seen at the next decision (mid-bit). From K, D+ falling is first taken as an edge, and SE0 is seen at the decision 1.5 bit later. An SE0 shorter than about 1.1 us after a K is therefore missed, while TLEOPR allows 670 ns. Normal sources send 1.25 us or more.

SYNC is not checked: any K starts a packet.

Host FIFO limits

The FIFOs hold 4 bytes each way. One USB byte takes 5.3 us or more.

  • TX, host writes L and the packet in one SPI burst at clk/8 without polling: up to 6 packet bytes (test_usb_tx_burst_limit; 7 bytes lose one byte). This covers handshakes, tokens and DATA with up to 3 payload bytes. A lost byte stalls the firmware mid-packet, and a soft reset recovers it.
  • TX, longer packets: the host reads the FIFO count (short STATUS, 5 bytes) and writes the free slots in one burst, repeatedly. 11-byte packets pass this way at clk/8 with a host that sends its SPI bytes back to back, as the test bench does. The board's host is slower: one SPI byte takes about 128 clocks from C (64 of SCK at clk/8, the rest register access) and 29 us from Python. From C, this loop ran the FIFO empty at the 4th byte of the 7- and 11-byte packets, and the packet stopped there (sigrok: CRC16 error). The board host now computes from the bit stream when the chip takes each byte (usb_feed.c "paced" in the board session's tree, above). Writing byte k when the chip takes byte k-2 passed the first 10 captures, but on a later build 1 of 10 stopped from its 6th byte: a gap of 414 clocks, Linux scheduling the host late. Writing byte j once the chip has taken byte j-3 (the FIFO at most 3 of 4 full) gave the right bytes in 30 of 30, yet three captures had edges up to 146.7 and 46.7 ns off the grid: the FIFO ran empty for 2 to 5 clocks at byte boundaries, which a check of the bytes alone does not see (hence the grid verdict above). The same timing with one change passes every check: when the host is late, it sends the bytes already allowed, up to 3, in one SPI transaction with one command byte instead of one transaction each; 30 of 30 packets of up to 11 bytes [measured, board]. A host must keep the FIFO from running empty at every byte boundary, not only on average.
  • RX, host not reading during the packet: 4 bytes are kept, and the trailer waits in the firmware until the host reads (test_usb_rx_fifo_limit: 3 and 4 bytes complete, 7 bytes give the first 4 plus trailer 7). Tokens, handshakes and zero-length DATA fit.
  • RX, longer packets: the host polls and reads during the packet. 11-byte packets pass this way at clk/8.

Missing for enumeration with a real PC host

(For usb_ls.pe. usb_dev.pe below answers within the turnaround, checks and makes the CRCs, and detects bus reset and keep-alive; the electrical items stay. usb_dev.pe has since been enumerated by a PC on the FPGA board, with the electrical parts on a breadboard: see the board paragraph at the end of this page.)

  • Response time: a device must answer within 6.5 bit times (4.3 us) of the host EOP. A round trip through host SPI (read the packet and trailer, decide, write a reply) takes far longer. ACK/NAK and the IN data reply must come from the firmware itself (a preloaded reply, or automatic ACK after a good DATA). The firmware cannot check CRC16 at line rate in the space left.
  • D- 1.5 kOhm pull-up for a device (host side 15 kOhm pull-downs), 3.3 V levels, and edge rates of 75 to 300 ns (Table 7-10 TLR/TLF), which need series resistors and capacitors on the chip pins.
  • Bus reset (SE0 10 ms or more) and suspend (3 ms idle) detection, which the firmware does not do. As a host, keep-alive EOPs every 1 ms (11.8.4.1) and reset are also missing.
  • The data toggle, the address after SET_ADDRESS, and the descriptors are host software.

Device firmware (firmware/usb_dev.pe)

Simulation only, not checked on a board. A USB low-speed device (function) that answers the host by itself within the bus turnaround time: it checks the CRC5 of tokens and the CRC16 of data packets, makes the CRC16 of its own data packets, filters tokens by address and endpoint, and sends ACK, NAK, STALL or DATA as the state bytes in the data memory say. It detects bus reset and keep-alive. Host software (over SPI) arms the endpoints and answers the device requests; it is only needed between transactions, because every time-critical answer comes from the firmware. 258 of 512 words (256, all of the earlier 256-word memory, until the length check of DATA packets was added on 2026-11-13), one hart (harts=1, START1 0). Pins as above: P0 = D+, P1 = D-. firmware/usb_ls.pe is unchanged.

What the firmware does

  • Receive: the same edge-timed decoder as usb_ls.pe, but the start of the packet is found by searching for the K K that ends SYNC, so a packet that starts while the firmware is still busy with the previous one is still read (the host may send the DATA packet 2 bit times after its token, TIPD). Each byte is stored in the data memory; more than 11 bytes are dropped. An EOP after a K is seen 200 ns after D+ falls (D- still low), after a J at the next bit decision.
  • Token (3 bytes): CRC5 checked with crc.lsb (polynomial 0x14 reflected, init 0x1F; the register is set at the start of every packet), then address = ADDR and endpoint = 0 or EPN. Another address or endpoint: no answer (8.3.1).
  • IN: the state byte is the PID to send. NAK or STALL: that handshake. DATA0 or DATA1: the record at the IN pointer (n, then n data bytes, n = 0 to 8) is sent with that PID and a CRC16 the chip computes (crc.lsb, 0xA001, init 0xFFFF, sent inverted). The host ACK sets the state to NAK; with no ACK the state stays and the next IN sends the same packet again (8.6.4).
  • OUT: if the OUT state is DATA0 or DATA1 the data packet goes straight into HOLD. After the data packet: its length must be 3 to 11 bytes (PID, 0 to 8 data bytes, CRC16), any other length gets no answer and sets STAT bit 0; then CRC16 checked (residue 0xB001); a bad CRC gets no answer. NAK or STALL state: that handshake. The expected DATA PID: ACK, the state becomes NAK and PSLOT = 8 - data length. The other DATA PID (a repeat): ACK and dropped (8.4.6.3).
  • SETUP to endpoint 0: always taken (8.4.6.4): EP0 IN := NAK, EP0 OUT := DATA0, STAT bit 3; the DATA0 is then taken like an OUT. SETUP to another endpoint: no answer.
  • The first SYNC edge of an answer is TURN ticks after the EOP decision (.equ TURN, 100 = 4 us), or later if the work takes longer (STATUS late flag, hart 0).
  • Idle: an SE0 of 240 ns or more sets STAT bit 6 (keep-alive: a low-speed EOP, Table 7-2 note 4 and 11.8.4.1). An SE0 that lasts about 2.6 us or more is a bus reset (TDETRST 2.5 us, 7.1.7.5): ADDR := 0 and STAT bit 7, before the reset ends.
  • Between packets the firmware takes host pokes from the FIFO.

Data memory

The host writes 0x17 to 0x1F with DATA_W before the run (soft reset keeps the data memory, power-on reset clears it, and 0 is not a valid state), reads everything with DATA_R at any time, and changes bytes at run time with pokes.

Host software

  • Poke: FIFO_W with two bytes, address then value, in one SPI transaction (the firmware waits for the second byte and hears nothing on the bus meanwhile). The firmware takes it between packets; when the STATUS in-count is back to 0 the byte is written.
  • IN: write the record into the frame buffer with ETH_W (it does not need the harts stopped; the firmware only reads the frame buffer), poke the pointer, then poke the state DATA0 or DATA1. When DATA_R reads NAK in the state, the host has ACKed the packet. The data toggle is kept by host software: alternate the PID per ACKed packet. A transfer longer than 8 bytes is one record per packet, armed one after the other; it ends with a short packet (a zero-length record when the length is a multiple of 8 and less than requested).
  • OUT: poke the state with the DATA PID expected next. NAK read back: 8 - PSLOT bytes in HOLD. Read HOLD before arming any OUT state again (one HOLD for both endpoints; a SETUP always overwrites it).
  • SETUP: STAT bit 3 set and EP0 OUT reads NAK: the 8 request bytes are in HOLD. Clear STAT, then arm EP0 IN (control read) or EP0 OUT (control write) for the data stage, and the other direction with DATA1 for the status stage; or STALL both for an unsupported request.
  • SET_ADDRESS: arm EP0 IN with a zero-length record and DATA1 (the status stage); when it reads NAK, poke ADDR = new address x 2 (9.4.6: the address changes after the status stage; the host then waits at least 2 ms, 9.2.6.3).

Enumeration as tested (test_usb_dev_enumeration): bus reset (SE0 50 us); GET_DESCRIPTOR (device, wLength 64) at address 0: SETUP ACKed, three IN packets 8 + 8 + 2 bytes (DATA1, DATA0, DATA1, CRC16 by the chip, checked by the host model), zero-length OUT status ACKed; SET_ADDRESS(7): SETUP ACKed, zero-length DATA1 IN; address 0 then gets no answer; GET_DESCRIPTOR(device, wLength 18) at address 7 returns the same 18 bytes. The device descriptor is in the frame buffer as three records.

Turnaround (measured)

USB 2.0 7.1.18.1: a device answers no earlier than 2 bit times (TIPD) and, for a low-speed device (which must have a captive cable, 7.1.1.2), no later than 7.5 bit times (TRSPIPD2) after the SE0-to-J of the host's EOP; 6.5 bit times (TRSPIPD1) is the limit with a detachable cable. test_usb_dev_turnaround, delay from the host's SE0-to-J to the device's first K in bit times (666.7 ns), min..max over five token bodies (so the host packet ends in J or in K):

Answer Shipped TURN = 100 TURN = 1 (as early as the firmware can)
NAK to IN 4.57..4.85 1.93..2.21
STALL to IN 4.55..4.81 2.15..2.41
NAK to OUT data 4.55..4.59 2.15..2.19
STALL to OUT data 4.65..4.69 2.85..2.89
ACK to OUT, 0 / 4 / 8 data bytes 4.56..4.76 2.40..4.52

Every answer is inside 2 to 7.5 bit times with the shipped TURN, so a minimal device fits the turnaround. DATA answers with 3 or more bytes are limited by the firmware, not by TURN: copying a byte into the send buffer and through crc.lsb takes 6 ticks (0.36 bit), and an 8-byte DATA packet starts 6.47 to 6.76 bit times after the EOP, inside TRSPIPD2 (7.5) but above TRSPIPD1 (6.5) for some token bodies. With TURN = 1 the fastest handshakes come before 2 bit times, which is why TURN is 100. The STATUS late flag is set after any answer that needed more than TURN: test_usb_dev_late_flag reads it after each kind of answer (one load each, the flag is sticky) and finds 0 after every handshake, after the ACK of OUT and SETUP data up to 8 bytes and after DATA answers of 0 to 2 bytes, and 1 after DATA answers of 3 to 8 bytes. tools/petime.py reports the same as a VIOLATION (worst-path, 103 instructions in TURN = 100 on the path of a 3-byte DATA answer, petime.md); for this firmware the flag means "this answer started later than TURN", not a fault. The table was measured again on 2026-11-13 after the length check below; the answers to OUT and SETUP data in the TURN = 1 column are two ticks (0.12 bit) later than before, the column of the shipped TURN is unchanged.

Over-long DATA packets (2026-11-13). The CRC16 loop of a received DATA packet ran once for every byte the packet was longer than its PID, and the receive buffer keeps 11 bytes. A packet of 12 bytes or more therefore had its CRC16 computed over the first ten bytes received and the settings stored behind the buffer, which fails for any packet that was not made for it, so such a packet got no answer (the 24-byte case of test_usb_dev_errors). The static deadline check pointed at the loop (up to 256 rounds inside TURN). test_usb_dev_late_flag showed it can be reached: with the first ten bytes chosen so that this CRC16 comes out right, the device ACKed a 12-byte packet (4.59 bit times), a 20-byte one late (6.65, late flag 1), a 25-byte one after 7.81 bit times, past the 7.5 allowed, and a 51-byte one after 14.07. Now a DATA packet that is not 3 to 11 bytes long gets no answer (two more words; the same test: no answer, STAT bit 0, the endpoint stays armed, late flag 0, also for packets of 1 and 2 bytes). What is left: the byte count is 8 bits wide and not saturated, so a packet of 259 to 267 bytes counts as 3 to 11; its CRC16 is then computed over its first bytes only, within TURN.

Before the 200 ns SE0 check after a K was added, an EOP after a K was seen about one bit later and 7-byte DATA answers reached 7.58 bit times; the measurement drove that change.

Timing

  • Transmit: the bit loop of usb_ls.pe (17, 17, 16 ticks). test_usb_dev_in_data: rate error 0.000 to -0.080 % per packet, edges within 26.7 ns of the nominal grid, EOP SE0 1320 or 1360 ns.
  • Receive (test_usb_dev_rx_margin, uniform jitter on every edge, so an interval moves by up to twice the value; a device receiver must take +-75 ns to the next transition, TDJR1, Table 7-10; token and data 2 bit times apart):
Jitter per edge Asserted (+-1.5 %, 3 seeds each) Sweep (one seed per rate)
0 pass -3.0 % and +3.0 % pass; +-4.5 %, +-6.0 % fail
+-40 ns pass

The spec point (TLDRATE +-1.5 % with TDJR1 +-75 ns between transitions) passes; the asserted +-75 ns per edge gives intervals up to twice TDJR1. Failures appear first at negative rate offsets (a slower host). usb_ls.pe passes +-150 ns in test_usb_rx_margin with one 8 x 0xFF packet (few edges); a point here needs a token and two data packets with many edges to pass, so the two numbers are not comparable.

  • Bus reset: test_usb_dev_reset_keepalive sweeps the SE0 from 2.0 us in 100 ns steps: 2.5 us and shorter are not a reset, 2.6 us and longer are; 500 us is a reset.

The firmware only reads the frame buffer and keeps everything it writes in the data memory (the 32 bytes at 0x00 to 0x1F; stores it does not need go to 0xA0 and up, where nothing reads them). A firmware store to the frame buffer in the same clock as a host ETH_W word drops the host's word (src/project.v, the capture memory write port takes the store), so a receive buffer there could lose descriptor bytes the host is writing. That is why HOLD and the receive buffer share the small data memory and why there is one HOLD.

CRC settings (G11)

The firmware uses exactly the crc instruction settings that firmware/crc.pe takes and that test/test.py test_crc_standard_check_values checks against the catalogue:

CRC crcpoly crcset Direction Final Check value of "123456789"
CRC-16/USB 0xA001 0xFFFF crc.lsb (LSB = 1) xor 0xFFFF 0xB4C8 (register 0x4B37)
CRC-5/USB 0x0014 0x001F crc.lsb (LSB = 1) xor 0x1F 0x19 (register 0x0006)

usb_dev.pe loads 0x00/0x14 and 0x00/0x1F at the start of each packet (CRC5) and 0xA0/0x01 and 0xFF/0xFF in c16 (CRC16). On receive it compares the register after the CRC bytes with the residue of a good packet (0x06, 0xB001) instead of inverting; on transmit it sends crcgl, crcgh xor 0xFF. test_usb_gen_model checks these settings and residues with the bit model of test.py, and the line model reproduces the crcdes.pdf packets. test.test_crc_standard_check_values was run again for this (PASS, registers above).
