Branch int5 grows the chip in the order of its design study (the plan of 2026-11-12, kept outside the repository): each step changes the meaning of something first and the structure later, and each is a commit of its own with the regression, the new checks and the planted bugs that must fail.

The delay lines (part D of the plan) come after these four: part D1 (the lines, bypassed after reset) is the last section of this page, on the tree of int5b; part D3 (a training firmware, no RTL change) is the section after it; part D2 (finer USB edges, on the lines of P0 and P1) is described in usb_fs.md.

What a firmware sees

Nothing changes for the firmware files of the repository: every one assembles to the same words (test/check_asm_compat.py), and every hart keeps its tick of 40 ns. The number of firmware files differs from section to section of this page because the branches differ: 117 on int4 and on int5 through its four parts (git ls-tree at 067e608 and e606e77), 143 on mem512, and 144 on int5b from the first merge of mem512 on (its 143 and spw.pe of int4), which is the count of this tree. A comparison against mem512 therefore covers 143 files and one against int5b 144. The differences a host can see are listed where they are described: three for the default capture (B0), the steal flag in STATUS byte 6 bit 5 and the unknown power-up contents of the SRAM outside the data memory and the frame buffer (B1).

  • What the deeper BMC found in the proof's environment and the CACHE claim (no RTL change): the first versions let the solver hold soft reset high while a transmitter ran, and let the host ask in every other clock, though pe_host_spi asks once per SPI byte (16 clocks or more); the props now assume a transmitter stops on soft reset, one host request in 8 clocks and no transmitter during the zero fill. With those, a real corner remained: right after a transmitter starts with both of its first words missing, the cache's urgent rule reads the first word a second time while that read is still on its way, so the two words can take 9 clocks instead of 8 with a host request between. A transmitter sends 32 clocks or more of preamble or SYNC before its first data word, so nothing is late; the claim is now 10 clocks per cache window, and choosing the next missing word past the one being read would remove the repeat (not done in part 1).

A

  • u_core1 (harts 2 and 3), u_prog1 (1024x16), u_shm1 (512x16), host FIFOs of core 1, peer FIFOs u_p01/u_p10. pe_core gets the peer FIFO instructions (rxp/txp), the other core's drives for the wired AND (core 0's pad registers form the pads of all four harts; the pad timing rule is untouched) and the other core's writes of gpo and the launcher reference (core 0's own write wins). Host: CTRL bits 3 and 4, START3, STATUS2 and the core 1 commands share the existing states through a core flag, so the host state machine keeps its 32 states. The launcher takes a 2-bit hart number. Core 0 alone drives the capture and the line units.
  • Departures from the plan: the pad registers stay in pe_core (core 0's), fed with core 1's drives, instead of moving to the top level, so the pad rule code that branch int3fix changes is not touched; STATUS2 has the layout of STATUS (core 1's hart fields in the same places, ID 0x51) instead of a shorter one, so a host reads either with one parser.
  • test/test_core1.py, 5 of 5: core 1's host commands (PROG_W/R, START3 at word 700, CTRL bits 3 and 4, STATUS2, DATA_W/R, FIFO_W/R) and core 0 left alone; core 0 and core 1 exchanging bytes over the peer FIFOs (rxp.nb on an empty FIFO sets Z); four harts driving random patterns: the pads are the wired AND of all four or the staged state in every clock and never change both bits at one edge but from the staged state; gpo written by harts 0 and 2 in one clock takes core 0's value, a clock later core 1's; firmware/uart.pe running on both cores at once (P0/P1 and P2/P3), both directions of both bridges.
  • test/test_iss_chip.py (new): both cores in lockstep with peiss.Chip, 30 seeds, 145,323 clocks, 62 rxp/txp in the programs, both cores writing in one clock 193 times for gpo and 47 times for pelsel, PASS. Its first version (127,664 clocks) never had both cores write a shared register in the same clock, and the control that lets core 1 win gpo survived it; the generator now adds short loops of gpo and pelsel writes to two-core programs (programs of one core are unchanged, the same text for seeds 0 to 299), and the test fails if the default seeds do not reach both races.
  • Planted bugs (test/controls.sh, one at a time): a_gpo_core1_wins, a_peer_fifo_own (core 1 reads its own output FIFO), a_pads_core0_only (core 1's drives left out of the wired AND), a_start3_ignored, a_chip_peer_own, a_chip_gpo_core1_wins, a_chip_sel_core1_wins (new), and r1_no_hart1_oe, c_start1_bit9_lost again on this RTL: 9 of 9 caught (a_chip_gpo_core1_wins after the generator change above).
