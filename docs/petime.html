The chip reports a missed period at run time: a twait that arrives after its period has run out sets the hart's sticky late flag (architecture.md). tools/petime.py answers the same question before a program is loaded. It reads a .pe file, assembles it with tools/peasm.py and decides for every twait a hart can reach whether the flag can be set there.

python3 tools/petime.py firmware/uart.pe                     # one file: full report
python3 tools/petime.py firmware/apa102.pe --data 0=5        # with a setting the host writes (DATA_W)
python3 tools/petime.py --data-default 0 firmware/*.pe       # several files: one line each and totals
Verdict Meaning Exit code
PASS No twait the hart can reach can be late 0
NO-DEADLINE The hart cannot reach a twait; there is nothing to check 0
VIOLATION On some path a twait arrives after its period has surely run out 1
UNDECIDED No such path was found, but for some twait the timer may or may not have run out; every reason is printed 2

A program's verdict is the worst of its harts (hart 0 from word 0, hart 1 from the label hart1 if there is one; --harts 0,1 checks hart 1 from word 0 as well).

The rule

The late flag has one cause in the RTL (src/pe_core.v, SYS_TWAIT): the twait ends in a tick in which the timer count is already 0. From there:

  • tset P (or tsetr, or the end of the previous twait) loads the count with P. The count drops by one in every later tick in which the hart runs, whether it executes or stalls, and stays at 0.
  • A twait that arrives while the count is 1 or more waits and is in time. A twait that arrives at count 0 is late.
  • So with n one-tick instructions between the time anchor and the twait, the twait is in time when n <= P - 1 and late when n >= P. With the prescaler (tpre k) the limit is n <= P x 2^k - 1, because the unit restarts at the anchor.

test/test_petime.py checks this rule against the RTL one instruction below and at the limit (see Agreement with the RTL).

How a program is checked

The tool explores every path of each hart with an abstract machine and keeps what it needs to bound the timer:

Part of the state Abstraction
r0 to r7 a known constant, a range lo..hi, or unknown. Unknown after soft reset (the registers keep their contents), after rxb, shin, rdp, gpi, tgeth/tgetl, erxl, crcgh/crcgl and after arithmetic on unknown values
Z, C 0, 1 or unknown. A branch on an unknown flag follows both sides; after cmpi r,k, cmp r,constant or test r,r each side narrows the range of r (so cmpi r3, 33 / jnc bounds a loop count or a buffer pointer)
Timer an interval [lo, hi] of the count, the period, the prescale and the position inside a prescaled unit, the frozen bit
PC, return address exact
Data memory a byte that some st of either hart can change is unknown. The others have the value given with --data ADDR=VALUE or --data-default V, or are unknown. The frame buffer is always unknown

Instructions take one tick. The ones that can stall are handled as follows.

Instruction Effect on the timer interval
twait checked as above, then the count is the period again
blocking rxb, txb at least one tick, no upper bound: lo becomes 0 (reason host-fifo)
waitp, waitp2 the same (reason pin-wait)
waitp.to, waitp2.to two outcomes: a match anywhere up to the end of the period (lo 0, reason pin-wait-timeout), or a timeout, after which the count is exactly 0
plaunch, plaunchr no upper bound (reason launcher): the launch may be pending for the other hart
erxon, etx, erxw no upper bound (reason line-unit)
tsetr with registers that are not constants the period is the range the two registers allow, high byte times 256 plus low byte, each at its lowest and at its highest ([0, 65535] when nothing is known); a twait it leaves open is reported with reason period-from-register. Since 2026-11-21; before, any such period was [0, 65535]

--wait-max N replaces "no upper bound" by N ticks for every stalling instruction. A PASS then holds only under that assumption.

At a twait the interval decides: lo >= 1 is in time (the report gives lo - 1 as the margin), hi = 0 is late, and lo = 0 < hi is not decided.

Loops and the size of the search

A loop with a constant count (ldi r1, 8 ... djnz r1, ...) is simply followed. A djnz on an unknown register is followed for up to 256 iterations as a range. A loop that does not change any register and has no anchor (polling a pin with shin, or jmp to itself) would lower the count for ever: after 8 timer states at one program point the tool merges them into one interval, and after 16 changes of that interval it sets lo to 0 (reason unbounded-loop; merging alone is reported as merged-paths).

The search is tried at up to three levels and stops at the first that finishes: exact register states (150,000 states), register states joined into ranges at time anchors and stalling instructions once more than 64 differ (300,000), the same after 16 (400,000). If the last one runs out, the hart is UNDECIDED with reason state-budget, and the stores it was not seen to make are taken as "any byte".

What the verdicts claim

PASS is a statement about every run: the abstract machine covers every value the registers, pins, FIFOs and unknown memory bytes can take and every length of every stall, so if no reachable twait can see count 0, the late flag of that hart stays 0 and every period is exactly as long as the firmware set it. It holds under these conditions, which the tool cannot see:

  • The image in the program memory is the one that was checked (the JSON report carries its SHA-256), and the host does not rewrite it while the harts run.
  • Data memory bytes given with --data or --data-default keep those values unless the firmware itself stores to them; the host does not stop the harts and rewrite them.
  • With --wait-max N, no stall is longer than N ticks.

It says nothing about what the pins do in those periods: that the edges are the right ones is the business of the protocol tests.

VIOLATION has two kinds, printed with the verdict:

  • every-run: no branch on unknown data or on a pin lies between the reset and the late twait. Every run that gets that far sets the flag (only stalls, such as waiting for a host byte, lie before it).
  • worst-path: the path takes branches whose outcome depends on unknown data or pins. Each such branch can go either way as far as the tool knows, but it does not prove that the outcomes of one path can occur together. The report names the twait, the anchor, the instruction count and the period so that the path can be read in the source. This is the usual worst-case-path verdict: correct firmware may be rejected because of a path that cannot happen.

UNDECIDED is not a pass. Reasons and what they mean:

Reason The deadline depends on
host-fifo how fast the host delivers or takes a byte between a time anchor and the twait
pin-wait, pin-wait-timeout when the other device changes a pin
launcher, line-unit the predictive launcher or the Ethernet/USB unit
period-from-register a period that comes from registers whose range does not decide the twait: host bytes, measured times without a lower bound that the firmware checks, or a data memory byte that the firmware also stores to or that was not given
unbounded-loop, merged-paths a loop without a time anchor whose exit depends on data, or more timer states at one point than are kept
indirect-jump a jtab with an unknown index (all 256 targets are followed; this alone does not make a hart undecided)
frozen-timer a twait while waitp.frz holds the count above 1, which would never end
leaves-image the PC can run past the last assembled word
state-budget the search did not finish

Agreement with the RTL

test/test_petime.py gets the verdict of the checker for a program, then runs the program on the RTL and reads the late flags from STATUS. PASS must leave the flag 0; VIOLATION must set it once the run has taken the reported path. One run of the module on 2026-11-13 (RTL of 92b38df, Icarus Verilog 11.0, cocotb 2.0.1): TESTS=7 PASS=7 FAIL=0, 15.12 ms simulated, 75 s wall. Three of the tests are about firmware in which this tool found a late path that has since been removed (Cases); each runs the file as it was before the change (the test puts the old lines back) and the file as shipped.

That is 26 programs or settings: 11 with a PASS and 10 with a VIOLATION compared with the flag directly, four where both sides of a conditional verdict were driven (the three files before their change and the pin wait), and can.pe as shipped, UNDECIDED, whose flag stayed 0 with a host that keeps up.

Controls on the module itself: with an error planted in a copy of the checker (PETIME_DIR=<folder> makes the module import that copy), test_petime_edges must fail. It did for each of three: the anchor loading the count with P + 1 (the rule becomes n <= P), "late" taken as count 1 or less, and the prescaler ignored.

Both false alarms come from the same abstraction: a data memory byte that the firmware itself stores to is unknown to the tool, even where every store writes a small known value. A firmware can be written so that the tool sees the bound (the count in a register, or a cmpi and a branch before the loop, which narrows the range), at the price of an instruction or two; that was not done for these two.

Counted over the six files with a worst-path report that were examined: four had a real late path (usb_dev.pe two of them, one a fault and one the documented use of the flag), two were false alarms.

The period of tsetr as a range (2026-11-21)

Until 2026-11-21 a tsetr whose registers were not both constants gave the period [0, 65535], so a measured period stayed undecided even when the firmware checked a lower bound just before (the ZACwire reader of the flexibility rehearsal, flexibility.md, item 2). Now the period is the range the two registers allow: the high byte's range times 256 plus the low byte's, each at its lowest and at its highest, as the compares before it narrowed them. The bound is sound for any pair of values in the two ranges; it loses the relation between the two bytes, and the registers' ranges are those the search keeps (joined at an anchor after 64 register states).

The old and the new tool on the 152 files of firmware/ and firmware/gen/ of this tree, in both settings (evidenceprivate repo file): two files change their verdict, zacwire.pe (margin 49 ticks: the start bit must be at least 50 ticks) and i2s.pe (margin 0: the firmware raises HALF to at least 5, and its header says four instructions fit in each half period), both from UNDECIDED to PASS, in A and in B. No verdict goes the other way and the late twaits are the same. Five files that stay UNDECIDED (inject_i2c.pe, inject_spi.pe, inject_uart.pe, peci.pe, spdif.pe) add the reason merged-paths, because a range is kept as more timer states, and sgpio.pe now needs the joined search, in which one pointer store is no longer bounded; its verdict is the same. Counts with the new tool, A and B: files PASS 43 and 48, UNDECIDED 69 and 62; twaits in time 564 and 605, not decided 422 and 348 (old tool on the same files: 41 and 46, 71 and 64, 548 and 593, 438 and 360). The tables above stay those of the 143 files of 2026-11-13.

test_petime_edges has a program for it, tsetr_range_fit: a pin value raised to at least 5 gives the low byte, and four instructions follow the tsetr before the twait; static PASS, and the late flag stays 0 on the RTL, where the pins are 0 and the period is 5. With the old tool the same test fails (UNDECIDED, expected PASS).

Limits

  • Only twait deadlines are checked. A firmware that keeps time with waitp.to, tgetl or by counting instructions has no deadline the tool knows; a hart without twait is NO-DEADLINE, not PASS.
  • The check is per image and per setting. Firmware that takes its period from the data memory needs --data for the setting in question; most of the general firmware (*_gen.pe) is in that group.
  • Registers are constants or ranges without relations between them. A pointer that walks a buffer in a loop counted by another register is bounded only while the search can follow the loop exactly; once register states are joined, a store through that pointer counts as a store to any byte and every setting read from the data memory becomes unknown.
  • A worst-path violation may be infeasible (two of the six examined were), and a long loop can make the search give up (state-budget).
  • The two harts are checked one at a time. They meet in the data memory (handled as above), the FIFOs, the pins and the launcher (handled as stalls of unknown length or unknown values).
  • This is a check outside the chip. The chip does not refuse an image; the run-time late flag stays the last word.
