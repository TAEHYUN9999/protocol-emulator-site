The brief asks for a chip that supports "new protocols after fabrication". This page says what the repository already shows about that, and sets out a procedure that shows it in a way a reader can check: freeze the RTL with a tag, draw protocols that the author cannot choose, implement them in firmware only, and record the time taken and every failure.

1. Freezing the RTL

Which commit. The submitted RTL after its full set of checks: GDS and precheck, gate-level tests and the gate-level equivalence proof, the board self test and the 8-hour run. No such commit exists yet. The RTL in src/ (two cores, five SRAM macros, delay lines, and the debug unit, instruction additions, tick generators and SRAM self test of int6) is not frozen: the fixes of the defects found where those blocks meet are in it (STATUS revision 0x05), and the freeze comes after its checks (a passing layout among them). Earlier candidates, kept here for the record with their frozen-file digests (below): the src/ tree of the one-core RTL 422ec10 (git tree 6613939b, the third integration int3, revisions), digest 736d02cb73aed1f5466e885422f8013e9a57587cf4117916bab86a099f8aa5da, and before it the tree of 7c40aac (git tree 96deec95, digest b4867a88255cf488bfb1a3ba55befc4656bb55bd26c0320516412a275f6ccd5a). Neither is a candidate now. TODO(author): the date.

What is frozen. Every file under src/ (RTL and flow setup) and macro/, and the keys of info.yaml that choose what is built: tiles, top_module, clock_hz, source_files. Firmware, tests, tools and documents may change after the freeze.

How.

python3 tools/freeze_check.py manifest --rev <commit>     # prints the digest and the src tree id
git tag -a rtl-freeze-v1 <commit> -m "RTL freeze v1
frozen-digest: <digest>
heldout-commitment-sha256: 85f9bfb0de48b0ba1752e8aefba8c43bada32a698b42eea39342236778cc1774
gds: <md5>  netlist: <md5>  evidence: <folders>"
git push origin rtl-freeze-v1                             # to the public repository

The digest is the SHA-256 of a sha256sum listing, so it can be checked without the script:

D=$(mktemp -d); git archive rtl-freeze-v1 src macro | tar -x -C "$D"; cd "$D"
LC_ALL=C find src macro -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum | sha256sum

After the freeze. tools/freeze_check.py check --tag rtl-freeze-v1 fails if any frozen file or build key differs from the tag, or if the digest differs from the frozen-digest: line of the tag message. A CI job runs it on every push:

name: freeze
on: [push, pull_request]
jobs:
  freeze:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
          fetch-tags: true
      - run: python3 tools/freeze_check.py check --tag rtl-freeze-v1

The job is not in .github/workflows/ yet, because the tag does not exist; it is added in the freeze commit. If an RTL fix is needed after the freeze, it gets a new tag (rtl-freeze-v2) and the record says which tag each result ran on; a held-out protocol that needed the fix counts as "needed an RTL change".

Controls of the check (2026-11-12, in a scratch clone with a test tag; the real repository has no tag): the tagged commit and a commit that changes only README.md pass; a comment line added to src/pe_fifo.v, clock_hz changed and a file added to source_files each fail; a changed description in info.yaml passes. The script's digest at 7c40aac equals the shell command's.

2. The candidate list and the commitment

heldout/candidates.tsvprivate repo file lists 28 candidates: the two firmware candidates the author's protocol survey left open (M-Bus, SPI PSRAM in QPI mode) and 26 protocols outside that survey. At the commit that adds it, its SHA-256 is 2ea0b1de277a5dfd260176f18f5bea8b600fbd507a6c28051919b9cfa5e2d782. None of the 28 has a firmware, a test or a protocol page here (searched by name in firmware/, docs/, test/ and tools/ before the list was written).

Inclusion. A candidate needs new behaviour at the pins: framing, line coding, a timing rule, arbitration or a turnaround that no firmware here has. It must have a public source (a data sheet, an application note, an RFC or a free specification) from which a test model can be written independently of the firmware; rows that rely on secondary descriptions say so.

Exclusion, with examples.

Rule Excluded, for example
E1 held: a firmware in firmware/ does it UART, SPI, I2C, CAN, LIN, the 89 protocol pages of docs/
E2 close variant: settings, a register map or messages on a held link, with no new pin behaviour 1-Wire overdrive, MDIO Clause 45 frames, GameCube controllers (N64 joybus is held), SFP and sensor register maps on I2C, CANopen and J1939 on CAN
E3 too fast: the shortest unit is under 16 ticks (640 ns), the firmware threshold of the survey USB full speed, FlexRay, RMII, SpaceWire, CAN FD data phase, STM8 SWIM, encoders at 2.5 Mbit/s
E4 pins: more than the 8 protocol pins GPIB, a Centronics printer port, HUB75 LED panels, parallel NOR flash
E5 analog: needs voltage levels, currents or modulation the chip cannot make (the logic-level baseband of such a link is allowed) HART FSK, AS-Interface, DSI3, an RFID front end
E6 frame size: needs an Ethernet frame over the 128-byte frame buffer DHCP (the fixed part of its message alone is 236 bytes), TFTP with 512-byte blocks
E7 no public source to test against debugWIRE, proprietary links without a published description

The list deliberately keeps hard rows (a TCP echo, SPI PSRAM in QPI mode, the PlayStation pad's acknowledge line) and rows whose fit is not known; a drawn row that cannot be done on the frozen RTL is a result, recorded as a failure with its cause.

The RTL changed after the list was written. The list was committed in 8d84000 (2026-11-12 11:24). Between that commit and 012c611 (2026-11-14), 38 commits touched src/*.v (31 without the merges), and git diff --shortstat 8d84000 012c611 -- 'src/*.v' gives 19 files, 4,472 lines added and 358 removed: the second core, the delay lines, the fine USB edges, and the debug unit, the instruction additions, the tick generators and the SRAM self test. The list was in the repository while that work was done, so whoever designed those changes could see it. None of the changes was made for a candidate of the list, but that cannot be shown from the history, and a draw from this list therefore tests less than a draw from a list the RTL never saw. The answer is a second list sealed after the freeze, from a source the author does not choose; that is a decision for the author and not made yet.

The commitment, before the freeze. It fixes the list's hash, the number of picks k, the draw rule (the hash of tools/heldout.py), the beacon and the draw time:

python3 tools/heldout.py commit heldout/candidates.tsv --k 8 \
    --draw-utc <freeze + at least 24 h, UTC> --chain-hash <H> --genesis <G> --period <P> \
    -o heldout/commitment_v2.json
git add heldout/commitment_v2.json && git commit && git push      # public, before the freeze tag

k = 8, set by the author on 2026-11-19 (v1 had the proposal 6). The commitment's SHA-256 goes into the freeze tag message. Git dates are set by whoever commits, so the time anchor is the push to the public repository (its time is visible on GitHub), and optionally a public timestamp of the hash (for example OpenTimestamps).

3. The draw

Beacon. drand, the public randomness of the League of Entropy: a new value each round, unknown before its round is published. Round r is published at genesis + (r - 1) x period, so the commitment's draw time fixes the round (tools/heldout.py round). The chain hash, genesis time and period are copied from https://api.drand.sh/<chain hash>/info when the commitment is made. The commitment uses the 30-second default chain (8990e7a9aaed2ffed73dbd7092123d6f289930540d7651336225dc172e51b2ce, genesis 1595431050, scheme pedersen-bls-chained), read from https://api.drand.sh/info on 2026-11-18; in v2 the draw is round 6703166 at 2026-12-06T03:00:00Z, at least 24 hours after the latest freeze date (2026-12-05 KST); v1 had round 6779486 at 2027-01-01T15:00:00Z after a freeze by 2026-12-31. The SHA-256 of each commitment is timestamped with OpenTimestamps (v1 on 2026-11-18, heldout/commitment.json.ots; v2 on 2026-11-19, heldout/commitment_v2.json.ots; ots verify <file>.ots), so its existence before the freeze can be checked without this repository's history. A round is read from

GET https://api.drand.sh/<chain hash>/public/<round>
{"round": <r>, "randomness": "<hex>", "signature": "<hex>", ...}

The rule takes any hex string, so another public beacon (for example the NIST Randomness Beacon) works the same way if the commitment names it.

Rule heldout-v1 (tools/heldout.py, docstring): seed = SHA-256 of heldout-v1|<list sha256>|<round>|<randomness>; a stream of SHA-256(seed, counter) blocks read as 64-bit words; a partial Fisher-Yates shuffle of the ids in file order, each index drawn uniformly by rejection. tools/heldout.py selftest checks it on fixed inputs (a stored six-pick vector, determinism, round arithmetic, uniformity of the first pick over 7,000 seeds); the vector was also reproduced once by a separate implementation with sha256sum and bc (not kept in the repository).

After the round:

python3 tools/heldout.py draw heldout/commitment_v2.json --randomness <hex> --signature <hex> \
    -o heldout/record.json

prints the picks and writes a record with one result entry per pick, published at once.

Offline verification. python3 tools/heldout.py verify heldout/record.json --git, from the repository root, without network, checks: the list and tool hashes against the commitment; the round against the draw time; that the randomness is SHA-256 of the signature (drand defines it so; TODO(verify) against the drand documentation for the chosen chain); the picks; the freeze tag time before the round; a result entry per pick with an allowed outcome, commits for every pass, a failure entry for every fail; with --git, that no result commit changes src/ or macro/ against the freeze tag. It does not check the BLS signature (that needs the chain's public key and a BLS12-381 library, for example the drand client) or the public timestamps; it prints both as notes to check by hand.

Controls of the verifier (2026-11-12, scratch clone, made-up chain values, not drand's): a good record passes; a byte changed in the list, a changed tool, changed picks, another round, a signature that does not hash to the randomness, a freeze after the round, a missing result, a pass without commits, and a result commit that changes src/pe_fifo.v each fail.

Alternative: a person chooses. The author, or better a person outside the team, picks k ids from the committed list after the freeze and publishes them at once (or publishes tools/heldout.py seal --salt <s> <ids> first and reveals the ids and salt later). The record then has "method": "chosen", "chooser", "chosen_utc" and, if sealed, "salt" and "sealed_sha256"; the verifier checks the picks against the list, k, the seal and the freeze time. This is weaker than the beacon: the chooser knows the design and can pick what suits it.

4. Implementing the picks with firmware only

  • Only firmware, tests, tools and documents change; the CI freeze check stays green.
  • Each pick gets a test model written from its cited source, at least two planted-bug controls that must fail, clock-exact checks of its timed outputs (test/edge_log.v), and a protocol page like the others.
  • A pick is never dropped or swapped. A pick that cannot be done on the frozen RTL is recorded as fail with the cause; that is a result about the chip's limits.
  • A time box per pick is set before the draw (TODO(author), for example 8 working hours); work past it is recorded but the outcome is fixed at the box.

The record, record.json in heldout/ once the draw has run (it does not exist yet), is published as two tables on this page:

Pick Started (UTC) First passing test (UTC) Work hours Firmware (words) Tests Controls Board Commits Freeze check Outcome
(one row per pick) pass, partial, fail or not started
Pick When (UTC) What failed Cause Fixed in firmware, or why it needs the RTL
(every failed attempt, not only the last)

5. Order of events

  1. Finish the RTL and its checks. The decision is made: the submitted RTL is the last of the planned RTL steps (section 1).
  2. Commit the commitment (commitment_v2.json in heldout/, written by tools/heldout.py commit; done 2026-11-19, replacing v1) and push it publicly.
  3. Tag the freeze, with the commitment's hash in the message; push the tag; add the CI job.
  4. Wait for the committed round, at least 24 hours after the tag.
  5. Draw and publish the record with the picks.
  6. Implement and fill the record; keep the freeze check green.
  7. Run tools/heldout.py verify --git and publish the tables here.

The competition deadline is 2027-01-18; steps 4 to 7 need several days of work, so the freeze has to come well before it: the author set it for 2026-12-05 at the latest, and the committed round is published 2026-12-06T03:00Z.

6. What this does not show

  • The list is the author's. A draw from it is no harder than the list; the inclusion and exclusion rules are written above so a reader can judge what was left out.
  • Git times prove nothing alone; the public push and any public timestamp are the anchors.
  • The firmware will be written with AI assistance like the rest of the repository (docs/ai-use.md); work hours are the author's record.
  • Running the picks on the FPGA boards is optional and is reported per pick.
