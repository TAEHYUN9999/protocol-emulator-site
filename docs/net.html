The firmware answers ARP requests (RFC 826) for its IPv4 address, ICMP echo requests (RFC 792, "ping") and UDP datagrams (RFC 768) sent to it: the UDP echo service (RFC 862) on port 7 (or a port set in the data memory) sends the data back, and a datagram for any other port gets an ICMP port unreachable (RFC 792, RFC 1122 4.1.3.1). It does not build a new frame for the replies: it rewrites the received frame in the 128-byte frame buffer (swaps the addresses and ports, changes the opcode or type, updates the checksum; for port unreachable it moves the request's IP header and first 8 data bytes behind new IP and ICMP headers) and sends it back with etx, and the chip appends the FCS. It runs on hart 0 alone (CTRL = 1) and uses 360 of the 512 program words (253 before UDP). Simulation only, not checked on a board.

Host setup

Step SPI bytes
Stop the harts 01 00
Load the program 10 00 + words
Settings 12 00 + MAC (6 bytes) + IPv4 address (4 bytes), wire order; 12 0F + UDP echo port (2 bytes, high first; 00 00 for the default 7)
Address filter (optional) 45 + the same MAC
ETH_CFG 42 05 at least (bit 0 TD pins, bit 2 chip FCS); 42 0F adds link pulses (bit 1, needed by a real link partner) and the address filter (bit 3)
Start 02 00, 01 04 (soft reset), 01 01 (run hart 0)

The firmware cannot read ETH_MAC, so the MAC is written twice when the filter is used. Without the filter the firmware checks the destination MAC itself; with it, frames for other unicast or multicast addresses never reach the firmware and are not counted. The host FIFO is not used. While the firmware waits for a frame the receiver owns the buffer, so host ETH_W and ETH_TX are ignored; stop the hart and cancel the receive (43 00) before sending frames from the host.

Data memory

Address Content Default
0x00-0x05 MAC address, first byte sent first 02:00:00:00:00:01 (.equ MAC0..MAC5)
0x06-0x09 IPv4 address, first byte sent first 192.168.0.2 (.equ IP0..IP3)
0x0A ARP replies sent (mod 256) cleared at start
0x0B IP replies sent: ICMP echo, UDP echo and port unreachable (mod 256) cleared at start
0x0C Frames dropped as errors (mod 256) cleared at start
0x0D Frames ignored as not for this host or not supported (mod 256) cleared at start
0x0E Status code of the last frame (table below) 0x00
0x0F-0x10 UDP echo port, high byte first 7 (.equ UPORT) if both bytes are 0

If all ten address bytes are 0 when the firmware starts (the power-on value; an all-zero MAC or IP is not a usable address), it stores the .equ defaults there, so a host can read them back with DATA_R. Every frame the firmware sees ends in exactly one counter. DATA_R reads one byte after the other, so the status is not read atomically: the firmware stores the code before the counter and the code sits after the counters, so a read that shows a counter change also shows that frame's code.

What the replies contain

ARP (RFC 826): target hardware and protocol address = the request's sender, sender = this MAC and IP, opcode 2, Ethernet destination = the request's sender hardware address, source = this MAC, bytes 42 to 59 set to 0, 60 bytes sent plus the chip's FCS. A request must be for Ethernet (hardware type 1) and IPv4 (0x0800) and come to the broadcast MAC or this MAC (Linux refreshes its cache with unicast requests). Hardware and protocol address lengths are not checked (optional in RFC 826).

Echo (RFC 792, RFC 1122 3.2.2.6): Ethernet destination = the request's source, source = this MAC; IP destination = the request's source, source = this IP; ICMP type 0. All other bytes stay: TOS, identification, flags, TTL, ICMP identifier, sequence and all the data, and the frame keeps the request's length (Ethernet padding included). Swapping the two IP addresses does not change the one's complement sum, so the IP header checksum stays valid without a change. The ICMP checksum is updated, not recomputed: RFC 1624 eqn. 3 for the word 0x0800 -> 0x0000 is HC + 0x0800 with end-around carry, except that a result of 0xFFFF becomes 0x0000 (the result recomputation would give; plain RFC 1141 addition would leave 0xFFFF). The firmware verifies both checksums of the request first (RFC 1071 sum over the header, and over the ICMP message using the IP total length, with a 0 byte added for an odd length).

UDP echo (RFC 862, RFC 768): Ethernet and IP addresses as for the ICMP echo, source and destination ports swapped, everything else kept (data, UDP length, checksum, the IP identification, flags, TTL). Swapping the two addresses and the two ports leaves the one's complement sum of the pseudo header, header and data unchanged, so the request's checksum is the reply's: a request without a checksum (0) gets none, and one whose sum computes to 0 (sent as 0xFFFF) keeps 0xFFFF. Before answering, the firmware checks that the UDP length equals the IP payload length and, if the checksum is not 0, verifies it over the pseudo header (the two addresses, which lie just before the UDP header in the frame, plus one word of protocol 17 and the UDP length), the header and the data with a 0 byte for an odd length. A wrong checksum is dropped before the port is looked at, so it never causes a port unreachable.

Port unreachable (RFC 792, RFC 1122 3.2.2 and 4.1.3.1): a 70-byte frame to the request's source: IPv4 header with TOS 0, total length 56, the request's identification and flags, TTL 64, protocol 1, a new checksum, this IP to the request's source; ICMP type 3, code 3, checksum, 4 unused bytes 0, then the request's IP header and the first 8 bytes of its data (the UDP header) exactly as received. It is not sent for a source address that is not one host (0x55); the other cases where RFC 1122 3.2.2 forbids an ICMP error (IP or link-layer broadcast, non-initial fragments, ICMP errors) never reach this point (0x52, 0x40, 0x50, protocol 1).

Supported and not supported

Item Status Reason or limit
ARP reply for this IP Supported
ICMP echo reply Supported ICMP data 0 to 86 bytes (frame up to 128 bytes before the FCS), even and odd lengths
Settings without re-assembling Supported DATA_W before the run, .equ defaults when 0
Errors and drops reported Supported Status code and four counters
Frames over 128 bytes before the FCS Not supported The frame buffer is 128 bytes; ignored with 0x41 (Linux ping -s 87 and up)
IP fragments Not supported Reassembly needs more than one 128-byte buffer; ignored with 0x50
IP options (IHL above 5) Not supported The rewrite uses fixed byte offsets; ignored with 0x50
UDP echo (RFC 862) and port unreachable Supported Data 0 to 86 bytes; one echo port, set in the data memory
A UDP length shorter than the IP payload Not supported Dropped with 0x85; RFC 768 does not say what a receiver does with it
Rate limit for ICMP errors Not supported One port unreachable per datagram
TCP, other ICMP types Not supported Ignored with 0x51 and 0x53
IP broadcast or multicast destination Not supported Only this address answers (0x52, or 0x40 for the broadcast MAC)
Fresh TTL in the echo reply Not supported The reply keeps the request's TTL. A new TTL needs a second checksum update (about 15 words, more than the earlier 256-word memory had free; not written). A request that arrived with TTL 1 through a router gets a reply that the router drops; RFC 1122 3.2.1.7 forbids sending TTL 0, which a request never carries after a router
VLAN tags (802.1Q), IPv6 Not supported EtherType 0x8100 and 0x86DD are ignored with 0x42
Sending ARP requests, ARP table, gratuitous ARP Not supported The firmware only answers, and the answer goes to the addresses in the request, so it needs no table
CSMA/CD Not supported The receiver shares the buffer and is not armed while sending, so there is no carrier sense or collision detection; a reply that collides is lost and the requester retries
Auto-negotiation Not supported The chip sends normal link pulses only (ETH_CFG bit 1); a switch falls back to 10BASE-T half duplex by parallel detection
Frames during a reply Not supported One buffer: the receiver is armed again only when the reply has been sent (table below); a frame that starts earlier is lost

Measured timing (test/test_net.py, RTL simulation)

Times from the end of the request's last bit cell on the receive line to the first edge of the reply on TD+/TD-, and to the end of the reply's TP_IDL. The firmware arms the receiver in the tick the transmitter becomes free, so the second column is when the chip can take the next frame (the test checks it is armed right after).

Request (bytes before the FCS) Response time Reply ends (ready again)
ARP request (60) 14.26 us 72.16 us
Echo, short, padded to 60 (ICMP 11 bytes) 18.30 us 76.20 us
Echo, Windows default (74) 24.32 us 93.42 us
Echo, odd length (75) 24.54 us 94.44 us
Echo, Linux default (98) 28.38 us 116.68 us
Echo, largest that fits (128) 34.36 us 146.66 us
UDP echo without checksum (60) 16.04 us 73.94 us
UDP echo, 18 data bytes (60) 23.62 us 81.52 us
UDP echo, 33 data bytes (75) 26.60 us 96.50 us
UDP echo, largest that fits (128) 36.66 us 148.96 us
Port unreachable for 1 data byte (60) 39.06 us 104.96 us
Port unreachable for 80 data bytes (122) 54.30 us 120.20 us

The response time includes the receiver's end-of-frame detection (no edge for 180 ns), the checks and the rewrite at one instruction per 40 ns tick (the checksum loops take about 10 ticks per 16-bit word) and the transmitter start. From 74 to 128 bytes it grows by 10.0 us, about 0.19 us per byte. The ICMP echo answers 0.24 us later than before UDP was added (the address rewrite moved behind the checksum update, shared with UDP). A port unreachable verifies the request's UDP checksum, copies 28 bytes and computes two new checksums (20 and 36 bytes). The tests assert below 20 us for ARP, below 40 us for both echoes and below 80 us for port unreachable (regression bounds; no RFC gives one).

Tests (test/test_net.py)

The requests are built field by field from the RFC layouts with struct, the expected replies come from the same field model with both checksums computed from scratch by an independent RFC 1071 function, and the ICMP checksum is also compared with RFC 1624 eqn. 3 applied to the request. The reply is decoded from the TD+/TD- edges by the Manchester decoder of test_eth.py and its FCS is checked with a bitwise CRC-32.

Test What it checks
test_net_arp Broadcast and unicast ARP requests answered byte for byte; a request for another IP (0x61) and an ARP reply (0x60) ignored; counters
test_net_ping Echo replies for Linux (98) and Windows (74) default pings, the largest frame (128), odd length (75), short padded (60), the RFC 1624 corner (request checksum 0xF7FF, reply 0x0000); 129 bytes ignored (0x41)
test_net_ignores_and_errors No reply and the right code for bad FCS, runt, bad IP checksum, bad ICMP checksum, total length beyond the frame, other IP, other MAC, IP to the broadcast MAC, IPv6, fragment, TCP, ICMP timestamp; a good ping afterwards is answered
test_net_settings One assembly, settings A, then B (A now ignored), then all zero (defaults stored and answered), then the hardware address filter: a frame for another MAC never reaches the firmware

Three more tests in the module check the frame buffer instructions that net.pe is built on, with short programs of their own (not net.pe):

Test What it checks
test_fw_reads_received_frame erxon, erxw (Z = 0 for a good frame), erxl and ld from the frame buffer at 0x20 + byte, absolute and through a register
test_fw_answers_in_place a program swaps the two MAC addresses of a received frame and sends it back with etx (length - 4, the chip appends the FCS), twice in a row, without the host
test_fw_buffer_ownership a frame buffer store lands while the buffer is free and is dropped while the receiver owns it

UDP tests (test/test_udp.py)

Run from a private directory (COCOTB_TEST_MODULES=test_udp; NET_FW=<path> runs another firmware file). The datagrams and the expected replies are built from RFC 768, 792, 862 and 1122 with struct and the RFC 1071 function of test_net.py, every checksum from scratch; a request whose UDP checksum computes to 0 is made by choosing its last two data bytes. check_unreach checks a port unreachable against the RFC rules alone (addresses, IHL 5, not a fragment, TTL above 0, protocol 1, total length, both checksums, type 3, code 3, unused 0, the request's 28 bytes unchanged), apart from the byte comparison that also fixes the firmware's free choices (identification and flags of the request, TTL 64, TOS 0). Every reply passes the Manchester decoder of test_eth.py: each edge on the 50 ns grid (2.5 clocks), gaps of 50 or 100 ns, the 300 ns positive TP_IDL start, the FCS.
