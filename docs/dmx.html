Source

ANSI E1.11 (USITT DMX512-A) itself was not available: ESTA hands it out only after a sign-in with contact details, which was not done. The firmware and the test models follow two secondary sources:

  • [AN] Microchip AN1076, "Using a PIC Microcontroller for DMX512 Communication" (DS01076A, 2007), which cites E1.11-2004: Figure 1 and Table 2. These are transmitter values.
  • [OLP] Open Lighting Project wiki, page "DMX", timing table (stated there to match DMX512-A 2004): the receiver column.

The two disagree on the transmitter's minimum mark after break (8 us in [OLP], 12 us in [AN]); the controller keeps 12 us.

Not implemented: RDM (E1.20, start code 0xCC) and other alternate start code protocols, the 8-bit/16-bit fine control conventions of fixtures, a second universe.

Pins

Pin Use
uio[0] (P0) Controller output, push-pull, high when idle. To the DI pin of an RS-485 transceiver (its DE tied high)
uio[1] (P1) Fixture input. From the RO pin of an RS-485 transceiver

The pins are .equ values (TX, RX). The controller and the fixture write different pins (the fixture writes none), so the two harts never touch the same bit of pin_out/pin_oe. For a loopback on one chip wire P0 to P1 (the test does this), or assemble with RX = 0 (assemble(text, {"RX": 0})): the fixture then reads the controller's pin through the pad.

Settings and host interface

Data memory, written by the host with DATA_W before the run (both harts stopped) and read with DATA_R at any time. Each hart checks its settings once at start and writes back what it uses (the controller its values, the fixture the skip count and FCNT); both read those bytes again before every packet.

Address Name Use 0 or out of range
0x00 NSLOT controller: slots after the start code, 1 to 224 0 or more than 224: 224
0x01 BRK controller: break, in bit times (4 us) 0: 44 (176 us); 1 to 22: 23 (92 us)
0x02 MAB controller: mark after break, in bit times 0: 4 (16 us); 1 or 2: 3 (12 us)
0x03 MBB controller writes it: mark before break, in bit times, at least 1, so that BRK + MAB + 11 x (NSLOT + 1) + MBB is at least 301 bit times (1204 us)
0x04, 0x05 FADRH, FADRL fixture: start address, 1 to 512 0: 1
0x06 FCNT fixture: channels, 1 to 15 0 or more than 15: 15
0x07 FPKT fixture counts packets with start code 0 (mod 256)
0x08 FALT fixture counts packets with another start code
0x09 FERR fixture counts framing errors: a first stop bit low that is not the start of a break
0x0A, 0x0B fixture: start address - 1 (used by it)
0x10 to 0x1E fixture: the channels from the start address. The first one, bits 7..2, is also on gpo (uo[7:2])
0x1F controller: start code, default 0
0x20 to 0x9F controller: slots 1 to 128. This is the frame buffer: the host writes it with ETH_W (frame byte 2k is the high byte of word k, slot n is frame byte n - 1)
0xA0 to 0xFF controller: slots 129 to 224 (DATA_W)

Universe byte n (n = 0 the start code, n = 1 to 224 slot n) is at address 0x1F + n, so the controller sends the bytes from 0x1F up.

Host FIFO to the controller (FIFO_W): pairs n v, universe byte n becomes v. n above 224: the pair is dropped. The controller takes one FIFO byte during the first stop bit of each slot, so a pair takes two slot times (88 us) and shows in the same packet when its slot comes later, otherwise in the next one. Nothing comes back through the FIFO; the fixture reports through the data memory only, so it never stalls on a full FIFO.

How it works

The controller runs on a twait grid of one bit time: every line change is two ticks after a twait, so all bits, the break, the mark after break and the mark before break are exact multiples of 4 us. The FIFO is read in the first stop bit, where 10 instructions fit easily in 100 ticks. At start it computes the mark before break from the settings with 16-bit arithmetic on two 8-bit registers.

The fixture looks for a break: a falling edge after which the line is still low 2000 ticks (80 us) later (waitp.to with the timer). After the break it waits for the line to go high (any mark after break) and reads the start code. Each slot is read from the falling edge of its start bit: the middle of the start bit (still low, else a glitch), then the middle of each data bit and of the first stop bit. A start code other than 0 sends it back to look for a break. It skips slots with a 16-bit count (start address - 1), stores FCNT slots and then looks for the next break. A low first stop bit after a slot of zeros is the start of a break if the line is still low 80 us after that falling edge; otherwise it is a framing error and the rest of the packet is dropped. A short packet (a break before the fixture's channels) is seen the same way, so the channels it did not reach keep their values.

Tests

test/test_dmx.py (cocotb). The receiver model and the model controller are written from [AN] and [OLP] (module docstring), not from the firmware. The receiver model records every edge of P0 and decodes it afterwards: a low of 88 us or more is a break; each slot is sampled in the middle of its 11 bits from its own start edge and every edge inside a slot must lie on a bit boundary; it checks per packet the [AN] transmitter limits (break, mark after break, bit time from the edge positions, break to break), the two stop bits, the slot count and the data. The model controller drives P1 with any break, mark after break, bit time, mark between slots, start code, slot count, and can make a stop bit low. Only the host interface (data memory addresses, FIFO pairs, gpo) is taken from this document. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_dmx

One run of the whole module on 2026-11-11: TESTS=9 PASS=9 FAIL=0, 180.8 ms of simulated time, 2190 s (36.5 minutes) of wall time on the loaded server. COCOTB_TEST_FILTER runs one test.

Controls

Each change was made in a copy of dmx.pe outside firmware/ (generated by string replacement into the run directory) and run with DMX_FW pointing at it, 2026-11-11. All six fail:

Change Test Caught by
d1 controller: one stop bit (the second stop bit's twait removed) test_dmx_controller_timing receiver model: stop bit 2 low in every slot, and an edge 40 us into the slot

d4 fixture: takes every start code test_dmx_fixture_start_codes_and_short the 0xCC/0x17/0x91/0xFF packets overwrite the channels with 0xEE
d5 fixture: break threshold 96 us instead of 80 us test_dmx_fixture_timing the packet with an 88 us break is not taken; the channels keep the previous packet's values

d6 shows why the controller checks n: 0x1F + n wraps around the address space onto the settings.

Limits

  • 224 slots at most from the controller (the data memory and the frame buffer from 0x20 up); E1.11 allows 512. A packet of 224 slots takes 10.1 ms. The frame buffer is shared with the Ethernet transmitter and receiver and the capture; slot changes to slots 1 to 128 from the FIFO are dropped while one of those owns it.
  • The fixture takes at most 15 channels and shows only the first one on the 6 general outputs (bits 7..2).
  • Break, mark after break and mark before break are whole bit times (4 us); E1.11's limits are all multiples of 4 us.
  • The fixture does not check the mark after break, the mark between slots, the second stop bit or the packet length; it takes any break of 80 us or more.
  • RDM and other alternate start code protocols are not implemented (the fixture only counts such packets).
  • Not tested: RS-485 transceivers, a real console or fixture, gate-level simulation, and the board.
