Target firmware

Behavior per request header (byte as received, bit 0 = start bit):

Header Request Reply
0xA5 DP read DPIDR OK, 0x1BA01477
0x8D DP read CTRL/STAT OK, bits 31..28 = {CSYSPWRUPACK, CSYSPWRUPREQ, CDBGPWRUPACK, CDBGPWRUPREQ}, each ACK equal to its REQ; all other bits 0
0xBD DP read RDBUFF OK, 0
0xA9 DP write CTRL/STAT OK, keeps bits 30 and 28 only
0x81 DP write ABORT OK, data ignored
0xB1 DP write SELECT OK, data ignored (DPBANKSEL is not decoded, address 0x4 is always CTRL/STAT)
other valid headers every AP access, DP read 0x8, DP write 0xC FAULT (0b100), no data phase
bad parity, stop or park no reply, lockout until a line reset

Choices and simplifications:

  • DPIDR 0x1BA01477: REVISION 1, PARTNO 0xBA, MIN 0, VERSION 1 (DPv1), DESIGNER 0x23B (Arm), the SW-DP value of the Cortex-M3 r1 parts (B2.2.5 field layout). It has even parity, and so do all CTRL/STAT values (each REQ comes with its ACK) and RDBUFF = 0, so the firmware always sends RDATA parity 0. Changing the IDCODE to a value with odd parity would need a parity 1 for that read.
  • FAULT for AP and unknown DP accesses: a real SW-DP sends FAULT only when a sticky flag is set (B4.2.4). FAULT is used here because the host then stops cleanly (Table B4-6: no data phase, can send new headers). WAIT would make OpenOCD and pyOCD retry until their timeout. CTRL/STAT reads afterwards still show no sticky flags.
  • Protocol errors go straight to lockout. B4.2.5 allows this: leaving the protocol error state on a DPIDR read is IMPLEMENTATION DEFINED, and without it the protocol error and lockout states are the same.
  • Line reset: 42 or more 1s, then a 0. A reset that starts while the target waits for a header first fills an 8-bit header (start, stop and park all 1, so it is a protocol error) and then needs 42 more 1s, so a 50-cycle reset is always seen. The spec reset is 50 HIGH plus two idle cycles (B4.3.3); the firmware needs only one idle cycle. CTRL/STAT keeps its value over a line reset (B4.3.3: only DLCR is reset).
  • The JTAG-to-SWD sequence (0xE79E, B5.2.2) is not decoded. After the first 50 1s its bits form a header with a bad parity, which leads to lockout, and the 50 1s after it are the line reset. The cocotb test sends the OpenOCD sequence (56 ones, 0xE79E, 56 ones, 2 idle).
  • Not implemented: WDATA parity check (WDATAERR), ORUNDETECT and the data phase it adds to WAIT/FAULT (the bit reads back 0, so the host knows it is off), DLCR and turnaround lengths other than 1, the DPIDR-only rule in the reset state (B4.3.3 makes other accesses UNPREDICTABLE), SWD protocol version 2 (TARGETSEL, dormant state).

Bit timing (from the firmware's view)

Rising edges of SWCLK numbered from the start bit, turnaround 1 cycle:

Edge Read, OK Write, OK FAULT
R1..R8 sample Start..Park same same
R9 drive ACK[0] (the Trn edge) same same
R10, R11 ACK[1], ACK[2] same same
R12 RDATA[0] release release
R13..R43 RDATA[1..31] R13 skipped (Trn), R14..R45 sample WDATA[0..31] R13 skipped (Trn)
R44 parity R46 WDATA parity (ignored)
R45 release, R46 skipped (Trn)

Every drive change happens after a SWCLK rising edge (B4.3.1: "When the target drives SWDIO, or stops driving it, signal changes are performed on the rising edge of SWCLK"). The skipped Trn edge is not sampled because nobody drives the line then; with the pull-up it would look like a start bit.

Response delay knob

N = ui_in[7:3] is read at each start bit. Each ACK and RDATA drive happens N ticks (N x 40 ns) later. Releases are not delayed. Measured in simulation at 250 kHz: SWCLK rise (at the pin) to SWDIO change (at the pin) = 10 + 2N clocks (200 ns at N = 0, 1440 ns at N = 31), the same for every edge of a DPIDR read.

Maximum SWCLK

test_swd_target_max_swclk runs the full session (JTAG-to-SWD, DPIDR, ABORT, SELECT, power-up handshake, RDBUFF, AP read and write, DP 0x8 / 0xC, DPIDR) at four phases of SWCLK against the 50 MHz clock, N = 0:

SWCLK Result
500, 750, 900, 925 kHz pass
950 kHz FAIL (the AP read gets its ACK one cycle late)

Maximum: 925 kHz with the test host, which samples SWDIO at the very end of the low phase.

Where the limit comes from: after the Park bit (R8) the firmware decides the reply with a chain of compares. The slowest path, a valid header that is not one of the six known ones (FAULT), takes about 26 ticks (about 1.04 us) from seeing R8 until it waits for R9. If R9 has already passed, ACK[0] goes out one cycle late. A period of at least about 1.05 us is needed, so about 950 kHz is the edge. The bit loops are much faster (a header bit needs 6 ticks, a driven bit 6 ticks plus N).

The second limit is the drive latency: data must be valid before the host samples it. With an ideal host that samples just before the next rising edge, the period must be longer than 10 + 2N clocks plus the host setup; for N = 31 that is about 1.5 us, so about 650 kHz. A probe that samples earlier (for example right after the falling edge) gives the target only half a period, which halves both limits. When this was written, the sample point of the ST-Link was not known.

Host firmware

SWCLK period is 2 x HALF ticks (HALF = 10: 800 ns, 1.25 MHz), and each phase is HALF ticks: every SWCLK edge comes one tick after a period boundary. SWDIO changes after the falling edge, and the host samples it at the rising edge on which the target changes it: the shin one tick after high CLK reads the level SWDIO had at that edge, because the input passes two synchronizer flip-flops. Until 2026-11-11 the host sampled one tick before raising SWCLK, so a read cycle was HALF + 1 ticks low and HALF - 1 high, and the cycles where reads and writes meet were 2 x HALF - 1 and 2 x HALF + 1 ticks (760 and 840 ns at HALF = 10). Sequence: 56 HIGH, 0xE79E LSB first, 56 HIGH, 2 idle, header 0xA5, Trn (released on the falling edge), ACK, 32 data, parity, Trn, 2 idle (driven low). The data phase is always clocked, also when the ACK is not OK (Table B4-6 asks the host to back off for a possible data phase).

Host FIFO output (5 bytes): DPIDR bytes 0..3 (LSB first), then {parity, ACK[2:0]} in bits 3..0. ACK OK reads as 1; no reply reads as 7 (pull-up).

Generalized firmwares

firmware/swd_host_gen.pe and firmware/swd_target_gen.pe are checked in simulation against an ADIv5 model, and on the FPGA board against each other on one chip (below); swd_target_gen.pe has also met a real probe (2026-11-19, Real-hardware tests below), swd_host_gen.pe has met an MCU too (2026-11-19, below). The first firmwares swd_target.pe and swd_host.pe stay separate files; swd_host.pe got the same read-cycle change as swd_host_gen.pe in commit 349139e (SWCLK rises before the sample instruction, so both phases of a read cycle are HALF ticks). Pins and wire timing are those of the sections above. Together they are 428 words (173 + 255), more than the earlier 256-word program memory held. With the 512-word memory one chip runs its host (hart 0) against its own target (hart 1) on the same pins: test/test_mem512.py test_swd_self_debug_one_chip (P0/P1, every result checked against the ADIv5 register model) and FPGA self test section 15 (P2/P3; 512-word design, bit 1110e built from commit 9feda71, 2026-11-11: 271 passes of the whole self test, 0 fails; log outside the repository). That board run used swd_host_gen.pe from before commit 349139e; the read-cycle change in that commit is checked in simulation only (test_swd_gen, test_mem512). swd_target_gen.pe has not changed in code since the board run. SWCLK is set to 625 kHz there (H_HALF = 20), because the target firmware tops out near 1.2 MHz (below) and the host default is 1.25 MHz.

Host: swd_host_gen.pe (173 words)

The PC orders any DP or AP register access through the FIFO; the firmware builds the packet request with its parity, runs the turnaround, ACK and data phases, checks the RDATA parity, retries WAIT and reports the result.

Settings (DATA_W while the harts are stopped; a 0 selects the default):

Address Meaning Default
0x00, 0x01 SWCLK half period in ticks (LSB first). SWCLK = 1 / (2 x HALF x 40 ns) 10 (1.25 MHz)
0x02 WAIT retries: a request is sent up to retries + 1 times 100
0x03 idle cycles (SWDIO low) after each transfer and before each retry; used as written 0: none (B4.1.4 allows the next start bit right away)
0x04 to 0x07 used by the firmware (data buffer)

Commands (FIFO_W 0x20):

Byte Command Followed by
0x00 to 0x0F transfer: bit 0 APnDP, bit 1 RnW, bit 2 A[2], bit 3 A[3] (bits 7..5 ignored) a write: 4 data bytes, LSB first
0x10 line reset: 56 HIGH, 2 idle
0x11 JTAG-to-SWD: 56 HIGH, 0xE79E LSB first, 56 HIGH, 2 idle

Example: DP read of CTRL/STAT is 0x06, AP write of DRW is 0x0C followed by 4 bytes, DP read of RESEND is 0x0A.

Replies (FIFO_R 0x21): a read gives 4 data bytes (LSB first; 0 unless the ACK is OK) and then the status byte; a write gives the status byte; 0x10 and 0x11 give 0x00 when done.

Status bits Meaning
2..0 ACK of the last try as received: 1 OK, 2 WAIT (retries used up), 4 FAULT, 7 no reply (line not driven, pull-up), other values an invalid ACK
3 RDATA parity error (read with ACK OK); the data bytes are the ones received
7..4 number of WAIT replies during this transfer, up to 15

On the wire (B4.2, Table B4-6): SWDIO changes after falling edges and is sampled at rising edges (the level just before the edge, as in swd_host.pe). Read OK: ACK, 32 data bits, parity, one turnaround cycle. Write OK: one turnaround cycle, then 32 data bits and their parity, driven by the host. WAIT and FAULT: one turnaround cycle, no data phase. No valid ACK: the host clocks 34 cycles with SWDIO released (a possible data phase and its turnaround) before it goes on. Then the idle cycles. On WAIT the same request is sent again after the idle cycles; when the retries are used up the status carries ACK 2. FAULT is reported (the PC then reads CTRL/STAT and writes ABORT). After a no-reply the PC sends 0x10 and reads DPIDR again. After an RDATA parity error the PC may read RESEND (0x0A) if the target implements it.

SWCLK runs only while the firmware has a transfer to do: it stops between FIFO commands, and the cycles at a byte boundary and around the ACK are longer than the others (the firmware works between the bits; SWD allows any stretched cycle). For the same reason the late flag of STATUS is always set and says nothing here.

Target: swd_target_gen.pe (255 words)

Settings: 0x0C to 0x0F DPIDR (LSB first), written by the host before the run. There is no default (the 11 words it takes did not fit the earlier 256-word program memory); after power-up the value is 0, which is not a valid DPIDR. Example values: 0x0BB11477 (Arm SW-DP DPv1 with MIN = 1, which fits this model: no transaction counter, no pushed compare) or 0x1BA01477 (the value of swd_target.pe).

State that the PC can read while it runs: DATA_R 0x10 to 0x13 CTRL/STAT, 0x14 to 0x17 RDBUFF, 0x18 selected AP bank (0 or 0x10), 0x19 protocol error count (every request that got no reply because of a bad parity, stop or park bit or a RESEND read; counts up from 0 at start and wraps at 256; the 0xE79E bits of a JTAG-to-SWD sequence and a line reset that starts while the target waits for a header each count one, as in swd_target.pe they are protocol errors); CAP_R words 0x00 to 0x0F the AP registers (bank 0 CSW, TAR[63:32], TAR; bank 0xF from word 8: BASE[63:32], BASE, CFG, IDR, each 4 bytes LSB first, frame buffer byte 2k = hi byte of word k), words 0x20 to 0x3F the 64-byte memory behind DRW. The memory is not cleared at start: the PC may fill it with ETH_W (word 0x20 on) while the harts are stopped. The firmware keeps its AP model in the frame buffer, so Ethernet and the capture must stay idle while it runs.

DP registers:

Request Reply
R 0x0 DPIDR always OK, the setting
R 0x4 CTRL/STAT always OK. Bits 31..28 {CSYSPWRUPACK, CSYSPWRUPREQ, CDBGPWRUPACK, CDBGPWRUPREQ}, each ACK equal to its REQ; bit 7 WDATAERR; all other bits 0
R 0x8 RESEND protocol error: no reply, then lockout until a line reset (B2.2.8 allows a target that cannot resend to do this)
R 0xC RDBUFF the result of the last AP read (B2.2.7); read again it gives the same value
W 0x0 ABORT always OK. WDERRCLR (bit 3) clears WDATAERR; DAPABORT and the other clear bits have nothing to act on
W 0x4 CTRL/STAT keeps CSYSPWRUPREQ and CDBGPWRUPREQ
W 0x8 SELECT APBANKSEL bit 0 picks bank 0 (0) or bank 0xF (1); APSEL and DPBANKSEL are not decoded
W 0xC reserved in DPv1, ignored

Every request other than a DPIDR read, a CTRL/STAT read and an ABORT write gets FAULT, with no data phase, while WDATAERR is set (B4.2.4). A WDATA parity error discards the write and sets WDATAERR (B4.1.6); this applies to every write, ABORT and the ignored 0xC included.

AP (a MEM-AP model; every APSEL value reaches it):

Bank, offset Register Behaviour
0, 0x00 CSW Size reads 0b010 (word only, as for the APB2/APB3 MEM-AP of Appendix E1), DeviceEn 1, TrInProg 0. AddrInc is bit 4 of the written value: 0b10 reads 0b00 as C2.2.2 requires without packed transfers, 0b11 (reserved) reads 0b01. Bits 31..8 are kept as written
0, 0x04 TAR 32 bits, read and write
0, 0x08 TAR[63:32] read and write, not used for addressing (CFG.LA = 1, so this offset is a register and not RES0)
0, 0x0C DRW word at TAR[5:2] in the 64-byte memory (TAR[31:6] and [1:0] ignored). With AddrInc 0b01, TAR[7:0] increases by 4 after each access; a write increments only when its parity is good
0xF, 0xF0 BASE[63:32] 0
0xF, 0xF4 CFG 0x2 (LA)
0xF, 0xF8 BASE 0x2: ADIv5 format, no debug entry
0xF, 0xFC IDR 0x04770002: designer Arm (JEP106 bank 4, 0x3B), class MEM-AP, type APB2/APB3

Writes to bank 0xF are ignored. AP reads are posted (Table B4-4): the reply carries the result of the previous AP read and the new result goes to RDBUFF; the first AP read after the start replies 0.

Timing: the firmware takes the request bits APnDP..A[3] in one call, decodes during the cycle that carries the parity bit, then takes parity, stop and park and checks them before the ACK. Drives use the transmit routine of swd_target.pe, so every ACK and RDATA edge has the same latency: test_swdg_target_skew loads both firmwares in the same bench and gets equal lists of SWCLK-rise-to-SWDIO-change times for a DPIDR read, 9 + 2N clocks for N = 0, 1, 5, 17, 31 (the 10 + 2N above comes from the other bench, whose SWCLK edges sit at a different phase of the 50 MHz clock).

HALF = 4 is the smallest setting at which the bit loops keep the nominal period (a read bit takes 3 instructions after its sampling twait, so a half period of 3 ticks comes late). Below it the clock is set by the loops: 240 ns, 4.17 MHz. The longest cycles are the byte boundaries and the ACK decision. Both output delays pass at every setting. From HALF = 4 up the test asserts that no SWCLK cycle in a transfer is shorter than 2 x HALF ticks and that the median is exactly that, to the clock; test_swd_host asserts that every phase of swd_host.pe is HALF ticks.

SWCLK 2 idle cycles no idle cycles
900 to 1150 kHz pass pass
1200 kHz pass FAIL (phase 1)
1250 kHz FAIL not run

Maximum: 1200 kHz with two idle cycles, 1150 kHz with requests back to back. Both failures are a DPIDR read that gets no reply: the request decode in the cycle after A[3] (the compare chain down to DPIDR, then the always-OK setup, about 20 ticks with the return from the bit routine) has to end before the parity bit's rising edge, which at 1.25 MHz comes 20 ticks after A[3]. A first version with CTRL/STAT at the end of the chain reached 1050 kHz; ordering the chain and moving work out of the gap before RDATA[0] and before the WDATA parity bit gave the rest. The same caveat as for swd_target.pe applies: the test host samples SWDIO at the very end of the low phase; a probe that samples earlier leaves the target less time.

host No turnaround before WDATA (the ldi r1, 1 and call rbits at wdat replaced by nop) test_swdg_host_transfers The DP write to 0x8 (SELECT) comes back with status 0x7 (no valid ACK) where the model wants OK

Spec references

ARM IHI 0031G, Arm Debug Interface Architecture Specification ADIv5.0 to ADIv5.2 (read from the Arm PDF for this work):

  • B4.1.1 operation phases, no turnaround between ACK and RDATA, Trn after RDATA and between ACK and WDATA
  • B4.1.3 turnaround, default one cycle; B4.1.4 idle cycles (line LOW); B4.1.5 LSB first, OK = 0b001 sent as 1, 0, 0; B4.1.6 even parity over APnDP, RnW, A[2:3] and over the 32 data bits
  • B4.2 header fields (Start 1, Stop 0, Park 1); B4.2.4 FAULT; B4.2.5 protocol errors, no reply, protocol error and lockout states
  • B4.3.1 target samples and changes SWDIO on SWCLK rising edges; B4.3.2 pull-up; B4.3.3 line reset (50 HIGH + 2 idle)
  • B5.2.2 JTAG-to-SWD select sequence 0xE79E LSB first
  • B2.1.3 DPv1 register map; B2.2.2 CTRL/STAT bits 31..28; B2.2.5 DPIDR fields; B2.2.7 RDBUFF

Not confirmed from IHI 0031G: the host timing (host drives on the falling edge, samples on or just before the rising edge). The spec says nothing about it in B4.3.1. The test host follows the Arm DSTREAM manual ("The probe writes data to SWDIO on the falling edge ... reads ... on the rising edge") and the CMSIS-DAP code (it samples SWDIO while SWCLK is low, just before raising it).

Real-hardware tests

Target firmware against an ST-Link V2 / a broken-off Nucleo ST-Link V2-1

Wiring, with the chip running swd_target.pe or swd_target_gen.pe:

Probe Chip
SWCLK (ST-Link V2 20-pin pin 9; Nucleo ST-Link CN4 pin 2) uio[0]
SWDIO (ST-Link V2 pin 7; CN4 pin 4) uio[1], plus a 10 k to 100 k pull-up to 3.3 V
GND (ST-Link V2 pin 4 and others; CN4 pin 3) GND
VAPP / target voltage sense (ST-Link V2 pin 1; CN4 pin 1) 3.3 V of the chip board, so the probe sees a target voltage
NRST (CN4 pin 5) not connected

On a whole Nucleo board the two CN2 jumpers must be removed so that the ST-Link uses CN4; a broken-off ST-Link part already does. The CN4 numbering is from the Nucleo user manuals (UM1724 / UM1956), not checked against the actual part.

Settings:

  • With swd_target_gen.pe, first write the DPIDR into its data memory, 0x0C to 0x0F, LSB first (77 14 A0 1B for 0x1BA01477), after loading and before the probe connects. There is no default: without this step the probe reads DPIDR 0 (SWD DPIDR 00000000, measured 2026-11-19 at 100, 240 and 480 kHz). With fpga/zcu104_demo/host/pe_demo.py the bytes go in the data map of the image ({"12": [119, 20, 160, 27]}), which pe_demo.py load <images.json> swd_target_gen writes with the program. The AP IDR needs no setting: the firmware writes 0x04770002 itself at start. swd_target.pe has the DPIDR built in.
  • Adapter speed: start at 480 kHz (an ST-Link step). For swd_target.pe 950 kHz is just above the simulated limit (925 kHz) and should fail, which is itself a measurement; the simulated limit of swd_target_gen.pe is higher (1150 kHz with requests back to back, 1200 kHz with idle cycles). Lower steps: 240, 125, 100 kHz.
  • No reset line: OpenOCD reset_config none, pyOCD -O connect_mode=attach.
  • OpenOCD needs the dap-direct transport to run its own ADI code (ST-Link firmware V2J24 or later): openocd -f interface/stlink-dap.cfg -c "transport select dapdirect_swd" -c "adapter speed 480" -c "reset_config none" -c "swd newdap chip cpu -enable" -c "dap create chip.dap -chain-position chip.cpu" -c init. With the older hla transport the probe firmware does the connection and OpenOCD prints less.
  • pyOCD: pyocd commander -t cortex_m -f 480k -O connect_mode=attach.

Expected: the probe reads DPIDR 0x1BA01477 and powers up the debug domain; the first AP access (AP IDR) gets FAULT and the tool stops with an error. Expected log lines (exact wording not checked):

  • OpenOCD: Info : SWD DPIDR 0x1ba01477, then an error on the AP access.
  • pyOCD: DP IDR = 0x1ba01477 (v1 rev1), then a transfer fault on the AP.

To measure the probe's timing tolerance, repeat at each adapter speed for N = 0..31 and note the highest N that still reads the right DPIDR; that bounds when the probe samples SWDIO after the rising edge. A logic analyzer on SWCLK/SWDIO (or the chip's own capture, 0x30) shows the probe's real sample point.

Host firmware against NUCLEO-L432KC, NUCLEO-F446RE, NUCLEO-G474RE

Connect uio[0] to the MCU SWCLK (PA14), uio[1] to the MCU SWDIO (PA13), and GND. The MCU has its own SWD pull-up, so no extra resistor is needed. The on-board ST-Link must not drive these lines: on NUCLEO-F446RE and NUCLEO-G474RE (Nucleo-64), take PA13/PA14 from the morpho header CN7 pins 13/15 and keep the ST-Link idle (no debugger session open, or held in reset). NUCLEO-L432KC (Nucleo-32) does not bring PA13/PA14 out to its headers, so it needs the ST-Link solder bridges opened or wires on the ST-Link side; the exact bridges are not checked here. Run swd_host.pe and read 5 bytes from the FIFO (0x21).

Expected FIFO bytes for all three Cortex-M4 parts: 77 14 A0 2B 01 (DPIDR 0x2BA01477, ACK OK, parity 0).

Board MCU Expected DPIDR Source
NUCLEO-F446RE STM32F446RE 0x2BA01477 STM32F4 reference manuals RM0402 / RM0430 list the SW-DP IDCODE 0x2BA01477 for Cortex-M4 F4 parts. RM0390 (F446) itself not checked.
NUCLEO-L432KC STM32L432KC 0x2BA01477 RM0351 (STM32L4x5/x6) lists 0x2BA01477. RM0394 (L41x..L45x, which covers L432) not checked.
NUCLEO-G474RE STM32G474RE 0x2BA01477 A read of 0x2ba01477 is reported on the ST community forum. RM0440 not checked.

The three values are not confirmed from each part's own manual. STM32 parts with an SWJ-DP start in JTAG mode, which is why the host firmware sends the JTAG-to-SWD sequence.
