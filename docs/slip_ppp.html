File Role Words
firmware/slip_ppp.pe Packet framing over a UART (115200 bit/s 8N1). Hart 0 frames host packets: SLIP (RFC 1055: END, ESC ESC_END, ESC ESC_ESC, END) or PPP in HDLC-like framing (RFC 1662: flag, octet stuffing of 0x7E, 0x7D and the control characters flagged in the sending ACCM, FCS-16 computed on the fly, flag). Hart 1 takes frames from the line and reports them: SLIP un-escaping; PPP flag hunt, removal of control characters flagged in the receiving ACCM, un-escaping, abort (0x7D 0x7E), FCS check, short and long frames. It fills one of two buffers while it hands the last good frame in the other to the host without waiting, so frames can come back to back. Each hart picks its mode from the data memory. 272 of 512 (hart 1 from word 102)

This is the octet-oriented framing of PPP over asynchronous serial lines; firmware/hdlc.pe does the bit-synchronous form (flags, zero insertion) on a clock and data line. No RTL change: tset/twait, shout.lsb, shin.lsb, the CRC unit (CRC-16/X.25 with crc.lsb), ld/st on the frame buffer, the host FIFO. Checked in simulation only, not on a board.

Sources

Document Used for
RFC 1055, "A Nonstandard for Transmission of IP Datagrams over Serial Lines: SLIP" (1988) END = 0300 (0xC0), ESC = 0333 (0xDB), ESC_END = 0334 (0xDC), ESC_ESC = 0335 (0xDD); an END before the packet flushes line noise and the receiver ignores empty packets; after ESC an octet other than ESC_END or ESC_ESC is a protocol violation and the sample receiver keeps it
RFC 1662, "PPP in HDLC-like Framing" (1994) 3.1 FCS transmitted least significant octet first; 4.1 flag 0x7E; 4.2 octet stuffing: after the FCS is computed, each flag, control escape 0x7D and octet flagged in the sending ACCM is sent as 0x7D and the octet XOR 0x20, with the examples; on reception, octets below 0x20 flagged in the receiving ACCM are removed before the FCS computation, 0x7D is removed and the next octet XORed with 0x20, unless it is a flag (abort); 4.3 invalid frames (shorter than 4 octets with the 16-bit FCS); 5: octets least significant bit first, 8 bits, no parity; 7.1 ACCM: default 0xFFFFFFFF, bit 0 maps NUL; Appendix C: the 16-bit FCS (0x8408, preset 0xFFFF, complemented; good residue 0xF0B8)

Pins

Constant Default Use
TX P0 UART out, high when idle
RX P1 UART in. Assemble with RX = 0 for a loopback on one chip

Host interface and data memory

Host to hart 0: n (1 to 255), then n octets (for PPP the whole frame between the flags without the FCS: address, control, protocol, information). Hart 1 to host: n, then n octets (PPP: without the FCS). Only good frames are reported; the rest is counted.

The receiver has two 64-byte buffers in the frame buffer (0x20 and 0x60): n at the start, then up to 62 octets. When a frame is good it becomes the report and the next frame goes into the other buffer. The report goes out with txb.nb, up to two bytes after each octet received and after each bit time of idle line, so the receiver never stops to wait for the host. A good frame that ends while the report before it is still going out is dropped and counted (ROVR): at two bytes per octet, a frame shorter than half the previous one cannot follow it back to back.

Address Use
0x00 TMODE, 0x01 RMODE 0 SLIP, 1 PPP (read once at start)
0x02-0x05 TACC sending ACCM: bit k of byte j maps octet 8 j + k (the LCP option sends the same map most significant octet first)
0x06-0x09 RACC receiving ACCM, same layout
0x0A TCNT frames sent
0x0B RCNT frames reported
0x0C RFCS PPP frames with a wrong FCS
0x0D RSHT PPP frames shorter than 4 octets
0x0E RABT PPP frames aborted by 0x7D 0x7E
0x0F RLNG frames longer than 62 octets (FCS included), or with a stop bit low
0x10 ROVR good frames dropped because the report before them was still going out
0x11-0x15 buffer in use, its end, drop flag, report pointer and bytes left (used by the receiver)
0x20-0x5F, 0x60-0x9F the two receive buffers (frame buffer)

Timing

BIT 217 ticks (8.68 us, 115,207 bit/s, +0.006 %). Every edge is one tick after a period boundary of the character's grid, and the octets of a frame follow each other without a gap while the host keeps the FIFO filled. The sender takes each octet from the host as it goes; when the FIFO is empty it waits and starts the grid again with the next octet, so a slow host only adds idle time between octets, which asynchronous framing allows (and the late flag stays 0). The receiver finds the start edge within a tick (waitp.to, between report bytes), samples each bit in its middle and checks the stop bit.

Limits

  • 16-bit FCS only (no 32-bit FCS), no address and control field compression handling (the host builds the frame), no LCP: the ACCMs are set by the host.
  • The sending ACCM covers 0x00 to 0x1F only (RFC 1662 allows up to 256 bits; 0x7E and 0x7D are always escaped).
  • Frames up to 62 octets (FCS included) are received (255 can be sent); a short frame right after a long one is dropped (ROVR), because the receiver does not wait for the host.
  • Simulation only: no board, no gate-level run.
