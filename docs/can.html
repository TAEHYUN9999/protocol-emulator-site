Two firmwares use the same pins: firmware/can_gen.pe (CAN 2.0A and 2.0B, the general one, simulation only) and firmware/can.pe (the first CAN 2.0A version, unchanged, with its own test). This file first describes can_gen.pe; the part from "CAN 2.0A firmware (firmware/can.pe)" on is the description of the earlier version.

CAN 2.0A/2.0B firmware (firmware/can_gen.pe)

Checked in simulation, and on an FPGA build of the chip against a CAN controller (see "Board check" below). Standard (11-bit) and extended (29-bit) identifiers, data and remote frames, automatic retransmission, error detection with error flags, fault confinement (transmit and receive error counts, error passive, bus off; section "Fault confinement" below), bit timing and a receive filter from the data memory. It uses all 512 words of program memory (it filled the earlier 256-word memory before fault confinement and the overrun count were added; the transmit readback at the sample point took it from 409 to 510 words; the ACK from the slot start took 15 more and other code was made 16 words shorter, 509; the bus idle loop of 2026-11-18 the last 3) and runs on both harts (CTRL = 3, START1 = label hart1):

  • Hart 1 is the bus engine. It receives every frame on the bus, its own frames too, and sends the stored request when the bus is idle. Per bus bit it samples, resynchronizes, destuffs, feeds CRC-15 with the crc instruction, tracks the fields (IDE, RTR, DLC) and stores the bits into the record buffer. Sending, it inserts the stuff bits, takes the CRC field from the CRC register and reads every bit back at the sample point; the bookkeeping of a bit it sends runs before that readback (section Timing).
  • Hart 0 is the host side. It stores a transmit request from the host FIFO for hart 1. When hart 1 has finished a record, hart 0 copies it to its own buffer and frees the record buffer at once (about 100 ticks), then filters and forwards the copy.

The harts talk only through memory. Hart 1 never executes rxb or txb, so a slow host cannot stall the bus timing (the old firmware could). The copy lets hart 1 take the next frame 3 bits after the last one although the host needs longer than that to read 18 bytes (about 85 us at SPI clk/10 with STATUS polling, by calculation; the filter test first failed because it looked after 80 us). If hart 0 still owns the record buffer when the next frame starts (the host has not read the copy before yet another frame ended), that frame is received, acknowledged and checked but its record is dropped, and the count OVR (data memory 23, section "Overrun count" below) goes up by one. Pins and transceiver wiring are the same as for can.pe (P0 = TXD, P1 = RXD, dominant = 0), see below; P0 stays released (high impedance) until the chip first drives it, so the transceiver's TXD input needs a pull-up.

Settings (data memory, DATA_W before CTRL = 3)

All timer values are 16-bit, high byte first, in ticks (40 ns). The host converts the bit timing into them; settings() in test/test_can_gen.py is the reference. With BIT = ticks per bit, SP = ticks from the bit start to the sample point and SJW = the late part of the resync window in ticks:

Hart 1 sets OVR (23) to 0 when it starts and 19 to 22 after the 11 recessive bits of the bus integration, and again after a bus off; the host does not write them (settings() writes 0 there, which is the same). TT1 and TT2 depend on SP and BIT only: TT1 and TT2 time the transmitted bits, and TT2 also the ACK of a received frame from the CRC delimiter's sample to the slot start; TS1, WIN and RST are the receive settings. Until 2026-11-18 the transmit readback was tied to the receive window (TT1 = RST - 2, the next bit start at the end of the window), so the chip read its own bits at SP - SJW; a host that writes only addresses 0 to 18 in the old form (TT1 = RST - 2, nothing at 24) does not work with this firmware.

Overrun count

A frame whose start finds the record buffer still owned by hart 0 (nrec: the status byte at frame buffer 0x42 is not 0) is received, acknowledged and checked into the drop buffer, and its record never reaches the host. This holds for an own frame too: its 0x81 record can be dropped, and the host then finds the end of its request by TXREQ and OVR (section "Host to chip: one transmit request", the rule there). Hart 1 counts each such record in OVR once, at the end of the frame (after fin at the end of EOF, or at ef7 after its error flags, so an error frame and a frame that leads to bus off count too). The count is not in the SOF path on purpose: on an own frame the drop branch is one of the two longest paths between a tsetr and the twait of a readback, 32 instructions from the SOF tsetr (nrec, the bookkeeping of the SOF bit and the choice of the next one), which TT1 = SP - 3 allows from SP = 36 ticks on, the transmit limit (docs/petime.md, the rule; section Timing); the four instructions of a count would raise that limit to 40 [calculated]. At the end of the frame the intermission wait follows, which only starts a few ticks later. The host reads OVR with DATA_R at any time; it cannot clear it while the harts run (DATA_W is dropped then), so it keeps the last value it read and takes the difference.

The constants 6, 4 and 7 (receive) and 3 and 8 (transmit) are the instruction path lengths of this firmware between a timer event and the tsetr that starts the next one, so that the RX bit period with and without an edge is exactly BIT, a resync puts the sample SP ticks after the edge, the TX readback is at the sample point and the TX bit period is exactly BIT. A frame received at +-1 % and a frame sent and decoded by the model at the nominal rate check these numbers in the test; the two-chip test of can_j7.md measures the readback point to the clock.

There are no .equ defaults for the settings: the host always writes them. Soft reset keeps the data memory and the frame buffer, so a restart without DATA_W reuses the last settings; TXREQ (address 18) must be 0 at start. The record status byte (frame buffer 0x42) is cleared by the hardware reset or by hart 0 when it copies the record; a soft reset in the 100 ticks between the end of a frame and that copy would leave it set.

Runtime variables live in the frame buffer: 0x21 to 0x24 (hart 1; 0x24 holds a stuff bit the transmitter sends next), the request at 0x30 to 0x3C, the record at 0x40 to 0x51, the drop buffer at 0x60 to 0x71 and hart 0's copy at 0x74 to 0x85. Ethernet and the capture must stay unused.

Host framing

Host to chip: one transmit request

k, then k bytes: the frame bits SOF .. last data bit, destuffed, packed MSB first, the last byte padded with zeros (k = 3 to 13). Bit 7 of the first byte is SOF and must be 0. The bits are exactly the frame layout of the specification:

  • standard: SOF, ID10..ID0, RTR, IDE = 0, r0, DLC3..DLC0, data (19 + 8 x n bits)
  • extended: SOF, ID28..ID18, SRR = 1, IDE = 1, ID17..ID0, RTR, r1, r0, DLC3..DLC0, data (39 + 8 x n bits)

n = 0 for a remote frame (RTR = 1, any DLC), otherwise min(DLC, 8). request() in test/test_can_gen.py builds it. The chip computes CRC-15 and the stuff bits.

Hart 0 takes a request only when none is in flight (TXREQ = 0). Hart 1 sends it at the next bus idle and repeats it after a lost arbitration or any error until it is acknowledged; the record of the acknowledged frame (status 0x81) clears TXREQ. A host sends the next request after it has read status 0x81, or after the rule below found the request done. The record of an own frame is dropped like any other when the frame starts while hart 0 still owns the record buffer (section "Overrun count"): at 500 kbit/s with a request arriving while the chip receives, hart 0 reads the request bytes with blocking rxb and the chip starts its frame 3 bits after the other node's EOF, so the 0x81 record of an acknowledged frame can be lost (test/test_can_b500.py::test_b500_host_during_rx: 4 of 12 request points, at 20, 40, 50 and 60 bits into the other node's frame, each with TXREQ 0 and OVR one higher). Rule for the host: if no 0x81 record has come within twice the longest frame (160 bits with worst stuffing, the tail and the intermission, so 640 us at 500 kbit/s), read TXREQ (address 18) and OVR (address 23) with DATA_R; TXREQ = 0 with OVR above the value read before the request means acknowledged, record dropped; TXREQ not 0 means the frame is still in flight (arbitration, errors), so keep waiting. A frame that never gets an ACK is repeated forever; the host stops it with a soft reset.

Chip to host: one record per frame on the bus

18 bytes, always: end, left, status, then 15 bytes of the frame bits as received, destuffed, from SOF on, MSB first. end is the chip address of the last (partial) byte: end - 0x43 bytes are full, then 8 - left bits sit in the low bits of the next byte, so the bit count is 8 x (end - 0x43) + 8 - left. A complete frame ends with the 15 CRC bits and the CRC delimiter, so it carries 19 + 8 x n + 16 (standard) or 39 + 8 x n + 16 (extended) bits. record_bits() in the test splits a record.

Status Meaning
0x01 received frame of another node, CRC good, delimiter recessive, ACK sent, ACK delimiter and EOF recessive
0x81 own frame sent and acknowledged (TXREQ cleared, request done)
0x21 own frame lost arbitration; the record is the winning frame, received good (the request is repeated)
0x02 stuff error (six equal bits)
0x03 CRC error, or a dominant CRC delimiter (no ACK sent)
0x04 form error: dominant ACK delimiter or EOF bit
0x85 bit error in an own frame (read back recessive for dominant, or dominant for recessive after the arbitration field or at a stuff bit)
0x86 ACK error: own frame not acknowledged

Bit 7 = own frame, bit 5 = own frame lost arbitration; the low bits are the result (1 good, 2 stuff, 3 CRC, 4 form, 5 bit, 6 ACK). Every error record is followed by the error flag on the bus. 0x84 is also possible for an own frame (dominant ACK delimiter or EOF bit; anything earlier in an own frame is a bit error), and 0x22 to 0x24 for errors in the winning frame after a lost arbitration.

Receive filter

A good frame of another node (status 0x01) is forwarded only if, for i = 0 to 3, (record byte i xor FILT[2i]) and FILT[2i+1] = 0. Record bytes 0 to 3 are frame bits 0 to 31: SOF, ID10..ID0, RTR, IDE, r0, DLC, first data bits for a standard frame; SOF, ID28..ID18, SRR, IDE, ID17..ID0 for an extended frame. So one mask/value pair covers an 11-bit identifier plus IDE, or a 29-bit identifier plus IDE (filt_for() in the test). A mask of 0 accepts everything (the default). The chip ACKs every good frame whether or not it passes; own frames, lost-arbitration records and error records always reach the host.

Errors and error frames

Error (CAN 2.0 B error detection) Detected Error flag starts
Bit error own frame: read recessive for dominant anywhere, dominant for recessive after the arbitration field (from IDE of a standard frame, from r1 of an extended one) and at any stuff bit next bit start
Stuff error sixth equal bit from SOF to the end of the CRC sequence, also the stuff bit after the CRC at once (inside the next bit)
CRC error CRC register not 0 after the last CRC bit (since 2026-11-18; before: not 0x4599 << 1 after the CRC delimiter) at the ACK delimiter (the standard says: after it)

While error active the error flag is six dominant bits; while error passive it is a passive error flag (the chip drives nothing and waits for six equal bits, see Fault confinement). Then the chip waits for the bus to turn recessive (the flags of other nodes); that first recessive bit, 7 more delimiter bits and 3 intermission bits follow (11 bits; before fault confinement was added the firmware waited 10, one bit short of the 8-bit error delimiter of Bosch 2.0 Part A 3.1.3). A dominant level in these 11 bits is taken as the next SOF. An error flag of another node shows as a stuff error (six dominant bits) and is answered with the chip's own flag.

Timing

Receiving, at the sample point hart 1 reads RXD twice, one tick (40 ns) apart: into the bus history (stuffing) and into the byte (data and CRC); an edge inside those 40 ns could give the two different values, as in the old firmware. Then it runs proc for the bit. proc takes at most 24 instructions (end of the header of a data frame with DLC 0); the CRC update is one crc instruction instead of the 12 the old firmware needed. Per bit:

  • Receive: sample; after a recessive sample waitp.to watches for a recessive to dominant edge from 9 ticks after the sample to the end of the window (BIT - SP + SJW after the sample). An edge restarts the bit time, the next sample is SP after it (unlimited jump inside the window); no edge: the next sample is BIT after the last. proc runs after the window, so RST >= 28 ticks: SP - SJW >= 31 and SP >= 34 ticks.
  • An edge later than the window is not used at all (the standard would still correct by SJW), so the late window must cover the whole drift between two falling edges: up to 10 bits (stuffing) times the sum of both clock errors. SJW >= 10 x (tolerance of both nodes) x BIT, about 10 % of a bit for a node 1 % slow. Measured: SJW 12 ticks (6 %) at 125 kbit/s loses sync with a -1 % transmitter (the first falling edge after SOF comes 8 bits later, 16 ticks late); 12.5 % passes. Early edges (a faster node) are always seen because the window starts right after the sample.
  • Transmit: drive at the bit start, the bookkeeping of the bit as sent and the choice of the next bit, the readback at the sample point (the bus level SP ticks after the TXD edge), compare, the next bit start: SP >= 36 and BIT - SP >= 10 ticks, whatever SJW is (subsection below). With chip B of can_j7.md lengthening a dominant pulse on a recessive bit, the chip judges the bus level 3000 ns after its own TXD edge (250 kbit/s, SP 75 %), 2880 ns after the bit start at the bus. Until 2026-11-18 the readback was at SP - SJW (2320 ns after the TXD edge, 55 % of the bit at the bus) and sending needed BIT - SP + SJW >= 40 ticks.
  • ACK of a received frame: from the slot start (subsection "Receive: the ACK from the slot start" below). The CRC is checked at the last CRC bit, the delimiter is sampled at SP, and a recessive delimiter is followed by the ACK BIT - SP + 1 ticks after that sample, until the end of the slot + SJW. Until 2026-11-18 the ACK was decided after the delimiter's resync window and its processing: it started 28 ticks after the window end (slot start + SJW), at 500 kbit/s as late as 72 % of the slot.
  • The EOF, intermission and error flag waits (rwt) are counted in BIT periods with 5 ticks extra per bit (they only need to be at least as long); the bus idle bits (idl, txw) are exactly BIT.

Bus integration: 11 recessive bits after start. A pending request is sent after the 3 intermission bits; a dominant level during the intermission is taken as SOF.

Bus idle and the SOF (2026-11-18)

A SOF taken late puts the whole frame late on the chip's bit grid: the hard sync sample falls SP + the delay after the edge, and the resynchronization corrects an early edge by 3 ticks at most (the window opens 9 ticks after a recessive sample). At 500 kbit/s (BIT - SP = 12 ticks at SP 38) a delay of about 10 ticks puts the first sample into the first identifier bit: the KD240's 0x328 recorded as 0x628 with a CRC error (the board session, 2026-11-18), 0x325 as 0x645 in test_b500_sof_race.

Until 2026-11-18 the chip had two places where that could happen:

  • Bus idle: one rwt bit per pass (idle, ifs, the request test, tsetr again); after each bit end 12 instructions ran before waitp watched RXD again, so a SOF there was taken up to 12 ticks late.
  • A request held at the end of the intermission: 10 instructions from the end of the last intermission bit to low TXD, RXD not read; a node SOF in them was missed and the chip sent its own SOF up to 10 ticks after the node's, on its own grid (a transmitter does not resynchronize), and after the lost arbitration received the node's frame on that grid.

Now (idl, txw in can_gen.pe): the timer runs on without tsetr (each twait and waitp.to ends one period after the last, docs/architecture.md), so between two waits of the idle loop there are only the 4 instructions of the request test. A request found there is sent at the end of the next bit (txw): RXD is watched until then, a node SOF in it is taken as SOF (jnz sof), and the chip's SOF follows 2 ticks after the bit end (shout of TXBUF bit 7, the SOF the host wrote). So the intermission counts in ifs are one bit shorter (2, 10) and the last intermission bit is the one in idl or txw. From the idle loop the path from the edge to the hard sync tsetr is the same 4 instructions as after a resync edge (rxe); from rwt (a SOF in the first intermission bits) it stays 6, 2 ticks later.

Receive: the ACK from the slot start (2026-11-18)

The KD240's CAN controller at 500 kbit/s (sample point 0.714) did not see the chip's ACK and repeated its frame without end (the board session, 2026-11-18): the ACK started at 0.64 to 0.71 of the slot (test_b500_ack_grid on the firmware before, node rates -0.79, 0 and +0.79 %, 32.4 to 35.1 ticks after the slot start). The receive path now decides the ACK at the last CRC bit and drives it from the slot start (rcc, rcd in can_gen.pe):

  1. pda of the last CRC bit (field event 4, during the next bit): own frame (MODE bit 7) as before; a receiver checks for a stuff bit next (it goes through the loop first and pst comes back here, ps2) and for a good CRC (register 0 after the last CRC bit). A CRC error goes on through the loop as before (no ACK, flag after the slot).
  2. rcd: the delimiter's sample (smp, SP after the bit start). Dominant: the loop as before (a CRC error). Recessive: a tsetr of TT2 = BIT - SP - 8 seven instructions after the sample, a twait, and low TXD: BIT - SP + 1 ticks after the sample (13 at 500 kbit/s with SP 38), one tick after the bit start of the chip's bit grid.
  3. The delimiter's bookkeeping then runs as after an edge (rxe, TS1); ev5 sees r7 = 0x81 (ACK on) and keeps the ACK to the end of the slot + SJW (ev5a), 2 ticks longer than before; 0x80 is a CRC error or a dominant delimiter.

Path lengths: from the tsetr before the last CRC bit's processing to the delimiter's sample, 26 instructions (the call of proc, 11 to the field event, MODE 5, stuff 4, CRC 4, call smp), within RST - 1 = 27 at the receive limit SP - SJW = 31, so the receive budget is unchanged; after a stuff bit, 18. From the TT2 tsetr to its twait: none (TT2 >= 1).

Transmit: readback at the sample point (2026-11-18)

The transmitter does the work of a bit before it reads the bit back (tdb, thb, tsb, tbc and the tails after them in can_gen.pe):

  1. Bit start (a twait ends): shout drives the bit on TXD; 3 ticks later a tsetr starts TT1 = SP - 3.
  2. The bit as sent is read from the TXD pin into the bus history and the byte, and pda (proc without its stuff-bit test) counts it, feeds it to the CRC, stores a full byte and follows the fields. Then the next bit is chosen: a stuff bit when the five bus bits up to this one are equal (its value goes to frame buffer 0x24), the top bit of the CRC register in the CRC field, otherwise the next request bit (r7 bit 7; shout rotates r7). A stuff bit only enters the bus history. All this assumes that the bit is read back as sent.
  3. Readback: the twait of TT1 ends and the next instruction reads RXD, SP + 1 ticks after the shout. Through the two-flop pin synchronizer it takes the bus level of 2 clocks before, SP ticks after the TXD edge: the configured sample point counted from the bit as the chip drives it. With a transceiver loop delay d that is SP - d after the bit start at the bus; the chip has no measure of d.
  4. Four instructions compare TXD with RXD, three start TT2 = BIT - SP - 8, before a stuff bit one more loads it from 0x24, and the next twait is the next bit start.

Each readback tail serves one kind of bit, chosen in step 2 from the field counters, so a difference needs no further test:

Tail Bit read back Dominant read, recessive sent Recessive read, dominant sent
trH, trSH (a stuff bit next) the arbitration field: SOF, identifier, RTR; SRR and IDE of an extended frame lost arbitration (tlo) bit error
trD, trSD (a stuff bit next) control field (IDE of a standard frame, r1, r0, DLC), data, CRC, CRC delimiter (read in ttl), every stuff bit bit error bit error

Lost arbitration (tlo): the bookkeeping counted a recessive bit that was dominant. tlo waits for the next bit start, starts the receive timer so that the next sample falls where the readback would have been, and corrects what the bookkeeping did with the recessive bit: bit 7 of the bus history, bit 0 of the byte, the byte already stored if the bit completed one, the CRC (fed with 1 instead of 0, the register is the generator 0x8B32 away from the right value, so it is XORed with it), and the header length if the bit was IDE (the extended frame the chip sent has 25 more header bits, the standard frame that won has 5). Then it receives the rest like the receive path (record status 0x21). Bit error: the error flag starts at the next bit start, as before (tbe); while it runs, bun takes the bit back out of the record (byte, bit count, and the record pointer if the bit had completed a byte), unless it was a stuff bit, which is never counted (the five bus bits before it are equal). So the record of a bit error ends after the bits before the bit in error, as it did before the change.

Why: receiving needs 28 ticks between the end of the window and the next sample (24 of them in proc). Sending needs 36 ticks from the bit start to the readback (the bookkeeping of the bit and the choice of the next, 32 instructions on the longest path) and 10 from the readback to the next bit start (the compare and the timer, 8 on the longest path); the two parts of a bit are separate, so a bit of 46 ticks is the shortest for sending, and the receive budget is counted from the receive window as before.

Fault confinement

Rules from Bosch CAN Specification 2.0, Part A section 7 "Fault Confinement" (the same twelve rules are Part B section 8), read from the PDF copy for this work. ISO 11898-1 is paid and was not read. Two public secondary sources agree on the parts they cover: Microchip MCP2515 data sheet DS20001801J section 6.7 (error-passive when a count reaches 128, bus-off when TEC exceeds 255, recovery after "128 occurrences of 11 consecutive recessive bits", and the note that the MCP2515 recovers by itself after 128 x 11 bit times of idle bus) and the Kvaser page "CAN Error Handling" ("transmit errors give 8 error points, and receive errors give 1 error point", error passive above 127, bus off above 255, "A Passive Error Flag comprises 6 recessive bits"; it does not list the exceptions or the recovery).

Rule (Bosch 2.0 Part A 7) In can_gen.pe
1. Receiver detects an error: REC + 1 (not for a bit error while sending an active error flag) after the error flag of a received frame (status 0x01..0x04, 0x2x)
2. Receiver sees dominant as the first bit after its error flag: REC + 8 sampled at the sample point of the first bit after the flag
3. Transmitter sends an error flag: TEC + 8. Exception 1: error passive, ACK error, no dominant bit during its passive flag. Exception 2: recessive stuff bit before RTR read dominant + 8 after the flag of an own frame; exception 1 done (the passive flag records whether any bit was dominant); exception 2 not done: such a bit is a bit error in this firmware (+ 8; until 2026-11-18 it counted as lost arbitration and the chip went on as a receiver)
4, 5. Bit error while sending an active error flag: + 8 not done: the chip does not read back its own flag bits
6. 14th consecutive dominant bit after an active flag (8th after a passive flag) and every 8 more: + 8 counted at the sample points of the bits after the flag (the 8th, 16th, ... dominant one)
7. Successful transmission (ACK, no error up to the end of EOF): TEC - 1 unless 0 after EOF of an own frame (status 0x81)
8. Successful reception up to the ACK slot and the ACK sent: REC - 1 if 1..127; above 127 set to 119..127 right after the ACK slot; above 127 the chip sets 127
9. Error passive when TEC or REC is 128 or more; the error that makes the node error passive is still signalled with an active flag the flag type is chosen from STATE before the counts change
10. Bus off when TEC is 256 or more STATE 2, address 20 set; TXD stays recessive, no ACK, no flags, no frames, no records
11. Back to error active when both counts are 127 or less STATE recomputed after every count change
12. Bus off to error active, both counts 0, after 128 occurrences of 11 consecutive recessive bits one sample per bit time, a dominant sample restarts the current sequence; then the pending request is sent

Passive error flag (3.1.3): "six consecutive recessive bits unless it is overwritten by dominant bits from other nodes"; "the error passive station waits for six consecutive bits of equal polarity, beginning at the start of the PASSIVE ERROR FLAG". The chip samples from the flag start (at the sample point, then every bit) until six samples in a row are equal. Suspend transmission (3.1.5): after a frame it sent (good or with an error) an error passive chip waits 8 bits more after the intermission; a frame of another node in that time is received as usual. Error passive nodes still acknowledge good frames.

Limits of the fault confinement:

  • Rules 4 and 5 (a bit error while sending an active error flag adds 8) are not done: the chip does not read back its own flag. Exception 2 is not done (see the table).
  • The receive error count stops at 255 (the rules give no upper end; receivers never go bus off).
  • Above 127 a good reception sets the receive count to 127 (the rule allows 119 to 127).
  • The waits after an error flag are counted with rwt, a few ticks longer than BIT per bit, so the next frame of the chip starts 1.3 to 1.8 bits later than the minimum (measured 18.31 bits after the ACK slot instead of 17 while error active, 26.41 to 26.74 instead of 25 while error passive, 2026-11-18). Later is allowed; earlier would not be.
  • The ACK error flag starts 0.09 bit before the end of the ACK slot at 250 kbit/s (the standard: at the next bit; 0.06 before the transmit readback moved to the sample point). This timing comes from the earlier firmware (the ACK slot wait), not from fault confinement.
  • Bus off recovery is automatic (like the MCP2515); there is no "wait for the host" option.
  • The counts and the state are checked in simulation only, against a model of the rules, not against a real CAN controller.

CRC-15 setting (G11)

The CRC-15/CAN setting of the crc instruction here is the one firmware/crc.pe uses in test/test.py, test test_crc_standard_check_values (case "CRC-15/CAN"): polynomial register 0x8B32 (0x4599 << 1, left aligned), init 0x0000, MSB first (crc, not crc.lsb), CRC = register >> 1, check value 0x059E for "123456789". can_gen.pe sets crcpoly 0x8B,0x32 on hart 1, crcset 0,0 at every SOF and feeds every destuffed bit from SOF to the last CRC bit with crc r3,1 (bit 0 of r3, MSB-first form). A good frame leaves register 0 after the last CRC bit and 0x8B32 after the recessive delimiter. test_crc_bit_counts in test/test.py checks that CRC-15/CAN fed one bit at a time gives the byte-wise result. The test of this firmware compares the chip's CRC bits of every sent frame with crc15() of test/test_can.py (shift-register form of the specification, checked there against polynomial division).

CAN 2.0A firmware (firmware/can.pe)

Classic CAN with standard 11-bit identifiers, data frames only. One bit engine sends and receives, computes bit stuffing and CRC-15 itself, acknowledges good frames, reads back every bit it sends and stops on lost arbitration or a bit error. It uses 131 of the 512 words of program memory and runs on hart 1 alone (CTRL = 2, START1 = label hart1); hart 0 stays stopped. Because one engine does both directions, the chip's own frames are decoded like any other frame and come back to the host as an echo.

Pins and transceiver

Pin Signal Direction
P0 (uio[0]) TXD to the transceiver output, driven high (recessive) at start
P1 (uio[1]) RXD from the transceiver input

Dominant = 0 on both. Wiring for a 3.3 V transceiver (for example TI SN65HVD230 / SN65HVD232, TI TCAN334 or NXP TJA1051T/3 with a 3.3 V VIO):

chip P0 (TXD) ---- TXD   transceiver   CANH ----+---- bus CANH
chip P1 (RXD) ---- RXD                 CANL ----|---- bus CANL
3.3 V ----------- VCC (VIO)            Rs/S ---- GND (high speed mode)
GND ------------- GND                         120 ohm at each end of the bus

The firmware does not use any other pin. P0 also feeds back into the chip (pad input) and is read to tell a lost arbitration from a bit error.

Host framing

Host to chip: one transmit request

Byte Content
c0 bits 7..6 = ID10 ID9, bits 5..4 = 0, bits 3..0 = n, the number of bytes that follow (2 + data length)
b1 ID8 .. ID1
b2 ID0, RTR = 0, IDE = 0, r0 = 0, DLC3 .. DLC0
data DLC bytes, first byte first, each MSB first on the bus

In Python: [((id >> 9) << 6) | (2 + len(d)), (id >> 1) & 0xFF, ((id & 1) << 7) | len(d)] + d.

  • The data length must equal the DLC, 0 to 8. Remote frames (RTR = 1) are not supported.
  • The firmware reads c0 when the bus is idle, b1 when c0's bits are out, and each later byte at the bit where the previous byte ends. A byte that is not in the FIFO by then stalls the bus with the current bit level held (it can be dominant). At 125 kbit/s a byte lasts 64 us or more, so the host only has to keep the 4-byte FIFO topped up (as test_can.py does with STATUS polling).

Chip to host: one record per frame on the bus

Byte Content
b0 bits 2..0 = SOF ID10 ID9 (bits 7..3 are left over, mask them)
b1 ID8 .. ID1
b2 ID0 RTR IDE r0 DLC3..0
data min(DLC, 8) bytes
crc_hi CRC14 .. CRC7
crc_lo CRC6 .. CRC0, then the CRC delimiter bit
trailer see below

id = ((b0 & 3) << 9) | (b1 << 1) | (b2 >> 7). The record length is always 6 + min(b2 & 15, 8), so the host can split the stream without markers.

Trailer Meaning
0x01 Received, CRC good, CRC delimiter recessive, ACK sent
0x00 Received, CRC or delimiter bad: no ACK
0x80 Own frame sent and ACKed
0x81 Own frame sent, no ACK
0x40 + x Own frame stopped: read dominant while sending recessive (lost arbitration). The rest of the record is the winning frame as received, x = 1 if it was good and ACKed
0x20 + x Own frame stopped: read recessive while sending dominant (bit error). The rest of the record is whatever the bus carried, counted out to the decoded length

After 0x40 or 0x20 the firmware reads and drops the request bytes it had not used yet, so the next request starts cleanly. It does not retransmit; the host resends.

The chip pushes record bytes as they complete and blocks if the host FIFO (4 bytes) is full, which would break the bit timing. The host has to read during the frame. At 125 kbit/s a byte takes 64 us or more.

What fits, and what was left out

Fits (131 words; 128, the whole memory before it grew to 256, until 2026-11-13): TX with stuffing, CRC-15, readback on every bit, arbitration loss, bit error, ACK check; RX with hard sync on SOF, resync on every recessive to dominant edge, destuffing, CRC-15 check, CRC delimiter check, ACK; record framing; the 11-bit bus idle rule before sending; dropping the unused part of a stopped request.

Not done (no room, or not asked):

  • Error frames, overload frames, error counters, error passive / bus off (Bosch 2.0A §3.1.3, §3.1.4, §7). On an error the firmware just stops sending; it never sends an error flag. Stuff errors are not reported; a frame with one fails the CRC instead.
  • Automatic retransmission.
  • Remote frames and extended (29-bit) frames. On the bus they decode as garbage and get no ACK (CRC fails); the record length still follows the decoded b2.
  • Form checks of ACK delimiter and EOF, and of IDE and r0 on receive.
  • The transmitter does not resynchronize. It does not need to after winning arbitration (rule 4 of §8 lets a transmitter skip edges it causes itself), but during arbitration against a node more than a few 0.1 % off it can drift.
  • A DLC above 8 is received as 8 data bytes (ISO 11898-1 behaviour; Bosch 2.0A §3.1.1 forbids those values). It cannot be sent.

Timing

One tick = 40 ns. At 125 kbit/s a bit is exactly 200 ticks (8.000 us), at 250 kbit/s 100 ticks, so the firmware's own bit rate has no quantization error; only the 50 MHz clock tolerance remains.

twait ends at an absolute time, so every period below is set by a tset at a fixed number of ticks after an event (tset X issued k ticks after a twait makes the next twait end k + X ticks after it). The constants and how they follow from the bit time are in params() in test/test_can.py; for 125 kbit/s they are the .equ defaults.

Receive

  • Hard sync: in bus idle the loop polls RXD every 4 ticks; the first dominant level starts the bit time and the first sample is 75 % of a bit after the edge.
  • After a recessive sample the firmware waits for a falling edge until 1/8 bit after the expected end of the bit (window W). An edge restarts the bit time (sample 75 % of a bit after it, like a resync with an unlimited jump width). No edge: the next sample is one bit after the last. After a dominant sample there is no edge to look for.
  • Processing of a bit (destuff, CRC, byte, header) runs after the window and must end before the next sample: at most 62.5 % of a bit minus 3 ticks.
  • Drift: stuffing allows at most 10 bits between recessive to dominant edges (five equal bits, a stuff bit, five more). At +-1 % that is +-10 % of a bit at the sample point, inside the 75 % sample point and the 12.5 % late window. 8-byte frames at +-1 % pass in the test; without resync they would drift 1.3 bits over a 135-bit frame.

ACK (the hard part)

The ACK decision needs the CRC remainder after the delimiter bit, which is known only after that bit has been processed. The delimiter is recessive, so its processing runs after the resync window, which ends at A + W (A = start of the ACK slot). The path from there to low TXD is fixed for a good frame (30 ticks), so the chip drives TXD low at A + W + 30 ticks and releases it at A + BIT + 2 ticks (ACKH is set from that path). If another node ACKs first, its edge ends the window early and the chip's ACK starts sooner.

Measured in test_can_rx and test_can_rates (model transmitter, 120 ns transceiver loop delay, numbers at the bus). The spread comes from the rate offset: the chip's bit grid lags or leads the transmitter by up to 10 bits of drift since the last resync edge. The test also checks that the ACK does not cover the transmitter's sample point of the CRC delimiter before it or of the ACK delimiter after it.

Margin to a transmitter that samples the slot at 75 % / 87.5 % (Linux default for these rates): 39 % / 51.5 % of a bit at 125 kbit/s, 25.6 % / 38 % at 250 kbit/s, worst case. The ACK ends at most 9.2 % into the ACK delimiter, far before its sample point.

Transmit

  • The chip starts a frame only after 11 recessive bit times (ACK delimiter, 7 EOF bits, 3 intermission bits, Bosch 2.0A §3.1.1, §3.1.5 and §9.1 rule [6]).
  • Each bit: drive at the bit start, read back at SPT (50 % at 125 kbit/s, 35 % at 250 kbit/s), then decide the next bit before the next bit start. The decision path is at most 60 ticks, which sets the 250 kbit/s sample point (BIT - SPT >= 60).
  • The readback point is early, but the bus in the target setup is short: the round trip (transceiver loop plus twice the cable delay) must be below SPT, 4 us at 125 kbit/s and 1.4 us at 250 kbit/s.
  • The ACK slot is sampled at the same point inside the slot.
