File Role Words
firmware/rcser.pe Hart 0 sends frames like an RC receiver, hart 1 takes them like a flight controller; each picks S.BUS or CRSF from the data memory. S.BUS: 100,000 bit/s 8E2 inverted, 25-byte frames (0x0F, 16 channels of 11 bits, flags with failsafe and frame lost, 0x00), parity, stop bits, header and footer checked. CRSF: 416,667 bit/s 8N1, C8 len 16 + 22 bytes + CRC-8 (polynomial 0xD5), length 2 to 62 and CRC checked, other frame types skipped. The channels are packed and unpacked bit by bit in the firmware. 289 of 512 (hart 1 from word 131)

No RTL change: tset/twait bit grid, shout.lsb, shin.lsb, waitp.to, the CRC unit (CRC-8, left aligned, MSB first), ld/st, the host FIFO. Checked in simulation only, not on a board.

Sources

Source Used for
TBS (Team BlackSheep), "CRSF Protocol", github.com/tbs-fpv/tbs-crsf-spec, crsf.md (published by the protocol's owner) flight controller side: non-inverted UART, 416666 baud 8N1 (RC to TX module: 400 kbaud); frame: sync byte 0xC8, frame length = bytes after it (type, payload, CRC), valid 2 to 62, at most 64 bytes in all; CRC-8 polynomial x^7 + x^6 + x^4 + x^2 + 1 (0xD5) over type and payload; 0x16 RC channels packed: 16 channels of 11 bits in 22 bytes; 992 is 1500 us
Bolder Flight Systems, sbus library README (github.com/bolderflight/sbus); Futaba publishes no S.BUS specification, so this is a secondary source inverted serial, 100,000 baud, 8 data bits, even parity, 2 stop bits; 25 bytes: header 0x0F, 16 channels of 11 bits in bytes 1 to 22, flags byte (bit 0 ch17, bit 1 ch18, bit 2 frame lost, bit 3 failsafe), footer 0x00; frames every 10 or 20 ms depending on the system (other sources say 14 and 7 ms)

Pins

Constant Default Use
TX P0 sender output, push-pull. S.BUS idles low (inverted), CRSF high
RX P1 receiver input. Assemble with RX = 0 for a loopback on one chip

Data memory and host interface

Address Name Use
0x00 TMODE hart 0: 0 S.BUS, 1 CRSF (read once at start)
0x01 RMODE hart 1: 0 S.BUS, 1 CRSF
0x02 TFLG S.BUS flags byte sent
0x03, 0x04 TGAPH/L idle bits after each frame (the frame period is set by the host)
0x05 TCNT frames sent
0x06 RCNT frames taken
0x07 RERR frames dropped: parity, stop bit, header, footer, short frame, CRC, length outside 2 to 62
0x08 RFLG S.BUS flags byte of the last frame taken
0x09 ROTH CRSF frames of another type, skipped
0xA0-0xBF channels sent, 16 x (low byte, high byte)
0xC0-0xDF channels received, same layout
0x20-0x3A, 0x40-0x7D frame buffer: frame being sent, frame being received

Host FIFO to hart 0: triplets (n, lo, hi); channel n (0 to 15) becomes hi:lo, n = 16 sets the S.BUS flags to lo. One triplet is taken before each frame.

Timing

S.BUS: one bit is 250 ticks (10.00 us). CRSF: 60 ticks (2.400 us, 416,667 bit/s, the TBS rate for the flight controller side; the older 420,000 bit/s would be 59.52 ticks). Every edge is one tick after a period boundary and the bytes of a frame follow each other without a gap. Between two frames the sender has a 4,000-tick window (160 us) for the host triplet, the packing of 176 bits and the CRC, then TGAP idle bits.

The S.BUS receiver takes a frame when the line has been quiet for 1 ms and then gets 25 bytes, each starting within 4 bits of the one before. The CRSF receiver hunts for 0xC8, then takes the length and that many bytes, each within 10 bits of the one before.

Tests

test/test_rcser.py, run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_rcser

The models are written from the sources above, not from the firmware: 11-bit packing least significant bit first, CRC-8/DVB-S2, frame builders, the line levels of an S.BUS byte (inverted) and a CRSF byte, a decoder that samples each bit of a recorded line in its middle and groups back-to-back bytes into frames, and senders at any bit time.

Controls

Each control is a copy of rcser.pe with one planted bug, run with RCSER_FW=<path>.

All three fail at the check they aim at.

Planted bug Test First failure
S.BUS odd parity (ldi r6, 0 in txsb) test_sbus_tx the parity of the first byte, 0x0F
CRSF CRC with polynomial 0x07 test_crsf_tx the CRC of the first frame
S.BUS receiver without the footer check test_sbus_rx footer 0x04: the frame is taken, RERR not counted

Limits

  • S.BUS: the frame period is the frame plus a host-set number of idle bits (14.000 ms in the test); the receiver takes footer 0x00 only (S.BUS2 telemetry footers are dropped) and does not time out to failsafe by itself (the host reads RCNT and RFLG).
  • CRSF: only the 0xC8 sync byte; only frame type 0x16 is unpacked (others are counted and skipped); the sender sends only RC channel frames.
  • 416,667 bit/s, not 420,000 (-0.79 %, inside a UART's tolerance; the receiver takes both, tested).
  • The firmware does the S.BUS inversion itself; level shifting and a half-duplex CRSF wire (both directions on one pin) are outside.
  • The S.BUS receiver needs 1 ms of quiet line before a frame, so it misses a frame that starts less than 1 ms after the receiver starts (in the loopback test the first frame comes 160 us after the start and is not taken; the later ones are).
  • Simulation only: no board, no gate-level run.
