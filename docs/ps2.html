File Role Words
firmware/ps2_host.pe PS/2 host (the 8042 side of a PC): receives bytes from a keyboard or mouse, checks parity and the start and stop bits, asks for a resend after an error, sends bytes with inhibit and request to send, and holds the device off while the host FIFO is full. One hart. 105 of 512
firmware/ps2_device.pe PS/2 keyboard: sends scan codes from the host FIFO, takes commands from the PS/2 host with the ack bit and answers them as a keyboard does (0xFA, 0xEE echo, 0xFE resend, 0xFF reset then 0xAA), and stops and sends the byte again when the host inhibits in the middle of it. One hart. 108 of 512
firmware/ps2_loop.pe Both on one chip at the same time: hart 0 is the host on P0/P1, hart 1 the keyboard on P2/P3, the two pin pairs wired together outside the chip. 245 of 512 (hart 1 starts at word 130)

Word counts are from tools/peasm.py. This protocol was not part of the design when the RTL was written. It uses only existing instructions (low/rel, shout.lsb.od, shin.lsb, waitp.to, tset/twait, the CRC unit as a parity counter, host FIFO, ld/st in the loopback); the RTL is unchanged. Checked in simulation only, not on a board.

Source

IBM's PS/2 Hardware Interface Technical Reference, where the interface is defined, is not openly published. The timing here comes from one secondary source based on it:

  • Adam Chapweske, "The PS/2 Mouse/Keyboard Protocol" (computer-engineering.org, 1999; mirror: burtonsys.com/ps2_chapweske.htm), and the keyboard commands from the same author's "The PS/2 Keyboard Interface" (computer-engineering.org, 2003).

The IBM text itself was not checked.

Pins

Firmware CLK DAT
ps2_host.pe, ps2_device.pe uio[0] (P0) uio[1] (P1)
ps2_loop.pe host (hart 0) P0 P1
ps2_loop.pe keyboard (hart 1) P2 P3

All lines are open drain: the firmware only drives them low (low, shout.od) or releases them (rel), so the board needs pull-ups (the PS/2 connector of a keyboard has its own; 5 to 10 k on the host side). The pins are .equ values.

Two harts on one chip

pin_out and pin_oe in src/pe_core.v are one register each, shared by the two harts. Each pin instruction rewrites one bit of them in the cycle of the hart that runs it, so the two harts can drive different pins without disturbing each other. On the same pin they cannot both hold the line: a rel from one hart clears the enable bit that a low from the other hart set, and the last write wins. PS/2 needs a true wired-AND on CLK (the host holds CLK low while the device releases it after a clock pulse; that is how an inhibit is seen), so the loopback gives each side its own pins and joins them outside the chip: P0 to P2, P1 to P3. The test does the same with a wired-AND of the two pins of each net. The control m6 below runs the same firmware with both sides on P0/P1.

The host FIFO has one reader, so in the loopback hart 0 takes all host commands and hands keyboard bytes to hart 1 through a ring in the data memory (0x00 to 0x0F, HEAD 0x10 written by hart 0, TAIL 0x11 by hart 1). The keyboard hart does not write the FIFO; everything it sends shows up in the host's reports.

Host interface

ps2_host.pe

Direction Bytes
Host to chip each byte is sent to the PS/2 device
Chip to host two bytes per event: status, then the byte
Status Meaning
0x00 byte received from the device; +1 parity error, +2 start or stop bit wrong (then the chip sends 0xFE)
0x04 frame cut short: no clock edge for 100 us; the byte holds the bits so far
0x80 byte sent and acknowledged
0x81 byte sent, no ack
0x82 the device gave no clock within 15.7 ms

A byte that arrives from the host while a frame is coming in from the device is sent at the next data bit: the chip inhibits in the middle of that frame (a keyboard drops it and clears its buffer, as for any command). While the output FIFO is full the chip holds CLK low, so the device keeps its bytes instead of sending them into a full FIFO.

ps2_device.pe

Direction Bytes
Host to chip each byte is a byte (scan code) to send to the PS/2 host
Chip to host two bytes for each byte the PS/2 host sent: status (bit 0 parity error, bit 1 stop bit error), then the byte

The chip answers the PS/2 host by itself (table above). Bytes that need more than 0xFA, such as the two ID bytes after 0xF2, are written to the FIFO by the host after it has seen the report. A received byte clears the output buffer: the byte waiting or to be sent again and the bytes still in the FIFO are dropped. At start the chip sends 0xAA. txb waits for room, so the host should read the reports; the chip does not watch the bus meanwhile.

ps2_loop.pe

Host to chip Meaning
0x01 v the host side sends v to the keyboard side
0x02 v v goes into the keyboard buffer and the keyboard side sends it to the host side

The chip answers with the reports of ps2_host.pe, plus 0x40 v when the keyboard buffer was full and v was not taken. Every command starts with an inhibit of 120 us, so a key queued while the keyboard is sending makes it send that byte again, and 0x01 in the middle of a byte makes the keyboard drop it.

Parity

The parity is not counted bit by bit. Each hart's CRC unit with polynomial 0x0001 keeps in bit 0 the XOR of every bit fed in: for the LSB-first form the register shifts right and XORs the polynomial when crc[0] ^ bit is 1, so a register that starts at 0 never holds more than bit 0. crc.lsb r0,8 gives the parity of a byte in one instruction, and crc.lsb r2,1 adds the received parity bit.

Tests

test/test_ps2.py (cocotb). The keyboard model and the host model are written from the Chapweske tables above, not from the firmware; only the FIFO byte formats come from the firmware files. The keyboard model runs at the corners of the clock ranges, and the host model inhibits at the start bit, in the data, at the parity and stop bits and after the 11th clock. A log of every CLK and DAT edge is checked afterwards: the device's clock halves (30 to 50 us), where DAT changes against the clock (5 to 25 us before the fall, at least 5 us after the rise, never while CLK is low), the 50 us of idle before each byte, the host's inhibit before each request to send (timed from the chip's own pin driver), and that the host never changes DAT while the keyboard holds CLK high. Run from a private directory:

T=<repo>/test; R=$T/sim_build/<name>; mkdir -p $R; cd $R
PYTHONPATH=$T make -B -f $T/Makefile PWD=$T SIM_BUILD=$R/build COCOTB_TEST_MODULES=test_ps2

One run of the whole module on 2026-11-11: TESTS=12 PASS=12 FAIL=0, 177 ms of simulated time (about 27 minutes of wall time on a loaded machine; COCOTB_TEST_FILTER runs one test). test/test.py passed 19 of 19 on the same branch.

The keyboard model follows the source in what it does itself: it aborts on an inhibit before the 11th clock, clears its buffer on a command and clocks on while DAT is held low at the stop bit. The models see the firmware only through the bus and the FIFO bytes; only the monitor that times how long the chip holds CLK low reads the chip's pin driver.

Limits

  • 0xAA after a reset follows the 0xFA at once; a keyboard sends it after its self test (500 to 750 ms after power on).
  • The device answers every byte with good parity and stop as a valid command; it has no scan code tables, typematic repeat or LED state of its own. The host gets every command byte as a report and can add answers through the FIFO.
  • The host waits 15.7 ms for the first device clock, a little more than the 15 ms of the source.
  • ps2_device.pe waits for room in the output FIFO after each received byte and does not watch the bus meanwhile; ps2_host.pe holds CLK low instead, so its device waits.
  • Mouse packets are bytes like any other for the host; the mouse command set is not modelled.
