Each runs on hart 0 alone (CTRL 0x01 value 1). Load and start them like the other firmwares (docs/architecture.md, Host SPI). Settings are written with DATA_W (0x12) while both harts are stopped, before the run; soft reset keeps the data memory. One tick is 40 ns.

Mode numbers follow the usual CPOL/CPHA definition (also the bit layout of Linux SPI_CPHA = 1, SPI_CPOL = 2): CPOL is the SCK level while CS is high. With CPHA = 0 each side puts its first bit out when CS falls and the next bit on every trailing edge, and both sides sample on the leading edges. With CPHA = 1 data change on the leading edges and are sampled on the trailing edges. Mode 0 = CPOL 0 CPHA 0, mode 1 = 0 1, mode 2 = 1 0, mode 3 = 1 1.

SPI master: firmware/spi_master_gen.pe

Pins

Pin Use
uio[0] (P0) SCK
uio[1] (P1) MOSI
uio[2] (P2) MISO (input)
uio[3] (P3) CS_N

Settings (data memory)

Address Name Meaning Default
0x00 MODE bit 0 CPHA, bit 1 CPOL, bit 2 LSB first; other bits ignored 0 (mode 0, MSB first)
0x01 HALFH SCK half period in ticks, high byte
0x02 HALFL low byte. 0x0000 means 10 ticks (1.25 MHz); the firmware then writes 10 into 0x02. Minimum 4 (3.125 MHz); below 4 the late flag rises (see Speed) 10
0x03 FILL MOSI byte of FILL transfers 0 after power-on

Usable half periods are 4 to 65535 ticks: SCK from 3.125 MHz down to 191 Hz. The data memory keeps its contents over soft reset, so a host that runs another firmware before must write all four bytes.

Host commands (FIFO)

One transfer is FLAGS, LEN, then LEN data bytes (none with FILL). LEN 1 to 255, 0 means 256.

FLAGS bit Name Meaning
7 FILL The host sends no data; MOSI sends the FILL byte LEN times (reads)
6 NORX No MISO bytes go back to the host (writes)
5 KEEP CS stays low after the transfer; the next transfer continues the same CS frame
4..0 Ignored, write 0

Reply: the LEN MISO bytes in order, unless NORX. Transfers run in FIFO order, so a host can queue a whole sequence (for an SPI flash: write enable, page program, then read status) and read only the bytes it asked for. Example, command 0x9F then a 3-byte read in one CS frame: 0x60 0x01 0x9F (NORX | KEEP), 0x80 0x03 (FILL); the reply is 3 bytes.

The transfer length has no upper limit beyond 256 per command: KEEP chains any number of commands into one frame.

Waveform

  • Every SCK edge is the instruction right after a twait, so inside a byte the half periods are exactly HALF ticks. The period restarts (tsetr) before each byte, after the byte has been fetched from the FIFO, so FIFO waits and the per-byte work only lengthen the SCK idle time between bytes; they never shorten a half period or raise the late flag.
  • SCK edges are shout r4, SCK with r4 = 0x55 or 0xAA: each shout writes the next bit of an alternating pattern, so CPOL and CPHA are data, not code. For CPHA = 0 the first shout of each byte writes the idle level (no edge) and the second one is the leading edge.
  • MOSI changes one tick (2 clocks) after the drive edge: setup before the sampling edge is HALF ticks minus 2 clocks, hold is at least HALF ticks.
  • MISO is read one tick after the sampling edge; through the two-flip-flop synchronizer this is the level just before the edge.
  • CS falls at least one half period before the first edge, rises one half period after the last byte ends, and stays high at least one half period. Between bytes SCK rests at the idle level for at least one half period plus the per-byte work.
  • MOSI is driven low at start and otherwise keeps the last bit sent. MISO is never driven.

Errors

SPI has no acknowledge, parity, CRC or arbitration, so a master cannot detect a bus error; the firmware sends exactly the bytes it was asked for. The one firmware error is a timing overrun: if a half period was too short for the code (HALF below 4), the hart's sticky late flag (STATUS byte 3 bit 3) rises. The host reads it after a run; soft reset clears it.

HALF (ticks) SCK Result
0x0123 (291) 85.9 kHz exact half periods

Fastest SCK: 3.125 MHz (HALF = 4). The limit is the second half of each bit: edge B, shin, djnz are three instructions between two twaits, so the period must be at least four ticks.

Between bytes SCK rests at the idle level for the per-byte work plus one half period: 52 clocks at HALF 4, 76 clocks at HALF 10 (measured). Throughput:

Case Measured
FILL + NORX burst of 64 bytes, HALF 4 (no host traffic during the transfer) 11034 clocks, 290 kB/s
Same, HALF 10 24102 clocks, 133 kB/s
Full duplex through the FIFOs, 32 bytes, HALF 4, with the cocotb host (host SPI at clk/10, STATUS polled before each FIFO access) 16162 clocks, 99 kB/s, bound by the host link

Slave output delay (test_spi_master_miso_delay): with a slave model that changes MISO d clocks after its drive edge, reads stay correct up to d = 7 clocks at HALF 4 (half period 8 clocks) and d = 19 clocks at HALF 10 (20 clocks), in modes 0 and 1. The master needs MISO valid one clock before the sampling edge.

SPI device: firmware/spi_device_gen.pe

Pins

Pin Use
uio[2] (P2) SCK input
uio[3] (P3) MOSI input
uio[4] (P4) MISO, driven low from the CS fall through the first byte and during writes, register data during reads, released while CS is high
uio[5] (P5) CS_N input
ui_in[7:3] N, MISO delay in ticks (0 to 31), read at every CS fall

The same pins as spi_device.pe (the board mapping).

Protocol

MSB first. The first byte after the CS fall is {R/W, A6..A0}:

  • R/W = 1: the following bytes read registers A, A+1, A+2, ... MISO carries the register while MOSI is ignored.
  • R/W = 0: the following bytes are written to registers A, A+1, ... A byte is stored after its eighth bit.
  • The address wraps from 0x7F to 0x00. A transfer may end after the first byte (no data).

Register map: register r is load/store address r.

Registers Backed by Host access
0x00 to 0x1F Data memory DATA_W (0x12, harts stopped) presets, DATA_R (0x13, any time) reads
0x20 to 0x7F Frame buffer bytes 0 to 95 ETH_W (0x40) presets, CAP_R (0x32) reads; register 0x20 + 2k is the high byte of word k. Only while the capture and Ethernet are idle (architecture.md, Load/store address space)

The firmware has no settings of its own in the data memory (all 32 bytes at 0x00 to 0x1F are registers) and never initializes the registers: what the host preset is what the external master reads.

Modes 0 and 3 need no setting. The firmware samples MOSI after each SCK rise and changes MISO after each SCK fall, waiting on levels (waitp). In mode 0 SCK is low when CS falls, so the wait for the first fall passes at once; in mode 3 SCK is high and the first fall is the leading edge. Both modes then run the same code.

Skew

N = ui_in[7:3] is read at every CS fall. Every MISO data change comes N ticks (2N clocks) later than with N = 0. The delay is a djnz loop of N + 1 ticks between the SCK fall and the shout, so the shift is exact.

Errors and end of transfer

  • Framing error: if CS rises after k = 1 to 7 SCK rises of a byte, the firmware pushes 0xE0 + k into the core-to-host FIFO (txb.nb, so nothing stalls; with a full FIFO the byte is lost). The bytes completed before the cut keep their effect (a write byte is stored after its eighth bit). A transfer that ends on a byte boundary, or a CS pulse with no clock, pushes nothing. Missed SCK edges from a too-fast clock show up here as well.
  • End of transfer: every wait for an SCK level has a timeout of TMO = 64 ticks (2.56 us), restarted every bit. On a timeout the firmware looks at CS for one tick and, if CS is still low, waits again at the same wait. A slow master or a pause of any length inside or between bytes is fine. Because the firmware returns to the very wait that timed out, an edge that comes during the check is not lost.
  • CS must stay high longer than TMO plus the check, or the next CS fall is not seen (see Speed).
  • Not reported: a MISO bit that comes too late for the master (the firmware cannot see when the master samples). The read speed limit below is where this starts.

Speed (measured, test_spi_device_max_sck, test_spi_device_skew)

Symmetric SCK, N = 0, at both hart phases, 4-byte writes and reads at random addresses, modes 0 and 3 give the same results:

SCK half period SCK Write Read
12 clocks 2.08 MHz pass pass
11 clocks 2.27 MHz pass pass
10 clocks 2.50 MHz pass FAIL (framing error 0xE5: edges missed)
9 clocks 2.78 MHz FAIL (framing error 0xE5)

Fastest SCK: 2.50 MHz for writes, 2.27 MHz for reads (N = 0), for a master that samples MISO at the very end of the low phase.

Where the limits come from:

  • Reads: from the SCK fall to the MISO change takes 8.5 to 9.5 clocks at N = 0 (two synchronizer flip-flops, the hart phase, jz, one djnz delay tick and the shout), measured on every MISO edge of a 4-byte read. The master samples half a period after the fall, so the half period must exceed this. Each further N adds exactly 2 clocks (measured for N = 0, 1, 7, 16, 31: shift 2N, the same on every edge, both modes, both hart phases). With N = 31 the latency is 70.5 to 71.5 clocks; reads pass at a half period of 100 clocks.
  • Every bit costs 9 ticks of code (two waits, jz twice, delay, shout, delay reload, timeout restart, djnz). The work between bytes is split between the low half of bit 7 (address step, bit counter) and the high half of bit 0 (load of the next register), 11 ticks each. At a half period of 10 clocks (10 ticks per SCK period) the code falls behind and misses edges, which the framing check then reports.
  • Writes: 7 ticks per bit plus 5 per byte (store, address step, bit counter). MOSI must be read after the rise and before the master changes it at the next fall; at a half period of 9 clocks the device falls behind and misses edges (framing error 0xE5).
  • CS high time: back-to-back reads worked with CS high for 135 clocks (2.7 us) and failed at 130 clocks, because the firmware sees CS high only at its next timeout (TMO = 64 ticks = 128 clocks) plus the one-tick check. Keep CS high at least 3 us.

Tests

test/test_spi.py. The device timing tests align to the hart slot from the clock (test/hart_slot.py); on the RTL they also compare that with u_core.slot, the one check left out at gate level (test/README.md). Run it from your own directory as for the other modules, COCOTB_TEST_MODULES=test_spi. 8 tests, all pass, about 310 s with Icarus (55 ms of simulated time).

The partner models are written from the mode definitions at the top of this file, not from the firmware:

  • SpiSlave (for the master): CPOL = SCK level while CS is high; CPHA 0: first bit out at the CS fall, next bit on each trailing edge, sample on leading edges; CPHA 1: out on leading, sample on trailing; MSB or LSB first. It answers byte k of the run with a fixed function of k and records each CS frame. It also checks the waveform against the requested HALF: SCK at the idle level whenever CS changes, edges inside a byte exactly HALF apart, at least HALF from the CS fall to the first edge, between bytes and from the last edge to the CS rise, MOSI setup at least HALF minus 2 clocks and hold at least HALF before and after each sampling edge, a whole number of bytes per frame. An optional delay moves its MISO changes later than the drive edge.
  • SpiHost (for the device): a mode 0 to 3 master that drives MOSI half a period before the leading edge (CPHA 0) or on it (CPHA 1) and reads MISO at the last moment before the sampling edge; it can cut a transfer after any bit, add random time to every half period and pause between bytes. RegModel is the register map of the Protocol section (128 bytes, wrap at 0x7F).

spi_master.pe: the period is set per byte

Until 2026-11-13 spi_master.pe ran tset HALF once, before its first wait for the host. Every wait for a host byte (rxb) then lay inside a running period, so the first twait after it found the period over: it ended at once and set the late flag. The clock was not wrong, but the first bit of such a byte was on MOSI for only 2 ticks before SCK rose instead of HALF - 2. The bring-up sequence left the late-flag check out of its spi step for that reason. The static deadline check reported it (petime.md).

Now tset HALF stands after the rxb of each byte, just before the first bit is shifted out (the same 20 words; the tset moved from word 3 to word 8). tools/petime.py gives PASS with a margin of 6 ticks at HALF 10, and HALF 4 is the smallest value that passes.

Measured at HALF = 10 (20 clocks) Before After
MOSI valid before SCK rises, first bit of a byte the hart waited for (test_spi_master) 4 clocks 20 clocks
MOSI valid before SCK rises, other bits 16 clocks 16 clocks
SCK high 20 clocks 20 clocks
SCK low between two bytes of a transfer, next byte already in the FIFO 20 clocks 36 clocks
Late flag after a transfer the hart waited for 1 0

The price is the fourth row: between bytes SCK stays low for HALF + 8 ticks, because the period restarts after the byte has been fetched. Inside a byte nothing changed. For bytes that follow each other without a wait for the host, a byte now takes 336 clocks instead of 320 at HALF 10 (8 highs and 7 lows of 20 clocks and the 36 between bytes): 148.8 kbyte/s, 1.19 Mbit/s, where it was 156.25 kbyte/s, 1.25 Mbit/s; SCK inside a byte is 1.25 MHz as before. The 3.125 MHz of the first screen and the throughput table above are those of spi_master_gen.pe, which already restarted its period for every byte and has not changed.

test_spi_master in test/test.py now records every SCK and MOSI edge and asserts SCK high = 20 clocks, SCK low at least 20, every MOSI change at least 16 clocks before the next SCK rise, and late flags 0. On the firmware as it was it failed with MOSI changes [16, 16, 16, 16, 4, 16, 16, 16] clocks before the next SCK rise. Rerun after the change (2026-11-13, RTL of 92b38df, Icarus Verilog 11.0, cocotb 2.0.1), every module that loads this file: test TESTS=19 PASS=19, test_symmetry 11 of 11, test_thirdparty 14 of 14 (cocotbext-spi as the device), test_petime 7 of 7, test_host_bringup 6 of 6 with the late-flag check back in the spi step (bringup.md). The FPGA self test (fpga/gen_script.py, section 3) assembles this file at build time: in the FPGA system simulation (fpga/sim/tb_fpga.v, Icarus) the whole script passes twice with the new file (pass=2 fail=0); no board bit was built with it.
